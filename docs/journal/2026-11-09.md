## 现象：DHCP 页只看到一半的终端

用户报的是"小米 AX3600 的 DHCP 列表只有那台网线连的 PC，虚拟机 ImmortalWrt 的 DHCP 列表只有那台手机，
可 DHCP 明明是 AX3600 发的"。按 `.local/lab-env.md` 的账号连上去读了一轮：

- `ax3600`（192.168.1.1，网关）的 `/tmp/dhcp.leases` 里当时只有 PC：`00:01:f3:96:43:cf → 192.168.1.162`；
- `owrt` 虚拟机（192.168.1.20，默认路由指回 AX3600）的 `dhcp.lan` 是 `dhcpv4='server'`、`ra='server'`，
  它自己的租约里就是手机：`0a:95:b7:16:e2:39 → 192.168.1.221`；
- 手机的 association 在 AX3600 的 `phy1-ap0` 上（`/sys/kernel/debug/ieee80211/phy1/netdev:phy1-ap0/stations/0a:95:…`），
  AX3600 的邻居表里也有它。

所以"DHCP 是 AX3600 发的不成立"：同一二层上两台 dnsmasq 都在答，谁先答谁写租约（今天再读，AX3600 那份租约里
也有手机了）。更关键的是租约文件的语义——**它记的是"本机 dnsmasq 发过谁"，不是"网内谁在线"**，AP 上天生为空。

## 为什么不做进 DHCP 页

| | 放进 DHCP 页 | 另写设备页 |
|---|---|---|
| 语义 | 页面叫"DHCP 租约"，要塞进非租约设备 | 准确：网内设备，与谁分配 IP 无关 |
| 完整性 | 静态 IP、IPv6、租约过期仍在线、多 MAC 设备都会漏 | 能把邻居表、租约、station dump 合并补齐 |
| AP 角色 | 天然为空，看起来像"没设备" | 邻居表照样看得到全网二层设备 |
| 跨节点 | 单机页表达不了"挂在哪个节点"，拼别的节点租约又与标题矛盾 | 先本机视角，以后加 1905 数据源不用换位置 |
| 动作入口 | 不适合放封禁/踢 | 现有封禁与踢本来就按 MAC，行上点更自然 |
| 代价 | 要接管/改上游 `luci-mod-network` 的租约页 | 新页 + rpcd 方法 + ACL + i18n + 测试，不碰上游 |

另一个约束是数据：控制器只有每 BSS 的终端**数**（A26），没有终端 MAC 列表，所以任何跨节点设备明细都得先补
数据通道（登记为 A28 / PLAN 30 / H-21）。

## 型号那一行改成"组网实际广播的型号"（B20）

现象：页面状态区 `Model` 显示 `router`，而主控页面上同一台设备的型号来自 1905 的 ModelName，两边对不上。

原因不是页面兜底写错，而是 **C 侧根本读不到**：`controller_self_identity()` 在沙箱里读 `/tmp/sysinfo/model`，
沙箱有自己的 `/tmp`，宿主那份看不见，于是退回 `"router"`（宿主上 `cat /tmp/sysinfo/model` 是
`Xiaomi AX3600 (stock layout)`）。

改法：型号优先取 `ZTE_MESH_REAL_MODEL`——init 给三个角色都设了它（值就是守护进程这次组网**实际广播**的
identity，也是主控页面上看到的那个字符串），取不到才退回 `/tmp/sysinfo/model`；两者都没有就留空，页面显示 `-`。
子路由行缺型号时同样不再填 `router`（缺名称那一条不变，仍是 `router`）。

验证：改的是 ARM32 侧，`tools/lab/build.sh database` 在 `ubuntu` 上重编 `out/db-engine-probe`
（211 696 B，HEAD 包里那份是 211 708 B，差 12 B），`openwrt/repack-runtime.py --replace` 只换这一个成员、
`tests/test_runtime.py` 0 failure；把新 probe 拷到 `ax3600` 的 `/usr/lib/zte-mesh/root/bin/` 并重启服务
（旧件备份在 `/tmp/zte-r26-backup/db-engine-probe`）。`ubus call luci.zte-mesh status` 的
`state.self.model` 变成 `ZXSLC SR1010`；浏览器强刷后状态区型号是 `ZXSLC SR1010`，所有表格里再没有 `router`。

顺带说明：这次重编只是为了让 `ax3600` 现在能看到正确读数；r26 的 apk 仍要等构建机或 CI，那时包里带的
probe 已经是这次重打包的那一份（`zte-mesh-runtime.tar.gz` 已随仓库更新）。

## 非中兴身份在两种模式下的组网（2026-11-09）

把子节点 `ax3600` 的广播身份换掉，两种模式各看一次。仍然一次只改一端、只重启一端；主控 `owrt` 的型号一直是
`ZXSLC SR1010`。

| 子节点身份 | `mesh.v2=0`（兼容） | `mesh.v2=1`（非兼容/严格） |
|---|---|---|
| 型号名 `Xiaomi AX3600`，厂商 `ZTE` | 入网，`model "Xiaomi AX3600"`、`zte:true` | 入网，同上 |
| 型号名 `Xiaomi AX3600`，厂商 `Xiaomi` | 入网，`zte:false` | 入网，`zte:false` |

- 做法：只 `sed` init 第 1004 行的 `ZTE_MESH_REAL_MANUFACTURER` / `ZTE_MESH_REAL_MODEL`，再
  `/etc/init.d/zte-mesh restart`；模式用 `uci set zte_mesh.main.mesh_compatible`（`0` ⇒ `mesh.v2=1`）。
  每步等 40 到 60 秒，读主控 `state.json` 的节点行。四格里 `online` 都是 `true`、`hops=1`，`metrics_age`
  一直在动。

  原因是本仓库 `P1905ComCfg.Policy` 默认 0 = **只记录不拒绝**（[CONTROLLER_CAPABILITIES](../research/CONTROLLER_CAPABILITIES.md)），
  `Enable=1` 只记原因码；真实 SR 固件的 `Policy` 取值可能不同，这套读数不能推论 ZXHN Z506 的拒绝行为。
- `zte:false` 的实际后果：控制器给它发厂商动作（LED、重启）时会跳过（`controller-service.c` 按
  `nodes[k].zte` 过滤），拓扑与终端统计照常。
- 还原：子节点 identity 改回 `ZTE` / `ZXSLC SR1010` 并重启子节点；两端 `mesh_compatible='1'`（`mesh.v2=0`）。

## 型号按本机无线规格自动选（2026-11-09）
