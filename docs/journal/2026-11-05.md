## 批 18 · 终端数的替身：问、答、采集三段各补一段

第 17 批收尾时 PLAN 第 3 节写着"主机侧没有可做的了，剩下的都卡在上机窗口"。**这句被用户一条追问推翻了**：
组合 ②③ 的「终端数」那一格是空的，而它空着的原因不是"要上机才知道"，是**沙箱里那个原厂 agent 压根没有可答的数据源**——
原厂这一格数字来自无线驱动经 `cspd`，沙箱两样都没有，`ns-run` 建的私有根连 `/sys` 都不挂。
把缺的三段补上（宿主量数、沙箱应答、主控定时问）全是主机可测的，于是有了这一批。

### 先把前提测出来，再决定替身坐在哪

`tools/lab/enroller.c` 加了一个 `--metric`：按原厂 `I5TlvApMetricsQueryInsert` 的写法组一帧 AP Metric Query
（CMDU `0x800b`，TLV `0x93` = 计数 + BSSID 列表），发进沙箱，把回帧的 `0x94` 逐条打出来。读数很干脆——
**agent 收到查询，一声不响**。这一条决定了替身必须自己把答的那一半做出来，不是去修 daemon。
`--metric` 的注释里另留了两条依据：`0x93` 的字段形状（计数 + BSSID 列表）对着 MultiAP 规范 3.6 的 dissector 核过，
以及"查询点名一个这台 agent 不认识的 BSSID 时，原厂回 Error Code 而不是沉默"（`ApMetricsQueryReceive` →
`slave_find_bss` 那条路径的符号名）。**两条都还是推的，没在设备上读过**——正是 H-15 第⑦ 那半要读的，
别在这里写成已验。

三段各自的位置由"数在哪里"决定：

- **采集（A）在宿主**：`openwrt/zte-mesh/files/sta-collect`，procd 实例，5 秒一轮，写 `/run/zte-mesh/ap-sta`
  （一行 `epoch=`，之后每路一行 `BSSID 数`）。三个坑是它的判据：①**AP 名单只取 netifd 里 `mode=ap` 的接口**——
  子节点那条朝主控建的回程 sta 接口自己也有 `stations` 目录，把它数进去就等于"这台子路由有一个终端，就是主控"；
  ②**计数走 debugfs**（`/sys/kernel/debug/ieee80211/phy*/netdev:<if>/stations`），因为 ax3600 那种出厂镜像上
  `iw`、`hostapd_cli`、`wpa_cli` 一个都没有，目录列举不需要包也不需要守护进程在说话；
  ③**整表先写到临时名再 `mv`**——应答的那一侧正在读它，半份文件就是一份半网络。
  `stations` 目录**不存在**时这一路整个不进表：内核没话说≠"0 个终端"，一行 0 会被当成量过的数报回主控。
- **应答（B）在沙箱内**：`src/agent-ap-metrics.c`，编进 `libzte_controller_trace.so`，挂在收帧钩子上。
  空列表＝本机跑的每一路；点名的只回点名的那几路；表超过 30 秒没刷新、或 `epoch` 落在未来 ⇒ **回 0 字节＝不吭声**。
  30 秒是六个采集周期，也是主控给一个 `.sta` 文件的有效期——同一个数在链路上只该有一个新鲜度定义。
  发送用的是**查询到达的那个 socket**，而且绕开 `controller-trace.c` 自己的 `sendto` 包装直接 `dlsym(RTLD_NEXT)`：
  走包装等于替 daemon 伪记一次它没做过的收发，日志会说谎。
- **问（C）在主控**：`ap_metrics_query_build()` 组空列表查询，`controller_ap_metrics_query()` 从 `veth-lab`
  （daemon 真正在用的那个口）发出，源地址取 `br0` 的 AL MAC，**发出即不读应答**——应答按那个 MAC 回到 daemon
  自己的 socket，`controller-trace.c` 照常交给 `controller-peer.c` 落盘。**这是这一批最值得留着的一个形状**：
  原厂子节点（真驱动）与 OpenWrt 子节点（这张表）在主控这一侧是同一条写入路径，主控不需要分两条路读，
  也没有为替身新增第二种状态。服务侧 `ap_metrics_reconcile()` 从拓扑就绪等 15 秒起、每 10 秒问**一个**节点
  （一次调用最多发一条，写 `state.json` 的那一秒循环不能被它拖住），节点离开拓扑就停问，文件自己过期——
  这是"这台的终端数还没人上报"和"这台不在了"的分别。

被否掉的一条：主控替子节点猜数。缺的那一路**不补 0**、整表过期**不答**，宁可为空。

## 批 19 · 给采集一条自己的开关，把"停"做成一个变量

### 先试了 procd 那两把杠杆，读回来的不是"采集停了"

⑥ 要的是"这台没人上报终端数"这一个变量。`ax3600` 上停掉 `sta-collect` 只有 procd 那一条路，实测：
`ubus call service delete '{"name":"zte-mesh","instance":"sta-collect"}'` 停得掉，主控约 45 秒后 `state.json` 里这个节点
`stations` 从 `0` 退回 `-1`、`bss_detail` 零行，**而节点行还在**（人没走，只是不报了）。坏消息在后半：恢复只能
`/etc/init.d/zte-mesh start`，那一下把守护进程也换了 pid（16814 → 22636），子节点从拓扑里掉出去十几秒——
**读回来的是"重启了一次"，不是"采集停了"**。所以这一批先把入口做出来，读数留到 r21 装机再读一次。

### 开关跟着 `trace-all` / `mm-off` / `db-profile` 那一套做

`touch /run/zte-mesh/collect-pause`：脚本不再重写表，**表留着、`epoch=` 不再盖章**，30 秒后应答自己就不回了——
沉默跟原厂 agent 一样，报一个陈旧的数才是编一个测量。`rm -f` 那个文件，下一次 5 秒的循环恢复盖章。
暂停期间退出码仍是 0（不给 procd 造 respawn 循环），`paused` 那道闸让"停了"这句话每个进程只说一次。
路径从表的目录推出来（`PAUSE=$DIR/collect-pause`），所以测试把表写到临时根就自带一份开关文件，不用另设环境变量。
这个文件没有任何页面、UCI 选项或 apk 能设，到不了用户的机器。

### 装机读回：把"采集没跑"和"应答没到"分成两行

`ap_sta_rows=` / `ap_sta_age=` 直接读那张表（表不在就两行 `absent`，`epoch=` 那行没了则 `ap_sta_age=unreadable`），
`peer_files()` 从一次采样改成连读：`peer_reads=` 说这次读了几份快照，`peer_input=` 是 H-13/H-15 真正在问的那件事
——**`.sta` 文件存在，或摘要里有 `stations=`**，两条来源任一成立都算有输入。`peer_reports_stations` 保持原来那个更窄的意思
（结束采样那一份快照），因为装替身的机器可以 `peers_sta=2` 旁边写着 `no`，那是设计不是故障。
包里 shell 文件的 marker 加到第五个：`collect_pause_in_collector`——老脚本装到机器上会老实报 `no`。

## 批 20 · 启动器不挑机器：一个 apk 带三份构建，入口脚本按 `uname -m` 选

起因是用户的一条追问——"现在 CI 生成的 zte-mesh-launcher 可以在 x86 上面安装吗"。答案是不能，而且比不能更糟：
launcher 那条 `DEPENDS:=@(TARGET_zte||TARGET_qualcommax)` 是 **apk 依赖**，求解全有或全无，一台 x86_64 机器上
`apk add zte-mesh zte-mesh-launcher luci-app-zte-mesh` 会被 launcher 一个人整串带走。目标定成"外部用户一个包什么机器都能装"，
带哪几档选了 aarch64 + armv7 + x86_64。

### 一个 apk 只有一份机器码，那就放几份 ELF、让一个不是 ELF 的东西去选

`package-pack.mk` 的 `Architecture:` 读 Makefile 级全局 `PKGARCH`，一个 Makefile 给不了两个架构，一个 ELF 也只带一个架构。
于是 launcher 变 `PKGARCH:=all`，机器码放进 `/usr/libexec/zte-mesh/arch/<cpu>/{ns-run,mesh-search}`，
而 `{ns-run,mesh-search}` 这两个名字改由 `openwrt/zte-mesh-launcher/files/launcher-dispatch` 这一个 shell 脚本顶着——
同一个文件装成两个名字，`$0` 的最后一截决定跑哪个程序，`uname -m` 决定进哪个目录。末尾必须 `exec`：
procd 盯的是实例自己的 pid，`attach` 的 `sandbox_pid()` 还在 `/proc/*/cmdline` 里 grep 守护进程，
脚本坐在二进制前面这两头都不成立。CPU→目录那张映射只在 dispatcher 里写一份（`aarch64|arm64→aarch64`、`armv7*→armv7`、`x86_64`），
认不出的名字原样拿它当目录名——这样"这台没带"那句报的是内核自己说的那串，不是替它编一个。
init 和装机读回都不抄第二份映射，问的就是装机真要跑的这份代码。

### 搬走的不是架构标签，是装机时那句拒绝，所以那句得说清带的是哪几档

arch:all 定义上什么机器都收，以前那句"这台不行"发生在 `apk add`，现在只能发生在运行时。两个入口：
`zte-mesh.init` 把实例交给 procd 之前先问一次 `--launcher-check`（不答就不交，否则 `respawn 3600 5 0` 每 5 秒重开一个 127，
把日志刷满——那是 LAB 里描述缺模拟器那种死法），`verify-install.sh` 问同一个问题。契约是
**`--launcher-check` 答的第一行必须跟人直接跑程序看到的那一句一模一样**：init 记的就是这一行，读回打印它的 `head -n 1` 当证据，
为检查另写一句短的等于让机器读一份假话。这条契约先在装机读回那套里跑红——`launcher_arch=` 收到的是只说"跑不起来"的那句短的，
`carries:` 那串架构名被盖掉了，读的人只知道"不行"，不知道这个 apk 到底带哪几档。
现在两支各说各的话：`arch/<cpu>/ns-run` 不在 = 这台没编，把包里的名单列出来；在但 `[ -x ]` 不成立 = 文件在盘上跑不起来，
只说这一件（那种情况下再报架构名单只会把人指向另一个 CPU）。两种都答 127，检查也就都算失败。

### 三份构建从哪来，少一份怎么变红

`tools/build/launcher-arches.sh` 用 `$(TARGET_CC) -dumpmachine` 认工具链属于哪一档——不读 `ARCH_PACKAGES` 这类内部变量，
目录名必须跟产出它的编译器一致；一个候选编译器不行就试下一个（Debian 的交叉 gcc 有时先搜宿主的 `/usr/include`，sysroot 要逐个试），
armv7 先硬浮点、软浮点兜底。`-static` 写死在脚本的 `FLAGS` 里而不是靠调用方传，因为 `ldd` 判不出。
`ZTE_MESH_ARCHES` 决定这个包带哪几档，`ZTE_MESH_REQUIRE_ARCHES` 让"CI 要三档而只出一档"从绿日志里的一行变成红，
`ZTE_MESH_CC_<档>` 是人工指编译器的口子。CI 那一步因此装两个交叉编译器，构建完**用 SDK 自己编出来的 apk-tools 解出成员**断言两个入口脚本与三个架构目录都在——
产物是判据，日志不是。feed 的两种接法差别记进 DEVELOPMENT 第 8 节：CI 用 `src-link`，`$(CURDIR)/../../tools/build/launcher-arches.sh`
指得回仓库；`src-git` 会把包**复制**进 `package/feeds/…`，那里没有 `tools/`，所以读不到脚本时明说并给 `ZTE_MESH_LAUNCHER_BUILD` 这条路。

### B：模拟器可以指宿主上的绝对路径，包里照旧不带 qemu

`zte_mesh.main.emulator` 现在除私有根里的相对路径外也认**宿主上的绝对路径**。原因是 `ns-run` 在 chroot **之后**才 exec 模拟器，
`/run/zte-mesh` 又挂成 `noexec`——"这路径在宿主上看得见"不等于"沙箱跑得动"。init 先比 sha256（每次重启重拷一份 11 MB 没有意义），
不同才 `cp -f` 进私有根的 `usr/bin/<basename>`、`chmod 755`，然后把根内的相对路径交给 ns-run；拷不进去就不起服务并说清为什么。
**不随包分发 qemu** 是有意的取舍（体积与许可），手工放仍是唯一路径，B2 不实现。

### 文档扫出一处真错的代码：`tools/lab/build-launcher.sh`

它还在往 `/usr/libexec/zte-mesh/{ns-run,mesh-search}` 这两个名字放 ELF——而这两个名字现在是入口脚本的。手工放过一次的机器上，
`--launcher-check` 一起就被盖掉了：真的 `ns-run` 收到两个参数只会打 usage 并返回 64（`src/ns-run.c:267-273`），
init 于是记一句"这台没带启动器"——一个假诊断。改成先问 `uname -m`、二进制放进 `arch/<cpu>/`，并加一条自检：
`$LIBEXEC/ns-run --launcher-check` 的第一行必须正好等于那个新路径。同一个坑写进 LAB 第 7 节（换二进制换 `arch/<cpu>/` 下面那份，
别覆盖入口名字）。

## 批 21 · 两个包合成一个：`zte-mesh-launcher` 并进 `zte-mesh`

起因还是用户的一条追问，连着三句："现在 apk 在不同架构都可以直装了吗"→"还有必要分 launcher 吗"→**"合并两个包"**。
第一句的答案是"是"，而且是批 20 那天在两台测试环境上读回来的（x86_64 与 aarch64 各一档，含把 `arch/x86_64` 改名那一次反面）；
第二句把剩下的东西问出来了：拆成两个包**唯一**的理由是 `package-pack.mk` 一条 Makefile 只读一个 `PKGARCH` 写进 `Architecture:`——
数据包要 `all`、编机器码的那半要 `aarch64_cortex-a53`，一个 Makefile 给不了两个答案。批 20 把这半也变成 `all`（一个 apk 带三份构建，入口脚本按 `uname -m` 选目录），
那条规则就管不到任何人了，分家剩下的全是坏处。最贵的一条上面刚读到：**两个包是两次事务**，
`05:54:30` 升 `zte-mesh`、`05:54:34` 才装 launcher，中间那次重启问到的入口是这台手工放着的旧 ELF，
于是日志记了一句假的"这台没带构建"。init 改成只认 127 是把那句假话说小，合并是让它没有发生的窗口——两件事动的是同一段代码，所以并成一批（原 #90）。

### 合并在 Makefile 里是什么：一次解包喂两半

`Build/Prepare` 解 `zte-mesh-runtime.tar.gz` 到 `root/`，那三个 launcher 源文件（`ns-run.c`、`controller-net.c`、`enroller.c`）本来就在这个 tarball 里，
所以**同一个解包同时交出运行环境与要编的码**——这正是 C5 那条老坑（陈旧 `ns-run` 混在 tarball 里烧掉一整天）的反面：这个包编的就是它自己装出去的那份。
`Build/Compile` 调 `tools/build/launcher-arches.sh` 出三档，`Package/zte-mesh/install` 把 `launcher-dispatch` 装成 `ns-run`、再复制一份叫 `mesh-search`，
连带 `arch/<cpu>/`、`attach`/`wlan-sync`/`sta-collect`、init 与配置文件全摆进同一个 `root/`。两处细节记进 DEVELOPMENT 第 8 节：
数据包**也得有 `Build/Compile`**（省了它，OpenWrt 会在那个只有 tarball 的构建目录里跑 `$(MAKE)`，报"No targets specified and no makefile found"），
而 `$(CURDIR)/../../tools/build/launcher-arches.sh` 这种指回仓库的写法只在 `src-link` 下成立——`src-git` 把包**复制**进 feed 树，那里没有 `tools/`，
所以读不到脚本时明说，并留 `ZTE_MESH_LAUNCHER_BUILD` 这个口子。

### init 那句假诊断：退出码分类，架构只有 127 一个答案

```sh
launcher_status=0
launcher=$("$NSRUN" --launcher-check 2>&1) || launcher_status=$?
if [ "$launcher_status" = 127 ]; then
	log "zte-mesh has no launcher build for $(uname -m): $launcher"
	return 1
fi
[ "$launcher_status" = 0 ] || {
	log "$NSRUN --launcher-check exited $launcher_status: $launcher"
	return 1
}
```

以前是 `|| { log "…has no build for…"; }`，任何非零都写成同一句。而入口脚本自己把两种死法分开得很清楚（都是 127：这一档没带 / 文件在但跑不起来），
**旧 ELF 答的是 64**——`src/ns-run.c` 收到不认识的两个参数打 usage 就走。所以现在 127 才配得上"这台不在包里"，
其余非零报退出码本身，不冒充架构判决；两条都在 `test_init.sh` 里各有一句断言。`zte-mesh-launcher` 这个名字也从 init 里消失了（有一条新用例专门 grep 它不在）。

### H-17：两个包抢同一批文件，apk 怎么答

两台当时都还装着合并前的 `zte-mesh-launcher`（r21 + r2），这正是叠加态；读之前谁也不知道答案，因为那是求解器的行为。
**`ax3600` 走的是后来写进 INSTALL 的那个顺序**：先 `apk del zte-mesh-launcher`（`rc=0`，`OK: 41.8 MiB in 224 packages`），
再 `apk add` 合并包（`Upgrading zte-mesh (0.1.0-r21 -> 0.1.0-r22)`，`rc=0`），一次到位，`RESULT=PASS` **19 查 0 败**，
同一趟 `air_matched_plan=yes` + `applier_writes=0`——升级没动本机广播的名字。
**`owrt` 先走了另一头**，而另一头不是"报个冲突就停住"，是一串不好收拾的状态：

```
ERROR: zte-mesh-0.1.0-r22: trying to overwrite usr/libexec/zte-mesh/ns-run owned by zte-mesh-launcher-0.1.0-r2.
（八行：两个入口名字 × 三档架构）
rc=1
```

`rc=1` 这一趟却把 `zte-mesh` 记成 `[installed]`、跑了 `post-upgrade`、也把新装的那批脚本写进去了；`apk info -L zte-mesh` 只列 **4** 个
`libexec` 成员（`attach` / `sta-collect` / `wlan-sync` / rpcd 那一支），入口两个名字和六份二进制仍归 launcher。
这台当场还能跑，因为包里那份入口与 launcher 那份是同一段脚本——**"能跑"和"装干净"在这一步不是一回事**。
接着按最直觉的两条恢复动作试，两条都不成立：

- `apk del zte-mesh-launcher` 把两个入口名字一起带走（`ls /usr/libexec/zte-mesh/` 只剩 `arch` `attach` `sta-collect` `wlan-sync`，
  `ns-run --launcher-check` 回 **127**，那是 ash 的 `not found`）；
- "再 `apk add` 一次这个包"是**空操作**——包已经"装着"了，`--force-overwrite` 也一样；`apk del zte-mesh` 单发被依赖挡住
  （`not removed due to: zte-mesh: luci-app-zte-mesh / luci-i18n-zte-mesh-zh-cn`）。

**`owrt` 最后是三个包一起 `apk del`（`OK: 205.6 MiB in 270 packages`，`rc=0`）再一起 `apk add`** 才回到干净态：12 个 `libexec` 成员、
`attached=true`、`RESULT=PASS` **18 查 0 败**。这条链写在 [INSTALL](../INSTALL.md) 第 2 节，判据全文在 [PLAN](../PLAN.md) H-17。

**读出来一处要改的代码**（下一批）：入口文件被 launcher 带走后 `"$NSRUN"` 回的 127，和"这台的 `uname -m` 在包里找不到那一档"是同一个码，
而批 21 刚把预检改成"127 ⇒ 那句架构拒绝"。于是这台机器上的日志会写 `zte-mesh has no launcher build for x86_64`，
真相是包只剩一半。修法是问之前先 `[ -x "$NSRUN" ]`，不在就说"入口脚本不在"，`test_init.sh` 为这两个 127 各断言自己那句。

### 顺手把 H-15 ⑥ 欠的那三个带秒的数抄齐了

批 19 那一轮判不了"主控退回 `-`"，缺的就是带秒的三个数（`.sta` 的秒级时间、`state.json` 的 `"metrics_age"`、`bss_detail` 每条的 `"age"`），
这次照 `touch` → 等 100 秒 → 抄 → `rm -f` 做了一遍，`ax3600` 摆闸、`owrt` 当主控。摆闸那一刻两台的 `date +%s` 都是 `1793872925`（先把"是不是时钟差"排掉），
暂停前主控是 `"stations":0` / `"metrics_age":6`；**100 秒后**（`18:03:45`，`date +%s=1793873025`）读到 `"stations":-1` / `"metrics_age":30` / `"bss_detail":[]`，
而同一时刻两个 `peers/*.sta` 还在原地（mtime 停在 `18:02`、内容仍是 `0`）、主控自己的 `ap_metric_query … status=0 epoch=` 每 10 秒照旧递增、节点行还在拓扑里。
**"过期即沉默，不是报 0"到这一刻才真的有秒级证据**：那枚 `-1` 来自 30 秒新鲜窗（`src/controller-service.c:954`），窗关了不等于"这台不在了"。
`rm -f` 之后 `18:04:09` 子节点重新盖章（`ap-sta` 的 `epoch=1793873049`、日志 `collecting 2 access point(s)`），44 秒后主控回到 `"stations":0` / `"metrics_age":3` / 两行 `"age":3`。
