## 二次修复：CONFIG_EXTERNAL_KERNEL_TREE 无效，改走 dl/ 预置内核包
- 第一次修法（clone 外部树 + 写 CONFIG_EXTERNAL_KERNEL_TREE）经 CI 实测无效：
  该符号不在 Config-kernel.in / Config-build.in / target/Config.in，`make defconfig` 直接丢弃
- 决定性证据（include/download.mk）：
  - `$(DL_DIR)/$(FILE):` 规则无前置依赖 → 文件存在即跳过 recipe，完全不下载、不校验
  - `check_download_integrity` 在 hash 不匹配时会加 `FORCE` 强制重跑 → 必须写真实 SHA256
- 最终方案（走上游标准路径，不依赖外部树分支）：
  1. `git clone --depth 1 -b codex/sr1010-mainline cnjn/linux-mainline-zte-zxslc-sr1010 → linux-6.18.38`
     （父仓库 build 分支只是把同 URL 的该分支当 submodule 钉住，直接浅克隆分支更省）
  2. `tar --exclude=.git -cf - linux-6.18.38 | xz -T0 -3 > openwrt/dl/linux-6.18.38.tar.xz`
     （顶层目录名必须与 LINUX_VERSION 一致；TAR_OPTIONS 是 `-xf -`，无 strip-components）
  3. `sed -i` 把 target/linux/generic/kernel-6.18 里 `LINUX_KERNEL_HASH-6.18.38 = x` 换成真实 SHA256
  4. rm -rf 内核目录回收磁盘；timeout 90→180 分钟，-j1 改 -j$(nproc)

## CI 加速：缓存交叉工具链
- 痛点：tools/install + toolchain/install（binutils→gcc/initial→musl→gcc/final）每次 30-45 分钟
- 方案：actions/cache 缓存 dl/feeds/staging_dir/build_dir
  - key = owrt-<immortalwrt commit>-<kernel commit>，只含上游版本
    → 改我们自己的包/文档/workflow 不击穿缓存（这是关键设计）
  - restore-keys 两级回退 owrt-<owrt>- / owrt- ，上游 bump 时可增量复用
  - 缓存需同时包含 staging_dir 的 install stamp 与 build_dir 的 .built stamp，
    只缓存 staging_dir 的话 make 仍会重建
  - build_dir 整体缓存（不列子目录），避免部分恢复；压缩后约 2GB，在 10GB 仓库额度内
- 内核 tarball 改为幂等：存在则复用，并从落盘字节重算 SHA256 再写回
  target/linux/generic/kernel-6.18 —— 否则缓存里的旧包和哈希对不上会触发 FORCE 下载
- 加 concurrency: cancel-in-progress，避免重复 push 时两次全量构建并行
- tools/toolchain 两步前加 time，日志里能看出缓存是否生效
- 预期：首次仍 40-50 分钟，之后 8-12 分钟
- 未采用的更大杠杆（备选）：预编译 SDK 作为 release 资产；self-hosted runner

## apk 装到真机：修 LuCI TypeError + 控制器起不来的两层原因
设备：192.168.1.1，ImmortalWrt 25.12.2 r38135，qualcommax/ipq807x，kernel 6.12.103（非中兴硬件）

### 1) TypeError: cfg.get is not a function（已修，commit 15f0632）
- 根因：`uci.load()` 的 resolve 值是"本次成功加载的包名数组 string[]"，
  不是配置游标；render() 里 `var cfg=data[2]; cfg.get(...)` 必然抛错，整页白屏
- 修法：`var role = uci.get('zte_mesh','main','mesh_role') || 'master';`
  （同文件 renderStatus 读 mesh_v2 本来就是 uci.get，写法统一）
- 实机验证：设备上 /www/luci-static/resources/view/network/zte-mesh.js 是
  **构建期压缩过的单行文件**（22435→22416 字节），按子串替换后 md5 精确一致，
  curl 取回确认已生效，node --check 通过
- 备份：/root/zte-mesh.js.bak.20261030-225902
- 工具坑：dropbear 无 sftp 子系统（paramiko open_sftp 报 EOF during negotiation）；
  设备上没有 base64/openssl/busybox base64/od；heredoc 分块会每块多一个换行导致
  md5 不符 —— 最终用 `printf '%s'` + 单引号转义分块（19×1200 字符）写入，字节完全一致
- PKG_RELEASE 1→2；顺带 gitignore 掉 /dist/

### 2) 控制器 running=false exit_code=80（未解决，硬件/内核限制）
- 页面显示"Starting or stalled"的数据来源：rpcd 读 /run/zte-mesh/state.json，
  文件不存在 → state=null、age=-1
- 第一层：`ZTE_DB_SANDBOX error=private-service-network errno=2`
  → controller-net.c 的 create_private_wire() 先 `stat("/sys/module/veth")`；
  该机 veth 完全不存在（`ip link add type veth` = Not supported，lsmod 无 veth）
  → 已 `apk add kmod-veth`(6.12.103-r1)，模块加载，veth 可建
- 第二层（当前卡点）：`error=execv errno=8`（ENOEXEC）
  → 运行时是 **32 位 ARM**（ELF class=1，e_machine=0x28，ld-linux.so.3），
  而这台 aarch64 固件内核没开 CONFIG_COMPAT（ash 把 32 位 ELF 当脚本报 syntax error 即证据）
  → cnjn fork 的 config-6.18 里有 CONFIG_COMPAT=y，所以原厂/该 fork 固件上没问题
- 结论：非中兴 + 无 32 位兼容的固件上，vendor multiapd 根本跑不起来，
  与之前"非中兴硬件 <10%"的判断一致。要跑需换开 CONFIG_COMPAT 的固件，
  或给 ns-run 加 qemu-user 路径（ns-run 目前把 qemu 只用于 x86_64 lab）
- 另注：CI 为了绕开 vendor 内核编译，把 +kmod-veth 从 DEPENDS 裁掉了；
  其他固件上装完必须自己补 kmod-veth，这一点值得在包里重新加回（对非 ZTE target）

## 01:40 两台设备真的组网了：AL MAC 撞号是唯一堵点（已修，main c9b888f）

### 结论
`controller-net.c` 给 br0/veth-lab 的 AL MAC 默认末字节写死 06，service 形态没人覆盖，
于是**两台设备都是 02:00:00:00:19:06**。1905 栈丢弃"源 AL MAC 等于自己"的帧，两端的
Search/Discovery 都被对端当成自己的回声 → `rx1905=0`、topology 只有自己。
修法：`start_service()` 取 LAN 网桥 MAC 末字节作 `ZTE_MESH_AL_LAST`（可被
`zte_mesh.main.al_last` 覆盖）。修完 VM=…:03、路由器=…:e3，控制器 `nodes` 立刻出现子节点
（zte=true online=true light=0），稳态 0x0004 私有心跳 + 0x0002/0x0006 拓扑/链路度量。

### 工具
`tools/lab/spark.c`（zig cc 交叉编译 x86_64/aarch64 静态）——发 Topology Discovery、
打印收到的每个 0x893a 帧的 MAC/CMDU。**关键教训**：网桥端口的 ingress 帧不会投给绑在该
端口上的 AF_PACKET 套接字，抓"线上进来的"要用 `tcpdump -i 物理口`，抓"daemon 发了什么"
要用 `br-lan`。这也是之前一堆"没收到"误判的来源。

### 另一个坑
`ZTE_MESH_EMULATED_LAB=1` / `ZTE_MESH_QEMU=/qemu-arm-static` 之前是手工加在两台设备的
init 里的，仓库没有；我用仓库版覆盖 init 后服务立刻 `execv errno=8`。现在 init 自动探测
（uname -m + /proc/config.gz 的 CONFIG_COMPAT + 私有根里有 qemu-arm-static），
`zte_mesh.main.emulator=none` 可强制原生。注意 qemu 必须在**私有根内**（chroot 后 exec），
值要写成 `/qemu-arm-static` 这种沙箱内路径。

## 06:10 枚举跑通了：M1 是被动的、M2 落到子路由的库（lab-tools 644f0b5）

### 上一节的"卡点"其实是测量假象
`bind(AF_PACKET, ..., htons(0x893a))` 在 bridge 的 rx_handler **之后**投递，`ETH_P_ALL` 在其**之前**
→ 绑在网桥端口上按 ethertype 绑的套接字看不见 ingress 单播，`tcpdump` 看得见。`tools/lab/enroller.c`
改用 `ETH_P_ALL` 收帧并自己过滤后，M1 一直在发：`tx1905 cmdu=9 bytes=771/801`。

### M1 是被动的（`tools/lab/elfx.py` 静态确认）
`_acdcSearchHandler`(event 2) 与 `_acdcConfigHandler`(收到 0x0008, event 8) 才调
`_acdcSendApAutoConfigWSCM1`；控制器侧 `acdsTimerMsg` 的 Search 被 `[basic+0x114+radio*12]` 门控，
只有 cspd 置位。沙箱没 cspd → 两边都在等对方。enroller 补上缺的那一步（回 35 B 的 0x0008），
于是完整三帧往返：M1 771/801 → M2 911（0x11 len=656 内含 0x1022=5）→ agent 回 218。

### 三个真 bug（都在本次提交里）
1. 运行包没打包 `libzte_agent_mm.so`（Makefile 里写了、tar.gz 里没有）→ 每次 enroll 都在
   `acdcConfigM2EncryptedSettings` 第一行 -3 中断。补 CI step + `openwrt/repack-runtime.py` 重打
   （逐成员字节不变，38 条 sha256 全过），之后 `row_applied=1`，`wlan-plan` 的 ssid 变成控制器的。
2. `wlan-sync` 的 `stamp()` 用 `stat -c`，ax3600 镜像**没有 stat** → stamp 恒为 missing，循环只在
   启动那一次应用 plan，M2 之后的 plan 永远没人应用。改成 md5sum/stat/ls 三级回退。
3. `radio_section_of 5g` 取第一个 band=5g 的设备，ax3600 有**两个**（PCIe 空卡 radio0 + SoC radio1）
   → 控制器的 SSID 写进空卡，`default_radio1` 还是 ImmortalWrt。现在 pin(`zte_mesh.main.wifi_5g`)
   > 单设备 > 唯一未停用；两可时不猜、日志点名。设备上验证：`radio 1 (5g, radio1.default_radio1)`，
   `bands=5g`，`default_radio1.ssid=ZTEMESHCTRL`。
