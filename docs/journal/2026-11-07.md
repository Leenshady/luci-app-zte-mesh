## 建 PR 这件事为什么绕了一圈：`github` MCP 的写工具坏了

`mcp__github__create_pull_request` **成功和失败都回同一条错误**：


## review 的三个 P1：越界写入、生产报文出口、apk 丢依赖

项目 review 报了 11 项（3 个 P1、8 个 P2），这一轮只修 P1，三项都配了回归判据。P2 未动。

**① `wlan-sync` 的状态写入跟着沙箱放的符号链接走。** `/run/zte-mesh` 是沙箱唯一可写的宿主路径，而沙箱与宿主同一个 UID（`ns-run` 只要求这个目录 root 所有、`mode & 022` 为 0，owner 是 root 就写得进去），所以它能在里面预先放一个 `wlan-sync.status.tmp` 符号链接；原来那句 `> "$STATUS.tmp"` 会跟着链接把宿主 root 的写入引到交换目录外面。改成把临时文件建在**宿主父目录**（`mktemp "$(dirname "$STATUS")/../.wlan-sync.XXXXXX"`、`umask 077`），再 `mv -fT` 覆盖目标：chroot 只 bind 挂共享目录本身（`src/ns-run.c:141`），父目录沙箱够不着，竞态从根上没有了——只把固定名字换成随机名字不够，同 UID 仍能在 `mktemp` 与 `printf` 之间抢换。`-T` 不能省：目标是指向目录的符号链接时普通 `mv` 会把文件搬进那个目录。两个新依赖都查过上游：busybox 1.36 的 `mv` 有 `-T`（`OPT_DESTNOTDIR`），`mktemp` 的位置参数 TEMPLATE 不受 FEATURE 开关限制，OpenWrt 的 `BUSYBOX_DEFAULT_MKTEMP` 是 `default y`。

**② 封禁/踢终端的报文从测试出口发，而且不等发送结果。** `controller_client_action()` 原来走 `lab-peer`——生产沙箱里那个接口已经被移回宿主 netns，daemon 只看得到 `veth-lab`——源地址还是写死的测试对端 MAC。改成与 `controller_radio_select()`、`controller_ap_metrics_query()` 同一条路：`veth-lab` 出口、`ioctl SIOCGIFHWADDR` 取 `br0` 的 AL MAC，`close` 前后保住 errno，并补上 kind 校验。服务那边原来 `(void)controller_client_action(...)` 把返回值丢掉，状态机在 tick 里就记 `sent`；现在 tick 只标 `pending`，服务逐个 agent 发完调 `actions_send_result()`，一个都没发出去或有任何一个失败就留在 `pending` 并 5 秒后重试（封禁不受踢终端那 3 次上限），发成功才记 `sent`（封禁下一跳改回 120 秒），撤销/到期的 `allow` 发成功才删行或记 `expired`。为此给 `action_entry` 加了 `releasing` 位，把"发 allow"与"规则已被删"分开——到期转 allow 时若重置重试计时器，configure 每秒进来一次就会把重试永远推后。

**③ 默认 CI 构建把三项运行依赖删干净了。** 这个 target 不编内核模块，workflow 为了把 kernel 包挡在构建图外，从 `DEPENDS` 里删掉 `ip-full`/`kmod-veth`/`kmod-sched-core`，但删完没补——装机主张写着依赖，发出去的 apk 里却没有，新板子装完缺 veth 就停在 `error=private-service-network errno=2`。读上游 25.12 的 `package-pack.mk`/`package-dumpinfo.mk`/`package-metadata.pl` 确认了正确机制：挪进 `EXTRA_DEPENDS`，`FormatDepends` 会把它并进 apk 的 depends，而 dumpinfo 与 metadata 都不读它，所以不进构建图；每项必须带版本约束（否则 `FormatDepends` 直接 error），故写 `(>=0)`。构建完再用 SDK 自己那份 `apk adbdump --format json` 读回 metadata 断言三项都在，少一项直接红。

**判据（全部在 WSL Ubuntu 的 Linux dash 上跑）**：`test_wlan_sync` **231/0**（新增那组先用一个真的会抢换共享临时文件的 `mktemp` 桩证明竞态存在，再读回受害文件未改、目标是普通文件、目录里没被搬进东西、临时文件已删、写/改名/分配三种失败各保住上一份状态并记日志）、`controller-packet-codec` **291 条**（桩掉 socket/ioctl/sendto/close，核对目的与源 MAC、CMDU 类型、帧长，五种失败路径查 errno 与 fd 闭合）、`controller-actions-test` **390 条**、`test_build_deps` **14/0**（把 workflow 那段 run 抽出来对四种开关组合各跑一遍真 sed，另加一条反证）、`test_rpcd` **24/0**、`test_verify_install` **278/0**、`test_init` **158/0**、`test_sta_collect` **32/0**。

**两个自己踩的坑记下来**：一是帧长断言先写了 `>= 60`，实际 builder 不补以太网 pad——kick 是 22+9+15+22+3=**71**、ban 是 22+9+19+3=**53**，ban 那条会红；改成按 kind 断言确切字节数。二是本机没有 C 编译器，WSL 也没有 cc/gcc/make，下载 zig 0.13.0 才编得动；第一次拿到的压缩包解出来没有 `zig.exe`，重下才发现取的是 **linux-x86_64** 那份——正好，`linux/if_packet.h` 与 `net/if.h` 本来就只有 Linux 有，在 WSL 里用 `zig cc` 编这两个 C 测试比在 Windows 上凑头文件对路。解包走 `python tarfile`（`filter='data'`）与 WSL 的 `tar`，不用 Git Bash 的 tar 解到工作区。

文档同步：`FEATURE_STATUS` A17（出口与发送回执）、B12（状态写入边界）、C12（apk 运行依赖断言），`DEVELOPMENT` 第 4 节测试清单与第 8 节 CI 那一行，`INSTALL` 第 1 节依赖那句。本轮**未触发 CI、未上机、未 commit、未推送**；上一轮 review 修复的 6 个文件改动原样保留。

## 顺着 ① 查同类：一处加固留下但改口，一处方案撤销

上面 ① 修完以后，我以为同一类（宿主 root 跟着沙箱放的符号链接写）还有两处，用户同意一起修。动手之后发现**其中一处的前提是错的**：方案已撤销、代码全部还原；另一处加固留下，但它的性质要改口。记下来是因为这个前提错得很隐蔽，主机测试还是绿的。

**判断"谁在宿主侧"的唯一依据是它在不在 chroot 里。** `controller_service()` 不是宿主进程：`zte-mesh.init:987` 起的是 `ns-run … /bin/db-engine-probe --controller-service`，`ns-run.c:161` 先 `chroot` 再 `execv`，`db-engine-probe.c:253` 才调 `controller_service()`。私有根在 `ns-run.c:111` 被 remount 成只读，唯一 bind 挂进来的宿主路径是 `/run/zte-mesh` 本身（`:141`，非递归 bind，子挂载不带进来）。所以 `controller-service.c`、`controller-run.c`、`agent-sync.c` 里的写入**都在沙箱内**，它们放的符号链接目标也在 chroot 内解析，越不到宿主根去。我上一轮把 `agent_sync_poll(WLAN_PLAN_PATH)` 标成"宿主侧"，是错的。

**② `src/agent-sync.c` 的 `plan_write`：`O_NOFOLLOW` 留下，性质改口。** 它挡的不是宿主越界（写方本来就在 chroot 里），而是同一个 chroot、同一个 UID 的原厂 daemon 预先放一个 `wlan-plan.tmp` 符号链接，把我们这次写入引到交换目录里的另一个文件（例如宿主写的 `config`）。注释按这个口径重写了。判据：`tests/agent-sync-codec.c` 原来只测纯函数，现在经 `agent_sync_poll()` 走到 `plan_write()`——那五个 vendor 桩让每一行都不可读，于是发布一份 `rows=0` 的空计划，写入路径照样跑到底，不需要给 static 函数开测试口子。新增两组：临时名字指向一个**已有文件**（断言拒绝、链接还在、受害文件字节未变、上一份计划未被覆盖），指向一个**还不存在的名字**（断言拒绝、那个名字没被 `O_CREAT` 造出来——没有 `O_NOFOLLOW` 时正是这条会把计划写到别处）。顺带核了正常路径：目标是普通文件、`0600`、临时文件已改名消失。**反证跑过**：把 `O_NOFOLLOW` 去掉重编，8 条断言红。

**③ rpcd 的 `actions/` 收件目录：方案撤销。** 原方案是"把整个收件目录搬出交换目录"（`/run/zte-mesh-actions`），我给用户的理由写的是"沙箱不读它，宿主服务自己 `opendir` 消费"。**这句是错的**：消费它的 `action_reconcile()` 就在 `controller_service()` 里，也就是在 chroot 里。搬出去之后 `/run/zte-mesh-actions` 在沙箱内解析成 `<私有根>/run/zte-mesh-actions`，只读挂载上 `mkdir` 得 EROFS、`opendir` 失败，宿主 rpcd 写的请求没人取，页面"重启／开灯／关灯"全部等满 8 秒返回 `null`。已还原 `src/controller-service.c`、`openwrt/zte-mesh/files/luci.zte-mesh`、`tests/test_rpcd.sh`、`tools/capture/mreplay.py`、`tools/dev/dev-service-smoke.py`、`docs/SERVICE.md` 六处，`test_rpcd` 回到 **24/0**。

**为什么主机测试没拦住**：`test_rpcd.sh` 的服务是个 shell 假替身，只验插件写没写、等不等得到应答，从来不跑真的消费者。我加的三条符号链接回归在"插件 + 假替身"这一层是绿的，反证也红（把 `ACTIONS` 改回子目录，受害目录里真被写进一个文件），但它证明的是插件侧，不是端到端。**这一类改动要判的是"沙箱里那个进程看不看得见这个路径"，主机测试表达不出来**——`test_rpcd` 那 27 条绿过一次，正是它掩盖问题的方式。

**正确的方向（未做，登记为 PLAN 第 3 节第 28 项）**：沙箱换得掉 `/run/zte-mesh` **里面**的任何东西，换不掉 `/run/zte-mesh` **本身**——那需要宿主 `/run` 的写权限，chroot 里没有。所以宿主写入的安全位置是直接写进 `/run/zte-mesh/<名字>`：临时文件建在 `/run`，最后一步 `mv -fT` 一次 rename 覆盖（目标即使是预先放的符号链接也被换掉，而不是被跟随）。rpcd 这一处照此要**取消 `actions/` 子目录**，请求文件直接叫 `/run/zte-mesh/<id>.act`；消费者的 `readdir` 已经按 `.act` 后缀与长度过滤，改成扫交换目录本身即可。
