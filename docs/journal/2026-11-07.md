## review 的三个 P1：越界写入、生产报文出口、apk 丢依赖

项目 review 报了 11 项（3 个 P1、8 个 P2），这一轮只修 P1，三项都配了回归判据。P2 未动。

**① `wlan-sync` 的状态写入跟着沙箱放的符号链接走。** `/run/zte-mesh` 是沙箱唯一可写的宿主路径，而沙箱与宿主同一个 UID（`ns-run` 只要求这个目录 root 所有、`mode & 022` 为 0，owner 是 root 就写得进去），所以它能在里面预先放一个 `wlan-sync.status.tmp` 符号链接；原来那句 `> "$STATUS.tmp"` 会跟着链接把宿主 root 的写入引到交换目录外面。改成把临时文件建在**宿主父目录**（`mktemp "$(dirname "$STATUS")/../.wlan-sync.XXXXXX"`、`umask 077`），再 `mv -fT` 覆盖目标：chroot 只 bind 挂共享目录本身（`src/ns-run.c:141`），父目录沙箱够不着，竞态从根上没有了——只把固定名字换成随机名字不够，同 UID 仍能在 `mktemp` 与 `printf` 之间抢换。`-T` 不能省：目标是指向目录的符号链接时普通 `mv` 会把文件搬进那个目录。两个新依赖都查过上游：busybox 1.36 的 `mv` 有 `-T`（`OPT_DESTNOTDIR`），`mktemp` 的位置参数 TEMPLATE 不受 FEATURE 开关限制，OpenWrt 的 `BUSYBOX_DEFAULT_MKTEMP` 是 `default y`。

**② 封禁/踢终端的报文从测试出口发，而且不等发送结果。** `controller_client_action()` 原来走 `lab-peer`——生产沙箱里那个接口已经被移回宿主 netns，daemon 只看得到 `veth-lab`——源地址还是写死的测试对端 MAC。改成与 `controller_radio_select()`、`controller_ap_metrics_query()` 同一条路：`veth-lab` 出口、`ioctl SIOCGIFHWADDR` 取 `br0` 的 AL MAC，`close` 前后保住 errno，并补上 kind 校验。服务那边原来 `(void)controller_client_action(...)` 把返回值丢掉，状态机在 tick 里就记 `sent`；现在 tick 只标 `pending`，服务逐个 agent 发完调 `actions_send_result()`，一个都没发出去或有任何一个失败就留在 `pending` 并 5 秒后重试（封禁不受踢终端那 3 次上限），发成功才记 `sent`（封禁下一跳改回 120 秒），撤销/到期的 `allow` 发成功才删行或记 `expired`。为此给 `action_entry` 加了 `releasing` 位，把"发 allow"与"规则已被删"分开——到期转 allow 时若重置重试计时器，configure 每秒进来一次就会把重试永远推后。

**③ 默认 CI 构建把三项运行依赖删干净了。** 这个 target 不编内核模块，workflow 为了把 kernel 包挡在构建图外，从 `DEPENDS` 里删掉 `ip-full`/`kmod-veth`/`kmod-sched-core`，但删完没补——装机主张写着依赖，发出去的 apk 里却没有，新板子装完缺 veth 就停在 `error=private-service-network errno=2`。读上游 25.12 的 `package-pack.mk`/`package-dumpinfo.mk`/`package-metadata.pl` 确认了正确机制：挪进 `EXTRA_DEPENDS`，`FormatDepends` 会把它并进 apk 的 depends，而 dumpinfo 与 metadata 都不读它，所以不进构建图；每项必须带版本约束（否则 `FormatDepends` 直接 error），故写 `(>=0)`。构建完再用 SDK 自己那份 `apk adbdump --format json` 读回 metadata 断言三项都在，少一项直接红。

## 批末 CI：先 lab-tools 再 apk；红在读法上，不在产物上

用户要"推送代码，发起 CI，然后测试"，并定下两件事：CI 走**完整**那条（先 `build-lab-tools.yml` 再 `build-apk.yml`），推 **`origin/main`（fork）**而不是 `ci/batchN` 临时分支。三个 P1 那笔是 `885800d`。

**repack 的三道核对**（LAB 第 3.0 节那四个坑照着走）：`--replace` 是 argparse 的 `store`，所有条目跟在**一个**标志后面；基线取**仓库里提交的那份** tar.gz，不是构建机上的旧副本；不在 Windows 上解包（`root/var/{tmp,run,log}` 是指向 `/tmp` 的符号链接，Git Bash 的 tar 建不出链接就整份复制本机临时目录），改用 `python tarfile` 逐成员比对。读数：4 567 624 → **4 566 479** 字节、52 个成员，只有 `SHA256SUMS` 与 probe 的内容变了，其余成员元数据逐个相同；新 probe 的 sha256 与 `prebuilt/db-engine-probe.sha256` 精确相等。`--replace` 跳过 `vendor_elf.audit()`，所以在成品压缩包上又跑了一遍（`root/` 下每个 ELF 成员读进内存、按 **basename** 索引 provider，不解包）：36 个 ELF、`missing_strong_symbols` 0、`missing_versions` 0。只换 probe 一枚的依据：trace `.so` 那六个源文件与 tar.gz 上次重生成那笔（`5905609`）逐个比过，没动。

- `T0=1794044019`，同一秒 `daemon_respawn old=116367 new=116679 status=0` 与 `role_loop role=slave epoch=1794044019`
- **+5 秒** `startup_renew=skipped role=slave epoch=1794044024`、**+8 秒** `agent_election attempt=1 status=0 epoch=1794044027`、**+20 秒** `attempt=2 epoch=1794044039`——两个门都从这次切换重新计时
- `/run/zte-mesh/` 多出 `wlan-plan`（子节点那条 M2 轮询真的开始跑了）
- `reload` 还原：同一秒 `daemon_respawn old=116679 new=116812` 与 `role_loop role=master epoch=1794044047`，**+4 秒** `startup_renew=0 epoch=1794044051`，`wlan-plan` 消失、拓扑 `online=true`
- **整个来回 `ns-run` 的 pid 一直是 115294**，三个实例没被 procd 重启过，换掉的只有沙箱里那个原厂守护进程

那个 +4 秒不是门限提前开了：门限量的是 `CLOCK_MONOTONIC` 上的 5 秒，打印的 epoch 是 `time(NULL)`，两者差一秒时墙上时钟就读成 4。

**同一步里还查出判据本身写错了一处**：原 ③ 要"`ubus call luci.zte-mesh status` 的角色那一行与 `state.json` 的 `role`"。可 `status` 的 `role` 读的是 **UCI**（`luci.zte-mesh:81`），这条判据故意不动 UCI，所以它整段都还答 `master`；而 `state.json` **根本没有 `role` 这个键**（`write_state`，`controller-service.c:890` 起那一段只 emit schema/running/sequence/uptime/daemon_pid/daemon_restarts/al_mac/self/version_mode/config_applied/restart_required/config_error/nodes）。已把 ③ 改成"看计划文件出现／消失"，并写明页面那一行为什么不作判据。

**H-19 ①（真 procd 那一层）**：关之前 `enabled=1`、三个实例 `running:true`、一个 probe 进程；`uci set zte_mesh.main.enabled=0` + `uci commit` + `/etc/init.d/zte-mesh reload` 回 `rc=0`，然后 `ubus call service list '{"name":"zte-mesh"}'` 答**空对象**（不是"实例还在但 stopped"）、probe 与 `multiapd` 进程都没了、`ip link show zmesh0` 答 `Device "zmesh0" does not exist.`、`/run/zte-mesh/` 只剩 `actions`/`peers`/`version_mode.host`。开回来三个实例全 `running:true`，`status` 答 `installed/running/attached=true`、`role=master`、`local=false`，签名尾部读到 `role=master local=off bridge=br-lan al_last= emulator=`——**P2-4 补进签名的那三个启动输入在真 procd 侧有读数了**。还原时 stderr 有一句 `Command failed: ubus call service delete { "name": "zte-mesh" } (Not found)`：`stop_service` 对已经不在的服务再删一次，rc 仍是 0、三个实例照常回来。走的是 UCI + `reload`，与页面保存进同一个 `reload_service`；表单那一层仍由 rpcd 与 `test_luci.js` 守，这一趟没开浏览器。

**H-19 ② 为什么没做**：测试环境两台都是 `backhaul=off`、`extra_slots=0`，子节点计划里两行都是 `slot=0 access=32`，一个 `zte_backhaul*` 段也没有——**不先搭出回程行就无段可撤**，"没报错"不等于验过。而且原步骤里"改主控的 `backhaul`"根本不是这个杠杆：那个选项只决定主控自己那一端，计划里的回程行来自主控的原厂 `WLANCfg` profile，**只有 slot 3 带 `MapAccessAttr=64`**（`wlan-profiles.c:305`），slot 3 又要先有 slot 2、slot 2 先有 slot 1（`zte-mesh.init:746`/`:749`）。搭建那一步还会给子节点主 BSS 加 `multi_ap 1`（`wlan-sync:573`）并触发 `wifi reload`，属会掉线的动作。这一轮只做了 ①，② 的步骤与代价已经写进 PLAN H-19，`prune_backhaul` 仍然只有主机判据。

**还原与复验**：两台 UCI 与动手前抄的基线逐字段相同（`enabled=1`、角色 master/slave、`backhaul=off`、bss/acl/backhaul/extra 段各 0 个），ax3600 仍 0 个终端，拓扑 `nodes_online=1`、`bss_detail` 两行各 `age=0`；只读 `verify-install.sh` 两台仍 `RESULT=PASS`（18／19 查——`batch_*` 那三条只在传目录那一轮跑）。这一批在两台 `/tmp` 上的暂存目录已删。

**留着没删的两处旧暂存**（不是这一批造的，只报告）：两台都有 `/tmp/zte-apk.batch12`（11.2M，11-03，里面有 r8/r9/r16–r18 的 apk 和一份 `zte-mesh-launcher-0.1.0-r1.apk`——正是 H-17 那条 `zte-mesh*.apk` glob 会误匹配的东西）与 `/tmp/zte-apk14`（3.7M，11-04）。删它们要单独点头。

**这一趟学到的**：

1. **判据里点名的字段，先去读它的写方。** H-18 的 ③ 要一个 `state.json` 里不存在的键，还要一行按设计不会变的读数——两处都不是"上机就能发现"的错，是写步骤时没打开 `luci.zte-mesh` 与 `write_state`。同类的还有 H-19 ② 那个杠杆：**选项名字看着对，不等于它通到你要的那条路**。
2. **同一个值，两条路。** `mesh_role=slave` 走 UCI 是冷启动、走运行期配置文件是热路径，两者跑的代码不同。判据要钉的是"哪条路"，不是"哪个值"——这也是为什么 P2-11 在主机测试里只能钉形状。
3. **strip 之后认身份只能靠 build ID**（批 25 已经写过一次，这一趟是第一次真拿它认定一批）：装上的 probe 189 155 字节对 tar.gz 成员的 211 708，sha256 必然不同，而 `.note.gnu.build-id` 是 allocated 段、strip 不动它。
