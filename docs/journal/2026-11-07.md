## 建 PR 这件事为什么绕了一圈：`github` MCP 的写工具坏了

`mcp__github__create_pull_request` **成功和失败都回同一条错误**：

```text
MCP error -32602: Input validation error: ... must have required property 'result'
```

服务器拿不到它预期的那个 `result` 字段，于是无论 GitHub 那侧成没成都报错。同一个服务器的 `pull_request_read(method:"get")` 也是这句，所以**连"有没有建出来"都问不出来**。能用的只有 `search_*` 与 `get_me`。

判据只能走 REST：`pulls/3`、`pulls/4`、`pulls/5` 逐个匿名读（issue 与 PR 共用一个编号序列，仓库里已经有 issue #3，所以新 PR 必然是 #4），`search_issues type:pr` 也是空的 ⇒ 确认没建。然后用 `git credential fill` 取 token + `curl` 走一次 `POST /repos/cnjn/zte-mesh/pulls`，回 `201`，`html_url` 才是那条 PR。**跨仓库的 `head` 必须是三段** `Leenshady:luci-app-zte-mesh:pr/upstream-batch24`——fork 的仓库名和上游不一样，写成 `Leenshady:pr/upstream-batch24` 这种两段式回 422。

这条坑连同配方一起写进了用户级记忆（`env-github-mcp-write-result-schema-broken.md`）。

## `github` MCP 的可用面（2026-11-07 实测）

| 能用 | 不能（`-32602 … must have required property 'result'`） |
|---|---|
| `get_me`、`list_pull_requests`、`search_pull_requests`、`search_issues`、`list_branches`、`list_commits`、`list_releases`、`get_commit`、`search_code` | `create_pull_request`、`pull_request_read`、`get_latest_release`、`get_file_contents`、`get_tag` |

两处参数规矩：`list_issues` 的 `state` 只认大写 `OPEN`/`CLOSED`（`"open"`/`"all"` 直接校验失败）；`issue_read` 必须带 `method`。`get_commit` 是单对象却回得来，所以坏的是一批工具的 output schema，不是"数组还是对象"。替代：最新 release 用 `list_releases` 取第一条；文件内容读仓库或走 REST；写（PR/评论）走 `git credential fill` + `curl`，见上一节。
