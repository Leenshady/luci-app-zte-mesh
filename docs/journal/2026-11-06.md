删之前要想清楚的两件事：**删 release 删掉 9 个资产但 tag 留着**；`docs/INSTALL.md` 第 29 行与 `README.md` 第 76 行都写着 Release 是唯一的下载来源，所以删完对外就只剩"自己从 feed 编"这一句——要删就得同时决定是重发一版（run #60 那份 `main` 产物）还是改那两处口径。

**"按架构分开"的答案是不必**，账用 r22 两台的读数算：

| 量的东西 | 读数 |
|---|---|
| apk 里三份架构的压缩后体积 | ≈ 1.19 MB / 整个 apk 5 101 814 字节 |
| 装机后 `arch/` 合计 | 2 420 KiB（aarch64 那对 128 KiB、armv7 745 KiB、x86_64 1 553 KiB） |
| 私有根 `/usr/lib/zte-mesh` | 18 996 KiB（`ax3600`）／19 076 KiB（`owrt`）——架构那部分是它的零头 |
| 一台机器真正会 exec 的那一种架构 | `ax3600` 132 KiB、`owrt` 1 560 KiB |
| 剩余 flash | `ax3600` 182 MB 空闲（已用 5%）、`owrt` 15 MB 空闲（已用 95%） |

省下的那一 MB 落在**最不需要它的机器**上：`ax3600` 有 182 MB 空闲却要背全部三种架构，`owrt` 只剩 15 MB 却把它真正要用的那一种架构（x86_64）编得最胖。风险则都在拆分那一边：

- `/etc/apk/arch` 装的是 **profile 串**（`aarch64_cortex-a53`、`x86_64`），两台都没有 `/etc/apk/compat_arch`——按架构出包等于把包写死在某个 profile 上，正是批 20 删掉 `DEPENDS:=@(TARGET_zte||TARGET_qualcommax)` 时要搬走的那句装机拒绝，拆回去会把"什么机器都能直装"重新变成"这台装不上"。
- 一个 Makefile 只有一个 `PKGARCH`（`package-pack.mk` 读全局值），三份包要么三个 Makefile 目录，要么回到批 21 刚合掉的那种"两个包抢同一批文件"（H-17 那个重装顺序问题）；要么每个 apk 都带一份 4.57 MB 的运行包 tarball——那是三倍的包体积换一倍的收益都不到。
- 判据全要重写：`ZTE_MESH_REQUIRE_ARCHES`、CI 的 `expect_elf` 循环、`verify-install.sh` 的三个 `launcher_*`、H-16 那条"armv7 没有机器"。

**真正起作用的不是拆分，是那一份是谁编的**——这句话把用户引到下一件事上。

## x86_64 那一份改用 musl-gcc（用户特别要求"把 x86_64 换成 musl-gcc 试试"）

验证方式按用户选的：**在编译机 `ubuntu` 装 musl 现场编**，不烧 CI 那一轮。

### 头文件路径找了三次

`tools/build/launcher-arches.sh` 的 x86_64 候选本来就是 `musl-gcc cc`——CI 日志里那句 `built x86_64 with cc` 是 musl 编不出来之后的退路，不是没装。装完 `musl-tools musl-dev`（musl 1.2.2）再编，失败三次：

1. 直接 `musl-gcc` → `linux/capability.h: No such file or directory`、`linux/if_link.h: No such file`。`musl-gcc.specs` 带 `-nostdinc`，内核 UAPI 头不在它的搜索路径上（Ubuntu 把它们全放在 `/usr/include`，属 `linux-libc-dev`）。
2. `-isystem /usr/include` → glibc 的 `errno.h` 赢过 musl 的 → `bits/wordsize.h: No such file`。`-isystem` 的优先级在 musl 那份目录之前，等于换了个 libc 编。
3. `-idirafter /usr/include` → `linux/types.h` 找到了，它 `#include <asm/types.h>` 又找不到：musl 的 include 目录里有 `arpa`/`net`/`sys`，**没有 `linux` 和 `asm`**，而 Debian 把 arch 的 `asm/` 放在 `/usr/include/x86_64-linux-gnu/`。

结论是 `-idirafter` 这个方向对、目录要两个，而且**不该硬编码发行版的路径**：脚本改成问宿主 `cc`"你会搜哪些目录"——它就是退路 `cc` 编译时用的那一个，它的答案对这些源文件必然是够的——再把其中真的有 `linux/if_link.h` 或 `asm/types.h` 那两个头的目录加在 musl 的搜索顺序最后。这样 musl 自己的 libc 头仍然优先，只是补回它本来就没有的内核头；换发行版不用改脚本，唯一的外部条件是这台机器上 `linux-libc-dev` 在（CI 现在装 `cc` 编出来的那份本来就需要它）。

只在**非目标架构**的候选上生效，并且匹配放在 `-musl-gcc` 之后：OpenWrt 自己的 aarch64 编译器就叫 `aarch64-openwrt-linux-musl-gcc`，它必须继续吃 `$(TARGET_CFLAGS)`，不能被这批 `-idirafter` 顶掉。

### 读数（编译机 `ubuntu`，Ubuntu 22.04，gcc 11.4，musl 1.2.2）

| x86_64 那一对 | `cc`（glibc） | `musl-gcc` |
|---|---|---|
| `ns-run` | 958 152 | 79 600 |
| `mesh-search` | 1 078 256 | 75 632 |
| 合计 | 1 992 000 | **155 232** |

CI r22 那对的读数是 1 590 648 字节（`owrt` 装机 `arch/x86_64/` 1 553 KiB），换成 musl 后同一种架构剩 152 KiB——三份架构合计从 2 420 KiB 少 1 401 KiB。apk 是压缩后 5 101 814 字节的容器，按上面那两份 `xz` 的差算约省 595 KB（≈12%）；**这两个 xz 数字来自本机的 `cc` 产物**，CI 那台编出来的 glibc 对本来就小 400 KB，真省的重量以下一次 CI 的 apk 为准。

## CI 读包那一步补上重量判据（用户接着特别要求）

上面那句"缺的只剩那一轮 CI"漏了一件事：**那一轮跑通也回答不了重量**——读包那一步只问两件事，成员在不在（`has_member`）和这份是不是这种 CPU 架构的代码（`expect_elf`）。而宿主 `cc` 编出来的 x86_64 那份**站在同一个路径、是同一个 CPU、`file` 回同一行 ELF**，它只是把 glibc 整份静态搬了进来。所以判据只能是字节数。

上限按测到的两组数定，各留三倍余量：要 musl 的两种架构每份 **204 800 字节**（musl x86_64 实测 79 600／75 632，宿主 `cc` 的 r22 那对 735 932／854 716；aarch64 从 SDK 的 musl 工具链出来是 128 KiB 那对，同一份源码在 glibc 交叉编译器上是 1 408 328）。**armv7 给上限是假的**：那种架构仍是 hard-float 的 glibc 交叉编译器（r22 每份约 372 KiB），编一个数进去只会把"libc 的选择"变成"红在别的原因上"，所以它只报数不判（判据传 `-`）。

实现是读包那一步里的 `expect_weight ARCH NAME CEILING`（`.github/workflows/build-apk.yml` 第 682 行）：`wc -c <` 取字节，`-gt` 比较（所以正好等于上限算过），六个读数写 `launcher-weights.txt`，`Summarise the batch` 那一步把它 `cat` 进 run summary——批末不看 artifact 也能读出这一轮的重量。失败那三行说清两件事：退路会在构建日志里先自报（`built x86_64 with cc`），以及**上限是要故意改就得写理由的那种承诺**。

干跑按第 2 节那条规矩做：`sed -n '680,698p'` 把**真那 19 行**取出来（去掉缩进），`head -c` 造出指定字节的 fixture，9 条断言全过——

| 传入的情况 | 结果 |
|---|---|
| aarch64／x86_64 各 79 600，armv7 400 000 | rc 0，六行读数（`ceiling -` 两条、`ceiling 204800` 四条） |
| x86_64 一份 735 932（r22 的 glibc 那一份） | rc 1，报出字节数与上限 |
| 正好 204 800 / 204 801 | 过 / 红（`-gt` 严格） |
| armv7 两份各 2 000 000 | rc 0——那种架构没有上限可破 |
| 删掉 `arch/armv7/mesh-search` | rc 非 0，`wc -c <` 失败不会被读成 0 字节 |

顺带踩到一个本机的坑，值得记下来：把 workflow 的 `run: |` 块逐块交给 `bash -n` 时，如果用 `subprocess.run(..., text=True, input=src)`，**Windows 会把 `\n` 写成 `\r\n`**，六个块因此假报 `syntax error near unexpected token $'{\r'`——看着像 workflow 真的坏了。改成 `input=src.encode('utf-8')` 之后 15 个块全部 `bash -n` 通过。

**还没读到的**：这一轮 CI 与它读出的六个数。`PKG_RELEASE` 照旧停在 r22，按第 2 节的节奏和"两个 127"攒成下一批一起触发——那时第一次跑的就是这条新判据本身，红了要先看它是红在 musl 没编出来，还是红在上限定得太紧。

### 拆成 launcher_ready()

`start_service()` 在主机上跑不动——它先要 `/sys/class/net/<桥>/bridge` 这一步（要真有一个桥），再要 procd。所以那三段判断以前只能用字符串盯着，永远读不出**顺序**。现在三段搬进 `launcher_ready()`，`start_service` 里只剩一句 `launcher_ready || return 1`，判据变成真的能执行：测试 source init，直接调这个函数，读 `$LOGF` 里落下哪一句。没有加新的环境变量——`ROOT`/`NSRUN` 顶部本来就吃 `ZTE_MESH_ROOT`/`ZTE_MESH_NSRUN`，测试要伪造的情况（缺目录、缺文件、stub 答 127、stub 答 64）那两把钥匙就够了。

### 顺带读出一条：apt 下载缓存一次都没保存成功

第 7 步 `Save the apt download cache` 的原文：

```
/usr/bin/tar: ../../_temp/apt/archives/lock: Cannot open: Permission denied
/usr/bin/tar: ../../_temp/apt/archives/partial: Cannot open: Permission denied

##[warning]Cache save failed.
```

根因是顺序：`chown -R` 排在 `apt-get` **之前**，而 apt 下载时把 `lock` 与 `partial` 重新收归 `_apt`（700）。
后果比"这一步坏了"更大——**没保存成功的 key 下一次也不可能命中**，所以批 23 第 2 条（缓存下载）从写下来到现在**一次都没生效过**，
上面那句"未命中"不是运气，是必然。修法是在 `apt-get install` 之后再 `chown -R` 一次，已改（判据：下一轮 `Save` 不出现
`Failed to save`，**且**再下一轮 `Restore` 报 `Cache hit for: apt-<同一个哈希>`；两行缺任何一个都不许把 apt 那一步的秒数当提速）。
`continue-on-error` 这条留着是对的：缓存服务坏了没连累一批包，只是这条提速自己没成。

第一版草稿按 `v0.3.0` 写，正文第一段还得专门解释"两个身份"（tag 是 `v0.3.0`、apk 里写 `0.1.0-r23`），
因为**这两套数从来没对上过**：`v0.1.0`→r10、`v0.2.0`→r22，而且三个包自己就是两个号
（`zte-mesh 0.1.0-r23` 对两个 LuCI 包 `0.1.0-r11`）。用户看了直接给规矩：**tag 和 apk 版本要统一**。
选的是"三个包的 r 号对齐 + tag 写完整版本串"，另一件事同时定：**旧的 `v0.1.0`、`v0.2.0` 两个 tag 删掉**。

### 对齐改的只有一行，欠的是一轮构建

`openwrt/luci-app-zte-mesh/Makefile` 的 `PKG_RELEASE` 从 11 写到 23。这一个 Makefile 同时出 `luci-app-zte-mesh`
和 `luci-i18n-zte-mesh-zh-cn` 两个包，所以一行让三个 apk 变成同一个号。
改动面先查过再动：`git grep` 扫 `*.sh` / `*.py` / `*.yml` / `*.js` / `Makefile`（排除 `out/`），
文档以外**没有任何一处写死 `r11`**，所以没有测试要跟着改。

**代价说清楚**：产物还没对齐。`out/ci/batch23/` 那两个 LuCI apk 仍是 `0.1.0-r11` 的字节，
`apk list` 三行要读到 `r23 / r23 / r23` 得等下一次构建——**这一轮只改 Makefile 不触发 CI 是不成立的**，
所以草稿里那两个包的位置写"待这一轮构建"，不填上一轮的数冒充。

规矩跟着改到三处：PLAN 第 6.3 节（"只给这一批改过的包加一" → **三个号对齐、批末一起加一**）、
DEVELOPMENT 第 8 节（tag 名 = `v<PKG_VERSION>-r<对齐后的号>`）、README 与 INSTALL 的版本串陈述。

### 删 tag 之前先把 SHA 抄下来

`ls-remote --tags origin` 回读两条：

```
feaac56b55ab8d32c26360e735da15610b5a411c  refs/tags/v0.1.0   # 2026-10-31 20:04 +0800，那次 release 的树
d9ce19d6ce3a058ad94f33189b19352406938b07  refs/tags/v0.2.0   # 2026-11-05 17:13 +0800，ci/batch21 的 tip
```

两条 `merge-base --is-ancestor … main` 都成立——**删 tag 删不掉任何提交**，删的只是那两个指向名字。
`d9ce19d` 尤其要留住 SHA：那是 `v0.2.0` 那次构建实际吃的树，将来要复现那批字节只能按 SHA 取。
SHA 已写进 PLAN 第 6.1 节、FEATURE_STATUS 头部与草稿「装机」那两条升级说明。
`upstream/main` 是另一棵树（`0df93c7f`），这两个 tag 不在上游，删除只影响 fork。

删完回读：`ls-remote --tags origin` **空**，本地 `git tag` 也空，`git tag -d` 报的两条 `was feaac56` / `was d9ce19d`
与被删的 SHA 一致。**从这一版起，"这一批发在哪个提交上"只能靠 release 的 `target_commitish` 说**，tag 名字不再额外携带信息。
