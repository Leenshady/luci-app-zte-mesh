### B16b 主控 CurHop 的实验室开关：不改 C

H-14 ⑦ 分不开的那一种：主控写 `CurHop=2`，子节点 `MaxHop` 也是 2，于是"子节点跟随主控下发的
TLV `0x43`"与"`slave_init` 把自己设成 `MaxHop`"读数一模一样。要分开只需要主控那侧写一个不等于 2 的数。

先看有没有现成的口子——**有**：`mesh-policies.c` 的 `profile_apply` 每次启动按视图读
`/run/zte-mesh/db-profile`（`TABLE ROW FIELD VALUE`），`controller-run.c` 在写角色列**之前**把它应用到
`MultiAPCfg`，而主控分支根本不写 `CurHop`（只有子节点分支写 `-2`）。所以一行

```sh
printf 'MultiAPCfg 0 CurHop 5\n' > /run/zte-mesh/db-profile   # 之后重启服务
```

就是一个只有实验室手写得出来、页面上没有对应选项、UCI 里没有对应字段、apk 里不存在的开关——
**它到不了用户的机器**，这是这个仓库一贯要求的情况。

考虑过环境变量（`ZTE_MESH_CUR_HOP`），放弃：`ns-run.c` 起手 `clearenv()`，只转发白名单里的
`ZTE_MESH_*`，加一项要同时动 launcher 和服务，还得给一个只存在于测试里的取值写生产代码。

真正缺的从来不是开关，是**"开关生效了没有"的判据**。子节点读到 2 有第三种可能：主控把这一列拒了，
从来没发过 5。于是 `verify-install.sh` 加两条：`db_profile_cur_hop=`（文件里那一行，没文件或没这一行
都是 `absent`）和 `master_cur_hop=`（拿守护进程那行 cfg 的 `cur_hop` 与它比，**相等才判 PASS**）。
不作判定的四种：`not-master`（子节点的启动路径会把 `-2` 写回来，它后来那个数归 `smoke_cur_hop` 判）、
`no-cfg-line`、`not-read`（`-98`）、以及同一道 `CUR_HOP_GRACE` 的"太年轻"。顺手把 `max_hop=` 也报出来——
⑦ 那一次读取要的就是 `cur_hop` 与 `max_hop` 两个数并排。

**一个容易踩的顺序**：`controller-service.c` 换角色那处往主控方向写 `CurHop 2`。所以窗口期间在页面上
把角色切走会静默覆盖开关，读数回到 2 会被当成"子节点用的是本机 MaxHop"。写进 INSTALL 第 3 节和 H-14 的风险列。
