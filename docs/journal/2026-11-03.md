## 批 5 · A22 的"日志轮转"：量完发现要修的不是轮转

PLAN 第 2 节把 A22 的尾巴写成"日志轮转"。先查它到底轮转什么，结论是**这个服务没有会无界增长的文件**，
所以"轮转"是个假问题；真问题是**一次配置推送把设备日志环占满**。两件事都不是靠读代码看出来的，是量出来的。

**文件这一半（负结果，但要留）**：沙箱根是 `MS_RDONLY` bind，写不进去；`/tmp` 与 `/var/tmp` 是
`size=8m` 的 tmpfs，`/dev/shm` `size=1m`；服务自己写的只有 `/run/zte-mesh` 下那几样（配置、`state.json`、
`actions/`、`peers/`），全是小文件原子替换。`ns-run.c` 的挂载表逐条对过，没有第三个日志文件。
所以唯一的落点是 **logd 的环**：两台实验机都是 `system.@system[0].log_size='128'`（KiB），
`logread` 当下 1179 行——"约一千行"不是估计，是现在能读到的数。

**挤占是真的**：一次真子路由配置推送里，原厂 daemon 自己重复打了 **1012 行**（`acdc current state[N]:…` 与
`WLAN_ASSERT_RET …` 两种格式，7 分钟内），比整圈环还多；四小时后回看，`logread` 里 94.5% 仍是这两行。
也就是说用户想看的东西（入网、封禁、告警）被自己控制器的状态轮询挤掉了，而**这一路原来挂在火管那 2 万行的预算上，
打光了也不吭声**——`ZTE_TRACE_VALUE` 与 `ZTE_TRACE_ALL` 共用一个计数，且没有 exhausted 提示。

**改法（`controller-log.c`/`.h`，新的可主机测的接缝，同 A21 的做法）**：

| 类别 | 预算 | 说明 |
|---|---|---|
| ordinary / protocol / device / renew | 160 / 64 / 48 / 48 | 沿用原来的每进程预算；前两个打光各发一条提示 |
| value | 20000 | 四条**一次性**证据行（`cfgChg`、`WSC-%d will cfg`、`M2 total Length`、`mesh sync for M2`），逐条打，不采样 |
| **poll（新）** | **每 60 秒 4 行** | 两条重复行改打 `ZTE_TRACE_POLL`，按 `CLOCK_MONOTONIC` 的分钟采样，每个超额的窗口发一条 `log_budget=poll sampled=1 limit=4 window=60s` |
| firehose | 20000 | `/run/zte-mesh/trace-all` 打开时才有；预算归进同一个 gate，不再由 `controller-trace.c` 自己数 |

三个决定值得记：

1. **判据读的是格式文本，不是值**——值行打印的是 daemon 已经格式化好的结果，所以带密钥/SSID/BSS 的格式
   （`PWKey`、`WEP`、`BeaconType`、`PSK`、`Bss`、`WLANCFG`…）在 `controller_log_shape()` 里**先否决**，
   永不展开。这条顺序是测试点：`"Bss current state[%d]"` 必须返回 -1，即使它也匹配 poll。
2. **时钟由调用方传进来**（`long now`），gate 也是调用方拥有的 `struct log_gate`。这不是风格：`controller-actions.c`
   踩过"用 `time(NULL)` 判到期、实际拿的是 `CLOCK_MONOTONIC`"的时钟域坑，所以这里 preload 侧取 `CLOCK_MONOTONIC`，
   测试侧自己造时钟，倒退的时钟、跨分钟、连续 60 分钟都是能喂的输入。
3. **提示语本身要能被读出来**：三条提示都是固定串，且 `controller_log_class(notice)` 落在 ordinary——
   读者要能分清"没发生"和"日志不说了"。同一句写在 `controller-log.h` 的注释里。

一次推送从 **1012 行 → 28 行 + 7 条说明**（测试里就是这么断言的：`kept*25 < 1012`、`kept+notices < 40`）。

**测试**：`tests/controller-log-codec.c`，`make test-host` 里跑，**655 649 项断言**（含 2^17 次有界变异：
随机改 11 条种子格式，断言类别/形状永远在集合内、被放行行绝不带提示、每类不超预算、ordinary 真的打满 160、
poll 在很多窗口里真的还在流）。三条 fixture 写错、当场改掉，都不是代码问题：
喂 145 行时 `step=1` 会跨两个 60 秒窗口（"7 窗口 28 行"的算术就崩），renew/device 只喂 40 行却断言等于 48 的预算，
`strncmp` 提示前缀的宽度写成 34（真实长度 32）。

`memcpy`/`snprintf`（`tools/lab/build.sh` 显式关掉 fortify），**没有比原厂 glibc 2.26 更新的引用**——

## 批 5 · 当天就补的尾巴：采样说明要报出丢了几个

装机读数里最有用的一条不是"上限守住了"，而是**它没告诉我守掉了多少**。四个窗口各 4 行、各一句
`log_budget=poll sampled=1 limit=4 window=60s`——`4 留 5 丢` 和 `4 留 1000 丢` 在日志里长得一模一样，
而这两种情况对读日志的人是不同的故事：前者无所谓，后者正是这次要防的挤占。所以 `gate` 里加一个累计计数，
说明改成 `… window=60s dropped_total=N`。

三个决定：

1. **数的是累计，不是本窗口**。一句说明只能在它被打印的那一刻写；本窗口还没过完，写"这一分钟丢了 X"必然是假的。
   累计数不用解释这一点：相邻两句之差恰好是**上一个**窗口丢的（第一句打在第一条被丢的行上，误差自己抵消），
   最后一句之后还在涨——所以它是下界，不是总量。这条写在 `controller-log.h` 的注释里，测试按它断言。
2. **提示文本仍然只由 gate 生成**，数字除外。原来的"三条固定串"变成"两条固定串 + 一条固定句式带一个数"：
   值行打印的是 daemon 格式化好的结果，那才是绝不能掺进去的东西，采样计数是我们自己的数。
   代价是 `*notice` 从"指向静态串"变成"指向 gate 里的缓冲区（到下一次 admit 为止有效）"，
   `emit_line()` 本来就是拿到就写，契约写在头文件注释里。
3. **`snprintf` 进 preload 前查过 ABI**：重编后的 ARM32 shim 新增引用只有 `snprintf@GLIBC_2.4`，
   远低于原厂 glibc 2.26（`tools/lab/build.sh` 关掉 fortify，所以不是 `__snprintf_chk`）。

主机测试多一条规则 `test_the_notice_reports_what_it_dropped`：七分钟 ×145 行的那一次推送，
第一句必须是 1、之后每句比上一句大 141（145−4）、总共七句、末句 847 且小于全轮丢弃数 987；
不满上限的窗口一句都不发。**655 671 项断言**（比上一版多 22）。换包走 LAB 3.0：逐成员 diff 只有
`root/lib/libzte_controller_trace.so`（21 372→21 376）和 `SHA256SUMS` 变了，`tests/test_runtime.py` 0 失败。

**没做的事**：`PKG_RELEASE` 不动——这次改的 `.so` 要装机才有意义，加号留到下一次批末 CI 一起；
`log_budget=ordinary` 与 `log_budget=packet` 两句也不加计数，它们一个进程只说一句，说了也读不到差值。

## 批 7 · A18c：拓扑页的软件版本那一格，为什么一直是空的

装机复验时页面上唯一还写着 `-` 的常用列就是软件版本。`nodes[].software` 取自
`IGD.P1905DeviceInfo` 的 `SoftwareVer`，而这张表在真子路由上是空的——所以先别改页面，先查这一列到底
有没有人往里写。全部结论是 [代码]：`out/vendor/root/bin/multiapd` 反汇编，地址用
`arm-linux-gnueabi-nm -n` 逐个核过。

四个环节，一条链：

1. **发送侧发**：`ApCapabilityReportSend @0x58470` 里 `movw r1, #0x8002`（`0x584e8`）是 AP Capability
   Report，`0x58668` 调 `I5TlvDeviceInventoryTypeInsert @0x501e0`，库存材料来自 `slave_get_global_data`。
   也就是**版本串确实上线了**，就在 0x8002 的厂商 TLV `0xd4` 里。
2. **接收侧收**：`ApCapabilityReportReceive @0x41f80` 在 `0x42068` 调 `I5TlvDeviceInventoryTypeExtract
   @0x3d674`。这个函数按 `[长度1 文本]` 连读三段，依次写进设备记录 `+312` 序列号、`+247` 软件版本、
   `+377` 硬件版本；`I5TlvExtractChildlv @0x68764` 里 `cmpls r2, #64`——超过 64 字节**不拷贝但照样跨过去**，
   后面的字段才保得住位置。
3. **但它不入库**：`IGD.P1905DeviceInfo` 唯一的写手 `topoAdd1905DevInfoToDB @0x8e37c` 只取 `+24`（MAC）、
   `+60`、`+124`、`+584`。`+247` 全仓库只有厂商 CLI `master_print_devinfo_list @0x23348` 读过。
   **`SoftwareVer` 从来没有被从线上解出来过**——页面空不是抓包没抓到，是原厂根本没写。
4. **旧猜测作废**：REPLAY_RESULTS 里写过"HLR 的厂商 TLV 里有 `V1.0.0.2B2.8000`"。顺着
   `I5TlvHigherLayerVendorTypeExtract @0x981f8` → `I5TlvVonderDevIdenExtExtract @0x6888c` →
   `I5TlvCoverStructToDevice @0x96010` 走一遍，落点是 `+520/+584/+392/+60/+124/+648/+456/+784` 和两个 u32，
   **没有一个 `+247`**；本地 15 个 pcap 也搜不到 `V1.0.0`。这条猜想去掉，换成上面这条有地址的链。

做法上只补数据通路，页面一行不动（`zte-mesh.js` 早就在渲染 `node.software || '-'`）：

- `controller-1905.c` 加 `device_inventory_software()`：跳过序列号取第二段，空、>64、含 `' '` 以下或 0x7f
  一律当"没说"。
- `controller-peer.c` 只在 CMDU **就是 0x8002** 时认这个号码——`0xd4` 在别的消息类型里是别的字段。落成
  独立的 `peers/<MAC>.software`：版本不是数字，不能塞进 metrics 那个 `key=value` 摘要里。
- `controller-service.c` 加 `read_peer_text()`，只在数据库那一列为空时用它填 `state.json`。**数据库里有值
  的行优先**：主控自己那一行本来就填得好好的，不该被一帧覆盖。

一个真踩到的坑：第一版是"先 `memcpy` 进 `out`，再校验 `out` 这个 C 字符串"。于是
`'V' 0x00 '1'` 这种带内嵌 NUL 的字段返回了成功，页面上会显示一个凭空的 `"V"`。改成把
指针和长度交给调用方、**校验原始字节后再拷贝**，所有拒绝路径都留 `out[0]=0`。

主机测试：`controller-1905-codec` 从 101 断言涨到 **192**（整段、每一刀截断、空字段、控制字节、
64/65 边界、小缓冲区截断 + 围栏字节，末尾还对整段做了逐刀扫，10 万次有界变异不变量守住）；
`controller-peer-codec` **71 项**（版本单独一个文件、同号码在别的消息类型里不落盘、没有清单的 capability
report 不落盘、空版本不覆盖已有文件、最新一版赢且只有报的那台变）。`out/db-engine-probe` ARM32 链接过、
`controller-service.c` 单独 `-Wall -Wextra -Werror -fsyntax-only` 过。

**没做的事**：`PKG_RELEASE` 不动、CI 不触发——这一批只有一项，跟下一次批末一起走。真机那一半登记成
**H-12**：这颗 Z506 到底发不发 `0xd4`、字段顺序是否与这份二进制一致，都得抓 0x8002 看；负结果也算数，
那说明得另找来源。

## 批 8 · A18d：终端数按 BSSID 记账——摘要文件是"最后一帧说了算"

批 2 落下的 `peers/<MAC>.metrics` 是一份 `key=value` 摘要，**每帧整份重写**。这在"一帧报全部"的
假设下没问题，但子节点是可以**按射频分别回 `0x800c` AP Metrics** 的：2.4G 一帧、5G 一帧，页面就在
两个数字之间来回换；夹一条只带 `0x83`（BSS 数）的帧，重写出来的摘要里根本没有 `stations=` 这一行，
服务读成 -1，页面上那一格直接空掉。数字没错，错的是"谁最后到谁说了算"。

先把范围定死：**这次不动页面**。`state.json` 里一个节点一个 `stations`，逐路的明细没有格子放，
要加就得连着 rpcd、LuCI、i18n 一起改；那不在这一项里。要做的是让**求和的对象**从"最后一帧"变成
"每一路各自的新鲜度"。

- `controller-1905.c` 加 `ap_metrics_by_bss()`：把一帧里的 `0x94` 逐条解成 `{BSSID, 终端数}`，按
  帧里的顺序返回。**唯一一条设计上的硬规矩**：同一个 BSSID 出现两次、或路数超过
  `CONTROLLER_AP_BSS_MAX`（16），一律返回 0，不给部分列表。半份列表加起来是一个偏小的数，而偏小的数
  和没测出来的数在页面上长得一样——这种"看起来像测量"的错不能留。
- `controller-peer.c` 每路落一个 `peers/<MAC>.<BSSID>.sta`，里面只有一个数字一行。每路**各自的时间戳**
  是关键：一路停止上报只让它自己的文件过期，别的几路照旧。摘要照旧写，作为拆不开时的回落。
- 读侧 `controller_peer_bss_load(mac, max_age, &load)` 遍历目录，把没过期（默认 30 秒）的条目加起来，
  `load.entries` 是几路、`load.age` 是其中最老的一路。目录是 root 可写的 tmpfs，文件名和文本都不信：
  两段 MAC 反着写、尾巴多一个字符、值不是数字、大于 0xffff（线上是 u16）都不算一条。
- `controller-service.c` 里 `stations` 改成先取这个和，取不到才用摘要——老设备写出来的
  `<MAC>.stations`（r10 及更早）那一路兜底也留着。跟着一起改的是 `metrics_age`：页面那一格的"新鲜度"以前读的是
  摘要文件的 mtime，一旦数字换成逐路的和，这个年龄就得跟着换成**其中最老那条 `.sta`** 的年龄——一个由两帧拼出来的
  数，最多只能老到它最旧的那一半。这一条没有代码守它：`controller-service.c` 只进 ARM32 的 `db-engine-probe`，
  主机测试喂给 `test_rpcd.sh` 的是假 `state.json`，`stations` 与 `metrics_age` 的对应只能在装机时对
  `peers/` 的 mtime 读一遍。

两个真踩到的坑：

1. **测试之间共用同一个目录**。`.sta` 的名字前缀还是 MAC，`two_children()` 那句
   `distinct_macs() == 2` 把新的文件当成新节点，报在 213 行。加了一个 `clear_peers()`，
   `stations_are_per_bss()` 开头清一次、结尾再清一次——它读别人的状态，但不给后面留自己的。
2. **ARM32 链接不过**：`fstat` undefined。原厂那套 glibc 2.26 只导出带版本的入口，
   `controller-service.c` 早写了 `__fxstat(3, ...)` 替身，但 `controller-peer.c` 同时要在主机上编
   （主机测试跑的就是它），所以替身用 `#if defined(__arm__)` 关住，主机仍走真 `fstat`。
   `libzte_controller_trace.so` 也链这个文件，两处一起重编才敢说链接是绿的。

主机测试：`controller-1905-codec` **192 → 212** 断言（两路保序、带"估计服务时长"的 20 字节 TLV、
0 终端是真条目不是缺项、没有 metrics TLV、8 字节残帧、切在计数中间、重复 BSSID、`max` 比路数小、
`max=0`/`NULL`）；`controller-peer-codec` **71 → 103** 项（空目录不等于 0、一帧两路落三个文件、
单射频帧后摘要变小而总和仍是两边、单独让一路过期、条目属于报它的这台、重复 BSSID 不落 per-BSS、
三种坏文件都不读、手写一条合法的能读）。`make test-host` 其余项不回归，ARM32 的 `out/db-engine-probe`
与 trace 库都重编过；`test_schema.py` 那 4 项还是缺 `out/analysis/cspd`，与这次改动无关。

**没做的事**：`PKG_RELEASE`、CI——都跟下一次批末一起走。**批末记得 `sh tools/build/runtime.sh install` 重打运行包**：CI 用的
`openwrt/zte-mesh/zte-mesh-runtime.tar.gz` 是随仓库提交的那份，批 7 与批 8 的 C 改动都还没进包（批 9 的也等着）。

两种都算通路成立，只是页面那个数的来源不同。

## 批 9 · A18e：把逐路的数送到眼前——一个总数说不出哪块射频忙

批 8 把每一路的数记成了各自的文件，页面却还只有一个总数：**5 台终端挂在 5G 上**和**5 台摊在两路上**，
在页面上长得一样。批 8 收尾时我把这件事写成"要动 `state.json` + rpcd + LuCI + i18n"，动手时才发现这句
估计贵了 rpcd 一半——`luci.zte-mesh` 的 `status` 本来就把整个 `state.json` 透传（批 2 的 A18b 已经踩过这个
事实），加字段不用碰它；i18n 本来也不必碰，只要不新增带文字的句式。

- **读侧**：`struct peer_bss_load` 多出 `detail[]`（`bssid` / `stations` / `age`，`listed` 是放了几行）。
  顺序按 **BSSID** 排，不是按 `readdir()` 的顺序：目录顺序会随一次重写变，一秒刷新一次的页面要是跟着变序，
  看起来就像网络在动。
- **放不下怎么办**：`detail` 上限就是写侧那个 `CONTROLLER_AP_BSS_MAX`（16）。满了以后**总数照旧全加，行只留
  BSSID 最小的 16 个**——反过来做的话，页面那个数会因为一行放不下而变小，那是批 8 一开始要避免的同一类错。
- **服务侧**：每个节点多一个 `"bss_detail":[{bssid, stations, age}]`。缓冲区从 16 KiB 放到 32 KiB，每节点的
  预留从 1200 提到 2400（16 行约 1 KiB），**能列出的节点数没掉**（两种算法都是 13 个）。
- **页面**：「终端数」那一格的悬停改成一行一路 —— `02:00:00:00:19:e3: 3 (5 s ago)`，最后仍跟着原来那句
  `2 BSS reported by the router`。格子里还是总数：一行一路的列要再加一列，得连着表单与翻译一起动，这一项不做。
  拼串只用 BSSID 和已有的 `_('%d s ago')`，所以 `python tests/test_i18n.py` 的 12 项一条没改仍绿。

测试：`controller-peer-codec` **103 → 162** 项，新加的两段是"两路时 `detail` 就是那两行、升序、年龄对得上"和
"**二十路**时 `entries=20 / listed=16 / stations=210`，留下的是最小的那 16 个 BSSID"——后者是先按从大到小的
BSSID 造文件，逼着 `readdir()` 顺序和期望顺序相反，排序那条才有意义。`node tests/test_luci.js` 加一条**整串**
悬停断言（不是只查 BSSID 出现，而是查"BSS 数那句 + 两行明细"的完整顺序），外加"没有指标的节点不该有悬停"。

一个只在编译期露脸的坑：新用例给 `write_stray()` 传一个 64 字节的 `name`，`char path[300]` 立刻被
`-Werror=format-truncation` 判成可能截断（`peers` 255 + `/` + 名字 63）。以前传的都是字符串字面量，长度可证，
所以没报——**测试自己的缓冲区也是缓冲区**，`path` 放到 512。

`make test-host` 其余项不回归（`test_schema.py` 仍缺 `out/analysis/cspd` 那 4 项，与本项无关），ARM32 的
`out/db-engine-probe` 与 `libzte_controller_trace.so` 都重编过。`sh tests/test_rpcd.sh` 不涉及这些字段（它只走
`actions`），故未列入验收。

**没做的事**：逐路的列上页（一列一路，要动表单 + 翻译）、每 AP 的**终端列表**（帧里只有数目，没有"是谁"）、
`PKG_RELEASE`、CI 与运行包重打（连着批 7、批 8 一起）。真机那一半还是 **H-13**：实验室的 peer 只有 `:e3` 一路，

## 批末 · 把三个批次的 C 改动装进随包的 tarball

批 7（`0xd4` 软件版本）、批 8（逐路 `.sta`）、批 9（`bss_detail`）都只写了源码与主机测试，
`openwrt/zte-mesh/zte-mesh-runtime.tar.gz` 一直停在批 6。这不是"晚一点再打包"的整洁问题：CI 直接吃仓库里
那份 tarball，所以装到设备上的**控制器**根本没有这三批的行为，而**页面**（apk 里的 JS）却已经在读
`bss_detail`。错法还不是崩，是回落到摘要——数字照样动，看着像"这台子路由就是一帧列全"，正好把 H-13 要区分
的两种情况抹平。C6 记下过一次同样的事故（`ns-run` 与 init 不同步），这次是它的第二类。

做的顺序，以及每条为什么这样判：

1. **先证明"实验虚拟机编出来的就是 main 编出来的"**：32 个参与 ARM 构建的 `.c/.h` 加 11 个非源码前置
   （`.def`、`startup-views.inc`、`vendor-db.h`、`Makefile`）逐个 md5 与本机比，全等。不做这一步，
   "重打"可能把 ubuntu 那份快照里的旧文件打进包。
2. **重编两个成员**：`out/db-engine-probe`（ARM32，`-nostdlib` 对原厂 glibc）与
   `out/runtime/lib/libzte_controller_trace.so`。取回本机逐字节核 sha256。
3. **只换成员**：`python openwrt/repack-runtime.py --replace root/bin/db-engine-probe=… root/lib/libzte_controller_trace.so=…`
   —— **两个替换项跟在同一个 `--replace` 后面**。第一次写成两个 `--replace`，argparse 的 `store` 语义让前一个
   整条作废，打印出来只有 `replaced=['root/lib/…']` 才发现；LAB.md 3.0 早就把这条列为坑 1，还是踩了。
   **判据看脚本打印的 `replaced=[…]`，不是看它退出 0。**
4. **逐成员比**：52 → 52 个成员、顺序不变，只有这三个变——两个替换项 + `SHA256SUMS`。
   `SHA256SUMS` 的 41 行与成员字节逐条对得上（格式是 `hash␣␣name`，按 `name→hash` 建索引，反了就报全表不匹配）。
   这一步一开始想用"两份都解出来再 `diff -r`"，在 Windows 上行不通：归档里 `root/var/tmp`、`root/var/run`、
   `root/var/log` 是指向 `/tmp` 的符号链接，Git Bash 的 tar 建不出链接，就**把 `/tmp` 指的东西整个拷进解出来的
   树**——补测时在 `out/` 里复现了一次，落下 6.8 GB，全是本机临时目录当时的副本，连 `tmp.XXXX/controller-trace.c`
   这种 10 月留下的旧目录也照搬，看着像"随包带了源码副本"（包里根本没有那个成员，`tar tvzf` 照出的只是
   `lrwxrwxrwx`）。方向是**归档 → 工作区**，不是往本机临时目录穿写：往这份副本里写文件，本机临时目录不增多，
   所以它是副本不是别名，删它不伤本机（但 `rm -rf` 要递归几 GB，还有个目录会 `Device or resource busy`）。
   逐成员比字节才对，已记进 LAB.md 3.0 的坑 3。
5. **补 `repack` 跳过的那道审计**：`make-runtime.py` 打包前跑 `vendor_elf.audit()`，`repack-runtime.py` 不跑。
   对成品补跑，36 个对象：`missing_strong_symbols=0`、`missing_versions=0`。**这里有个假故障**：第一次按归档成员名
   （`root/lib/libc.so.6`）建索引，`audit()` 拿 SONAME（`libc.so.6`）找提供者，于是每个版本需求都"找不到"，
   报出 50 条缺符号——不是包的毛病，是我 harness 的键错。`make-runtime.py` 用 `Path(n).name`，跟着它才对。
   批 8 那个 `__fxstat` 替身正好是这类要盯的引用，审计通过说明原厂 `libc.so.6` 供得起；`nm -u` 查 `__time64` /
   `__isoc23_` 两个产物各 0 处。
6. **让下一次不再靠记得**：`tests/test_runtime.py` 加两条哨兵——probe 必须含 `bss_detail`（批 9 的 JSON 字段名），
   trace `.so` 必须含写侧才有的文件名格式 `.%02x:%02x:%02x:%02x:%02x:%02x.sta`。旧包这两处都是 0 次命中、新包都是
   1 次，所以哨兵真会失败，不是永真。为什么不能用哈希比：装机读回时 apk 会剥 ELF 节（PLAN C10 记过，设备上
   `.so` 16 484 B vs 包内 21 372 B），只能按字符串认。
7. **`PKG_RELEASE`**：`zte-mesh` 16 → 17、`luci-app-zte-mesh` 8 → 9（批 9 改了 JS），launcher 不动。
   不加这一位，装机读回 `0.1.0-r16` 就分不清装的是哪一批——上一轮 CI 就是这么点错 ref 才发现的。

`python tests/test_runtime.py` 29 条全过；`sh tests/test_init.sh` 122、`test_verify_install.sh` 60 不受影响。
文档同步：LAB.md 3.0 补两个坑（第 5 步那个索引键、第 4 步的 Windows 解包穿写；守卫条数 9 → 29）、
DEVELOPMENT.md 指回它、INSTALL.md 的版本号那行、FEATURE_STATUS C6 记下这次复发、PLAN 状态速览批 7/8/9
三行与 A22 尾巴。

**还没做**：CI 与装机。r17 的 apk 还没构建过，所以"哨兵过了"只证明**仓库里这份包**是对的，不证明设备上跑的是它
——那要 `ci/batch9` 触发一次 `build-apk.yml`、装两台、按 `PKG_RELEASE=r17` 与 `.so` 里的 `.sta` 标记读回。

## 批 10 · B8b：子节点的种子改从空中读回——重启不再把名字翻两次

上面 C8 那节记下的现象（**每次重启服务，空中名字翻两次**）今天修掉。

**为什么会翻**（链条是 `init write_config` → `/run/zte-mesh/config` → 原厂守护进程的 `WLANCfg`/`WLANPSK` 行 →
`agent-sync` 发 `/run/zte-mesh/wlan-plan` → `wlan-sync` 写 `/etc/config/wireless` → `uci commit` + `wifi reload`）。
子角色的服务配置里，2.4G 的名称/密钥/加密取的是页面上那三项（ax3600 装完就是 `ImmortalWrt` / `labbpass123` / sae-mixed），
而空中此时已经是主控下发的 `FRESHR10` / `FRESHR10-5G`。种子 ≠ 空中，于是重启一次要挨两下：
守护进程一起来就把空中改成种子（日志那行 `name set to 11 characters` 就是这一下），`wlan-sync` 拿着同一份种子也要
改名、`commit`、`reload`——**`wifi reload` 是全局的**，一个频段上一次空写就把两个频段的终端一起踢掉；约 21 秒后 M2 到，
档案换成主控的，再翻一次。所以判据不能是"少改一次名字"，得是**一次写入都不发生**。

**四处改动**：

1. `live_ap_iface`（`zte-mesh.init`）。借哪一段这件事必须和 `wlan-sync` 用的是**同一条解析**：点名 `wifi_2g`/`wifi_5g`
   优先、只有一个候选就用它、只有一个活着就用它，`wifi-iface` 侧跳过 `zte_backhaul_*`、跳过 `mode != ap`、跳过
   `multi_ap=2`、优先 `default_*`。两边指到不同的段，读回来的种子就护不住要被改的那一段——比翻两次更糟，是"读了 A 改了 B"。
2. **广播已关的射频不借**。ax3600 那块 PCIe 空卡（`radio0`）就是现成的反例：`disabled=1` 却还挂着 `ZTEMESHCTRL` /
   `00000000`。借它当种子等于把工厂测试名写回空中；而且 applier 遇到 plan 里 `enabled=1` 会 `enable_radio`，那又是一次
   全量 reload。测试里专门数了配置里 `ZTEMESHCTRL` 出现的次数，必须是 0。
3. `set_flag`（`wlan-sync`）。UCI 里 `disabled` / `hidden` **没写过就等于 0**，按拼写比就要"补一个 0"，
   那还是一次写、一次 commit、一次 reload。改成按含义比（`uci_true` 之后相同就不动）。
4. `wifi_dual_band_sync` 从"页面写什么就是什么"改成"**空中是什么就是什么**"：两个频段的名称/密钥/隐藏/加密全一致才写 1，
   否则写 0 并把 5G 逐字段写全——守护进程在 sync=1 时是按 2.4G 派生 5G 的，派错就得改名。
   只借到 2.4G（5G 读不出）且页面声明同步时，5G 那一行的 hidden/加密跟着 2.4G 的种子走。

**证据**：

- `sh tests/test_init.sh` **122 → 130**、`sh tests/test_wlan_sync.sh` **169 → 182**；两份都在 owrt 的 busybox ash 上跑过
  （130/182 全绿）。Windows 这边跑不完不是代码问题：wlan-sync 那套 53 次调用，Git Bash 上单次实测 1.5 秒——HEAD 版本
  同样超 120 秒。**这类 shell 套件去 ubuntu 或 owrt 跑**。
- 反证留在测试里：把种子改一个字符，就必须 `commit`。所以 `changed=0` 不是"什么都没测出来"。
- **ax3600 上的配置面**（不碰射频的那一半）：仓库版的 `zte-mesh.init` / `wlan-sync` 放 `/tmp`，`/etc/config/wireless`
  拷成 `/tmp/b17etc/wireless`，`wifi` 换成桩。新种子与真配置逐字段相同，`wlan-sync --once` 报
  `result=ok changed=0 bands=`，副本与真文件 md5 一致（`59094b96b83f8f74655f5268b95be2be`），桩 `wifi` 一次没跑。
  同一台机器上装着的 r17 写的是 `radio0.ssid=ImmortalWrt` / `key=labbpass123` / `beacon_type=12`——那才是翻两次的源头。

## 批 11 · C11：把"这一次重启写了几次无线"变成一个数——H-14 剩一条命令

批 10 收在"配置面证到了、真重启没证"，而 H-14 的判据当时是**人读 `logread` 数行数**。当天就撞过的坑在这里更容易
重演：C10 那个假 FAIL 的根因是"问得太早"，而真重启之后本来就要等收敛（子节点等主控 M2 那一路约 21 秒），并且
**文件前后一模一样**——旧种子先把空中改名、M2 再翻回来，`/etc/config/wireless` 的 md5 分不出"一次没动"和"动了两次"。
所以这一批不写新逻辑，只把那句判据做成脚本里的一个数。

**三个设计点，每个都是"另一种说谎的方式"**：

1. **数日志，不比文件**。窗口就是脚本自己要求的那次重启，数的是 applier 自己那行
   `applied; wireless committed` 的**增量**（`BEFORE_WRITES` 在 `restart_services` 里、重启之前取）。
2. **判 `0` 要有前提**：重启前先读一次"空中是否已经带着 plan 里每个启用行的名字"（`air_matched_plan`）。
   是，才把 `applier_writes=0` 当判据；不是（刚装完、还在收敛），只报数不判——把一次正常收敛说成故障，就是
   C10 那个假 FAIL 的重演。
3. **四种形状不算故障**：这一趟没重启 `no-restart`、这个角色本来没有 applier `no-applier`（纯主控）、
   `logread` 读不出来 `no-logread`、日志环在窗口里翻了圈 `wrapped`。

`RESTART_NOW=1` 让**不装机也能驱动这一次重启**，这就是 H-14 的执行入口：
`rssh.py ax3600 put tools/lab/verify-install.sh /tmp/` 然后 `RESTART_NOW=1 sh /tmp/verify-install.sh`。
它会让 ax3600 上的终端真掉线（哪怕什么都没装），所以默认关着。

**测试 85 → 108 条**，七个新断言组：安静重启 PASS、`writes=2` 必须 `FAIL applier_writes expected=0 got=2` 且
`RESULT=FAIL`、收敛中只报不判（`air_matched_plan=rows-unset:0` 且不出现 FAIL 行）、纯主控 `no-applier` 且不打印
`air_matched_plan`、没重启 `no-restart`、读不到日志 `no-logread`、窗口翻圈 `wrapped`。`zte-mesh` 的 init 桩现在会
按 `$FIX/writes` 往日志里长那几行，也能按 `$FIX/wrapped` 整份换掉日志——后一个是为了让 `wrapped` 那条测得到。

**我自己的三处**：

1. 一开始把 `BEFORE_AIR=$(air_carries_plan)` 放在主流程顶部。那里面要跑 `ssid_where`，也就是**多一次
   `uci show wireless`**——case 12 那个"第三次 `show` 才返回新名字"的计数桩整个错位，`ssid_wait` 从 2 变 0，
   101 passed / 1 failed。把它移进 `restart_services`：**不要求重启，就一次机器读都不做**。
   新增的采集必须待在它自己的触发条件里，顶上那句"顺手先读一下"是把别的时间段的判据拖进本次窗口。
2. `grep -c` 在日志读不出来时答 **0**，而 `0 - 0` 恰好长得像一次安静重启——这条不是补 `if` 就完事，得先让
   `logread` 失败可分辨（`logread_readable`）。桩本身也要讲这个语义：`[ -f $FIX/log ] && cat $FIX/log` 作为脚本
   最后一行，文件不存在时就是 rc=1，`no-logread` 才测得出来。
3. 日志环翻圈时 `after < before`，我没有把它写成"负数"，而是 `wrapped`：**被截断的窗口不是个数**。
   窗口里的数不可信时，报一个形状比报一个数是诚实的。

**设备上的读回（只读，两台都没重启任何东西）**：`RESTART_NOW` 没设、没给 apk 目录，owrt `RESULT=PASS`（11 项）、
ax3600 `RESULT=PASS`（11 项），两台都打 `applier_writes=no-restart`；ax3600 的两条 SSID 仍跟着主控
（`plan_ssid_0=FRESHR10@default_radio2`、`plan_ssid_1=FRESHR10-5G@default_radio1`、`ssid_wait=0`）。

## 批 12 · B16：总账挂着"没做"，结案注写着"已结案"——缺的只是一条命令

`FEATURE_STATUS` 的 B16 那一行是 `⬜ / 实验室用 -2 顶替`，可**同一份文档末尾**有一条"B16 `CurHop` 已结案"，引的是
原厂 E2631 的实测（`CurHop=2=MaxHop`、`EnMasterOnly=0`）；而实验机上更早就读到过：`AGENT_PROBE` §13.7 那张"现在的
事实"表里写着 ax3600 `cur_hop=2 max_hop=2`（此前 `-2`）。**结论一直在，缺的是一条能重复跑的判据**，所以总账不敢改。
这一批就是补判据，不是补功能。

**为什么 `-2` 之外都算更新**：子角色那三支（`Mode=1`、`SetRoleEnable=0`、`EnMasterOnly=0`）里，`CurHop` 只有我们
启动路径写一次 `-2`；换角色时往子节点方向写的还是 `-2`，往主控方向才写 `2`。所以一台跑着的子节点读到别的值，
只能是那颗原厂守护进程写的——`slave_init` 的 `CfMultiapSetCurHop`，或者采用主控 TLV `0x43` 下发的值
（[FINDINGS](../FINDINGS.md) 第 7 节的两条路径）。主控那一列本来就是我们自己写的（`multiap-cfg.c` 那张表里
`CurHop=2`），**所以只在子角色判**。

**先写错了一次，才知道哪一窗才是可判的**：第一版把 `cur_hop` 也做成"重启前捕获、重启后读增量"那一套（`BEFORE_CFG`
加一个 `log-before` 的桩 fixture）。思路是照抄 `applier_writes`。但它数的不是**增量**而是**最新一行**：
owrt 的环里每个守护进程生命周期只有一行 cfg（相隔几分钟），一次 procd 重启会换掉写这行的进程，新进程那行基线快照
**可能落在我们读之后**——重启窗口里读到的可能是旧的，也可能什么都没有。更要紧的是"刚装完就重启"那一档：那时
`-2` 是合法状态（守护进程还没来得及更新），拿它判 FAIL 就是 C10 那个假 FAIL 换个栏目重演。
于是整套机械撤掉（`BEFORE_CFG`、`log-before` 的 fixture、init 桩里那句 `rm` 全删），改成一句判据：
**这一趟重启过服务就不判 `cur_hop`**，稳态只读机器自己的最新一行。

**不判的形状**：`no-cfg-line`（环里没有那一行）、`-98`（守护进程自己读不到那一列，不是跳数）、刚重启过、主控角色。

**两台实验机的读数（只读，什么都没重启）**：owrt（master）打 `cur_hop=2`，**不进计数**——那一列是我们自己写的，
`pass=11` 与加这一条之前相同；ax3600（slave）打 `cur_hop=no-cfg-line`。这台早上还看得见那一行：

```
Tue Nov  3 10:41:47 2026 daemon.info ns-run[5489]: ZTE_MESH_SERVICE cfg mode=1 set_role_enable=0 en_master_only=0 cur_hop=2 max_hop=2 epoch=1793673707
```

到中午环里只剩两行 `agent_election`，cfg 那行**被翻出去了**（环 1054 行）。所以这条读数的诚实定位是
**"环里有就判"的读数**，不是"随时可判"的——判据结案用的是今天还在的那一行（`mode=1` 正是子角色那三支，
而 `-2` 是我们写的），复验归到 H-14 的真重启窗口里去。

**还分不开的一种**：实验台上主控的 `CurHop` 与本机 `MaxHop` 都是 2，"slave_init 设成 MaxHop"与"采用主控下发的值"
读数相同。要分开得让主控那侧不等于子节点的 `MaxHop`，也就是改 `multiap-cfg.c` 那张表的取值——**登记成 H-14 的第 ⑦ 步**，
跟真重启窗口一起做，别单开一个窗口。

**测试 108 → 124 条**：健康子节点 `cur_hop=2` 算一条断言；`-2` 必须打
