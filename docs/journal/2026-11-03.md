## 批 5 · A22 的"日志轮转"：量完发现要修的不是轮转

PLAN 第 2 节把 A22 的尾巴写成"日志轮转"。先查它到底轮转什么，结论是**这个服务没有会无界增长的文件**，
所以"轮转"是个假问题；真问题是**一次配置推送把设备日志环占满**。两件事都不是靠读代码看出来的，是量出来的。

**文件这一半（负结果，但要留）**：沙箱根是 `MS_RDONLY` bind，写不进去；`/tmp` 与 `/var/tmp` 是
`size=8m` 的 tmpfs，`/dev/shm` `size=1m`；服务自己写的只有 `/run/zte-mesh` 下那几样（配置、`state.json`、
`actions/`、`peers/`），全是小文件原子替换。`ns-run.c` 的挂载表逐条对过，没有第三个日志文件。
所以唯一的落点是 **logd 的环**：两台实验机都是 `system.@system[0].log_size='128'`（KiB），
`logread` 当下 1179 行——"约一千行"不是估计，是现在能读到的数。

**挤占是真的**：一次真子路由配置推送里，原厂 daemon 自己重复打了 **1012 行**（`acdc current state[N]:…` 与
`WLAN_ASSERT_RET …` 两种格式，7 分钟内），比整圈环还多；四小时后回看，`logread` 里 94.5% 仍是这两行。
也就是说用户想看的东西（入网、封禁、告警）被自己控制器的状态轮询挤掉了，而**这一路原来挂在火管那 2 万行的预算上，
打光了也不吭声**——`ZTE_TRACE_VALUE` 与 `ZTE_TRACE_ALL` 共用一个计数，且没有 exhausted 提示。

**改法（`controller-log.c`/`.h`，新的可主机测的接缝，同 A21 的做法）**：

| 类别 | 预算 | 说明 |
|---|---|---|
| ordinary / protocol / device / renew | 160 / 64 / 48 / 48 | 沿用原来的每进程预算；前两个打光各发一条提示 |
| value | 20000 | 四条**一次性**证据行（`cfgChg`、`WSC-%d will cfg`、`M2 total Length`、`mesh sync for M2`），逐条打，不采样 |
| **poll（新）** | **每 60 秒 4 行** | 两条重复行改打 `ZTE_TRACE_POLL`，按 `CLOCK_MONOTONIC` 的分钟采样，每个超额的窗口发一条 `log_budget=poll sampled=1 limit=4 window=60s` |
| firehose | 20000 | `/run/zte-mesh/trace-all` 打开时才有；预算归进同一个 gate，不再由 `controller-trace.c` 自己数 |

三个决定值得记：

1. **判据读的是格式文本，不是值**——值行打印的是 daemon 已经格式化好的结果，所以带密钥/SSID/BSS 的格式
   （`PWKey`、`WEP`、`BeaconType`、`PSK`、`Bss`、`WLANCFG`…）在 `controller_log_shape()` 里**先否决**，
   永不展开。这条顺序是测试点：`"Bss current state[%d]"` 必须返回 -1，即使它也匹配 poll。
2. **时钟由调用方传进来**（`long now`），gate 也是调用方拥有的 `struct log_gate`。这不是风格：`controller-actions.c`
   踩过"用 `time(NULL)` 判到期、实际拿的是 `CLOCK_MONOTONIC`"的时钟域坑，所以这里 preload 侧取 `CLOCK_MONOTONIC`，
   测试侧自己造时钟，倒退的时钟、跨分钟、连续 60 分钟都是能喂的输入。
3. **提示语本身要能被读出来**：三条提示都是固定串，且 `controller_log_class(notice)` 落在 ordinary——
   读者要能分清"没发生"和"日志不说了"。同一句写在 `controller-log.h` 的注释里。

一次推送从 **1012 行 → 28 行 + 7 条说明**（测试里就是这么断言的：`kept*25 < 1012`、`kept+notices < 40`）。

**测试**：`tests/controller-log-codec.c`，`make test-host` 里跑，**655 649 项断言**（含 2^17 次有界变异：
随机改 11 条种子格式，断言类别/形状永远在集合内、被放行行绝不带提示、每类不超预算、ordinary 真的打满 160、
poll 在很多窗口里真的还在流）。三条 fixture 写错、当场改掉，都不是代码问题：
喂 145 行时 `step=1` 会跨两个 60 秒窗口（"7 窗口 28 行"的算术就崩），renew/device 只喂 40 行却断言等于 48 的预算，
`strncmp` 提示前缀的宽度写成 34（真实长度 32）。

`memcpy`/`snprintf`（`tools/lab/build.sh` 显式关掉 fortify），**没有比原厂 glibc 2.26 更新的引用**——
逐个符号拿包里那份 `root/lib/libc.so.6` 验过都能解析（`clock_gettime@@GLIBC_2.17` 是 weak T）。

## 批 5 · 当天就补的尾巴：采样说明要报出丢了几个

装机读数里最有用的一条不是"上限守住了"，而是**它没告诉我守掉了多少**。四个窗口各 4 行、各一句
`log_budget=poll sampled=1 limit=4 window=60s`——`4 留 5 丢` 和 `4 留 1000 丢` 在日志里长得一模一样，
而这两种情况对读日志的人是不同的故事：前者无所谓，后者正是这次要防的挤占。所以 `gate` 里加一个累计计数，
说明改成 `… window=60s dropped_total=N`。

三个决定：

1. **数的是累计，不是本窗口**。一句说明只能在它被打印的那一刻写；本窗口还没过完，写"这一分钟丢了 X"必然是假的。
   累计数不用解释这一点：相邻两句之差恰好是**上一个**窗口丢的（第一句打在第一条被丢的行上，误差自己抵消），
   最后一句之后还在涨——所以它是下界，不是总量。这条写在 `controller-log.h` 的注释里，测试按它断言。
2. **提示文本仍然只由 gate 生成**，数字除外。原来的"三条固定串"变成"两条固定串 + 一条固定句式带一个数"：
   值行打印的是 daemon 格式化好的结果，那才是绝不能掺进去的东西，采样计数是我们自己的数。
   代价是 `*notice` 从"指向静态串"变成"指向 gate 里的缓冲区（到下一次 admit 为止有效）"，
   `emit_line()` 本来就是拿到就写，契约写在头文件注释里。
3. **`snprintf` 进 preload 前查过 ABI**：重编后的 ARM32 shim 新增引用只有 `snprintf@GLIBC_2.4`，
   远低于原厂 glibc 2.26（`tools/lab/build.sh` 关掉 fortify，所以不是 `__snprintf_chk`）。

主机测试多一条规则 `test_the_notice_reports_what_it_dropped`：七分钟 ×145 行的那一次推送，
第一句必须是 1、之后每句比上一句大 141（145−4）、总共七句、末句 847 且小于全轮丢弃数 987；
不满上限的窗口一句都不发。**655 671 项断言**（比上一版多 22）。换包走 LAB 3.0：逐成员 diff 只有
`root/lib/libzte_controller_trace.so`（21 372→21 376）和 `SHA256SUMS` 变了，`tests/test_runtime.py` 0 失败。

**没做的事**：`PKG_RELEASE` 不动——这次改的 `.so` 要装机才有意义，加号留到下一次批末 CI 一起；
`log_budget=ordinary` 与 `log_budget=packet` 两句也不加计数，它们一个进程只说一句，说了也读不到差值。

## 批 7 · A18c：拓扑页的软件版本那一格，为什么一直是空的

装机复验时页面上唯一还写着 `-` 的常用列就是软件版本。`nodes[].software` 取自
`IGD.P1905DeviceInfo` 的 `SoftwareVer`，而这张表在真子路由上是空的——所以先别改页面，先查这一列到底
有没有人往里写。全部结论是 [代码]：`out/vendor/root/bin/multiapd` 反汇编，地址用
`arm-linux-gnueabi-nm -n` 逐个核过。

四个环节，一条链：

1. **发送侧发**：`ApCapabilityReportSend @0x58470` 里 `movw r1, #0x8002`（`0x584e8`）是 AP Capability
   Report，`0x58668` 调 `I5TlvDeviceInventoryTypeInsert @0x501e0`，库存材料来自 `slave_get_global_data`。
   也就是**版本串确实上线了**，就在 0x8002 的厂商 TLV `0xd4` 里。
2. **接收侧收**：`ApCapabilityReportReceive @0x41f80` 在 `0x42068` 调 `I5TlvDeviceInventoryTypeExtract
   @0x3d674`。这个函数按 `[长度1 文本]` 连读三段，依次写进设备记录 `+312` 序列号、`+247` 软件版本、
   `+377` 硬件版本；`I5TlvExtractChildlv @0x68764` 里 `cmpls r2, #64`——超过 64 字节**不拷贝但照样跨过去**，
   后面的字段才保得住位置。
3. **但它不入库**：`IGD.P1905DeviceInfo` 唯一的写手 `topoAdd1905DevInfoToDB @0x8e37c` 只取 `+24`（MAC）、
   `+60`、`+124`、`+584`。`+247` 全仓库只有厂商 CLI `master_print_devinfo_list @0x23348` 读过。
   **`SoftwareVer` 从来没有被从线上解出来过**——页面空不是抓包没抓到，是原厂根本没写。
4. **旧猜测作废**：REPLAY_RESULTS 里写过"HLR 的厂商 TLV 里有 `V1.0.0.2B2.8000`"。顺着
   `I5TlvHigherLayerVendorTypeExtract @0x981f8` → `I5TlvVonderDevIdenExtExtract @0x6888c` →
   `I5TlvCoverStructToDevice @0x96010` 走一遍，落点是 `+520/+584/+392/+60/+124/+648/+456/+784` 和两个 u32，
   **没有一个 `+247`**；本地 15 个 pcap 也搜不到 `V1.0.0`。这条猜想去掉，换成上面这条有地址的链。

做法上只补数据通路，页面一行不动（`zte-mesh.js` 早就在渲染 `node.software || '-'`）：

- `controller-1905.c` 加 `device_inventory_software()`：跳过序列号取第二段，空、>64、含 `' '` 以下或 0x7f
  一律当"没说"。
- `controller-peer.c` 只在 CMDU **就是 0x8002** 时认这个号码——`0xd4` 在别的消息类型里是别的字段。落成
  独立的 `peers/<MAC>.software`：版本不是数字，不能塞进 metrics 那个 `key=value` 摘要里。
- `controller-service.c` 加 `read_peer_text()`，只在数据库那一列为空时用它填 `state.json`。**数据库里有值
  的行优先**：主控自己那一行本来就填得好好的，不该被一帧覆盖。

一个真踩到的坑：第一版是"先 `memcpy` 进 `out`，再校验 `out` 这个 C 字符串"。于是
`'V' 0x00 '1'` 这种带内嵌 NUL 的字段返回了成功，页面上会显示一个凭空的 `"V"`。改成把
指针和长度交给调用方、**校验原始字节后再拷贝**，所有拒绝路径都留 `out[0]=0`。

主机测试：`controller-1905-codec` 从 101 断言涨到 **192**（整段、每一刀截断、空字段、控制字节、
64/65 边界、小缓冲区截断 + 围栏字节，末尾还对整段做了逐刀扫，10 万次有界变异不变量守住）；
`controller-peer-codec` **71 项**（版本单独一个文件、同号码在别的消息类型里不落盘、没有清单的 capability
report 不落盘、空版本不覆盖已有文件、最新一版赢且只有报的那台变）。`out/db-engine-probe` ARM32 链接过、
`controller-service.c` 单独 `-Wall -Wextra -Werror -fsyntax-only` 过。

**没做的事**：`PKG_RELEASE` 不动、CI 不触发——这一批只有一项，跟下一次批末一起走。真机那一半登记成
**H-12**：这颗 Z506 到底发不发 `0xd4`、字段顺序是否与这份二进制一致，都得抓 0x8002 看；负结果也算数，
那说明得另找来源。

## 批 8 · A18d：终端数按 BSSID 记账——摘要文件是"最后一帧说了算"

批 2 落下的 `peers/<MAC>.metrics` 是一份 `key=value` 摘要，**每帧整份重写**。这在"一帧报全部"的
假设下没问题，但子节点是可以**按射频分别回 `0x800c` AP Metrics** 的：2.4G 一帧、5G 一帧，页面就在
两个数字之间来回换；夹一条只带 `0x83`（BSS 数）的帧，重写出来的摘要里根本没有 `stations=` 这一行，
服务读成 -1，页面上那一格直接空掉。数字没错，错的是"谁最后到谁说了算"。

先把范围定死：**这次不动页面**。`state.json` 里一个节点一个 `stations`，逐路的明细没有格子放，
要加就得连着 rpcd、LuCI、i18n 一起改；那不在这一项里。要做的是让**求和的对象**从"最后一帧"变成
"每一路各自的新鲜度"。

- `controller-1905.c` 加 `ap_metrics_by_bss()`：把一帧里的 `0x94` 逐条解成 `{BSSID, 终端数}`，按
  帧里的顺序返回。**唯一一条设计上的硬规矩**：同一个 BSSID 出现两次、或路数超过
  `CONTROLLER_AP_BSS_MAX`（16），一律返回 0，不给部分列表。半份列表加起来是一个偏小的数，而偏小的数
  和没测出来的数在页面上长得一样——这种"看起来像测量"的错不能留。
- `controller-peer.c` 每路落一个 `peers/<MAC>.<BSSID>.sta`，里面只有一个数字一行。每路**各自的时间戳**
  是关键：一路停止上报只让它自己的文件过期，别的几路照旧。摘要照旧写，作为拆不开时的回落。
- 读侧 `controller_peer_bss_load(mac, max_age, &load)` 遍历目录，把没过期（默认 30 秒）的条目加起来，
  `load.entries` 是几路、`load.age` 是其中最老的一路。目录是 root 可写的 tmpfs，文件名和文本都不信：
  两段 MAC 反着写、尾巴多一个字符、值不是数字、大于 0xffff（线上是 u16）都不算一条。
- `controller-service.c` 里 `stations` 改成先取这个和，取不到才用摘要——老设备写出来的
  `<MAC>.stations`（r10 及更早）那一路兜底也留着。

两个真踩到的坑：

1. **测试之间共用同一个目录**。`.sta` 的名字前缀还是 MAC，`two_children()` 那句
   `distinct_macs() == 2` 把新的文件当成新节点，报在 213 行。加了一个 `clear_peers()`，
   `stations_are_per_bss()` 开头清一次、结尾再清一次——它读别人的状态，但不给后面留自己的。
2. **ARM32 链接不过**：`fstat` undefined。原厂那套 glibc 2.26 只导出带版本的入口，
   `controller-service.c` 早写了 `__fxstat(3, ...)` 替身，但 `controller-peer.c` 同时要在主机上编
   （主机测试跑的就是它），所以替身用 `#if defined(__arm__)` 关住，主机仍走真 `fstat`。
   `libzte_controller_trace.so` 也链这个文件，两处一起重编才敢说链接是绿的。

主机测试：`controller-1905-codec` **192 → 212** 断言（两路保序、带"估计服务时长"的 20 字节 TLV、
0 终端是真条目不是缺项、没有 metrics TLV、8 字节残帧、切在计数中间、重复 BSSID、`max` 比路数小、
`max=0`/`NULL`）；`controller-peer-codec` **71 → 103** 项（空目录不等于 0、一帧两路落三个文件、
单射频帧后摘要变小而总和仍是两边、单独让一路过期、条目属于报它的这台、重复 BSSID 不落 per-BSS、
三种坏文件都不读、手写一条合法的能读）。`make test-host` 其余项不回归，ARM32 的 `out/db-engine-probe`
与 trace 库都重编过；`test_schema.py` 那 4 项还是缺 `out/analysis/cspd`，与这次改动无关。

**没做的事**：逐路明细上页（要动 `state.json` 结构 + rpcd + LuCI + i18n）、`PKG_RELEASE`、CI——
都跟下一次批末一起走。**批末记得 `sh tools/build/runtime.sh install` 重打运行包**：CI 用的
`openwrt/zte-mesh/zte-mesh-runtime.tar.gz` 是随仓库提交的那份，批 7 与批 8 的 C 改动都还没进包。
真机那一半登记成 **H-13**：这颗子路由到底一帧列全所有 BSS，还是一射频一帧，
实验台那份抓包里连一帧 `0x800c` 都没有，只有真机上抓一次才知道逐路文件是"各自更新"还是"同时更新"。
两种都算通路成立，只是页面那个数的来源不同。
