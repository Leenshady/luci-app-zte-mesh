## 装机反馈两条：有线口会掉，`search` 会死；角色从三个名字拆成两个开关

**报上来的现象**：master 端长时间运行后，页面上的「有线接口」变成未接入，重启主控就恢复。这是用户描述，不是结论——
中间隔了多久、期间发生了什么，都得自己查。

**线的死法**：沙箱的入口 `veth-lab` 与宿主的 `zmesh0` 是一对 veth，删掉任一端两个一起消失。沙箱里没有 `/proc`、
没有 `/sys`、没有 `ip`、也没有 `CAP_NET_ADMIN`，daemon 又在 `bind()` 时把 ifindex 写死了——所以掉线之后**里面没有任何
办法重建这根线**，即使能建，已绑定的 socket 也还对着那个已经消失的 ifindex（`controller-route.c:49` 只在绑定时改写
br0→veth-lab）。用户"重启主控就好"不是巧合，那是唯一出路，只是以前得有人守着。

**修法（按用户定的口径：只改 host 侧 shell，不动 C）**：`attach` 本来就是唯一看着这根线的人，让它兼任看门狗——
`zmesh0` 与 `lab-peer` 连续 20 秒都不在，而沙箱进程还活着，就给它发 `SIGTERM`；ns-run 退出码 128+signo，procd 重新拉起，
新沙箱建出新线，同一个循环把它改名入桥。之后 60 秒冷却，不追着杀。选 shell 而不是 C 的实际收益：**不用重编 ARM32
二进制、不动 prebuilt 归档、不用跑 CI 就能装机验证**，代价是"发现问题的进程"和"重建线的进程"是两个。

**顺手挖出来的第二条**：核对 respawn 语义时发现 `search`（和 `wlan-sync`）写的是裸 `procd_set_param respawn`。
被中断那一轮的结论是"改成 `-1` 才是无限"，实测下来这条前提是错的：procd 把裸 `respawn` 填成 `3600 5 5`，
而 **retry=0 本身就是不限次**（ lab 上让一个进程 50 秒内退出 13 次，仍在拉起）。`search` 每 300 秒按设计退出一次，
5 次预算半小时烧完，日志 `crash loop 6 crashes, 300 seconds since last crash`，之后永久不再启动——晚开机的子路由
再也找不到主控。`zte-mesh status` 当时只剩 `running (2/3)`。所以真正要改的只有 `search` 和 `wlan-sync`
（`controller`/`attach` 早就写了 `3600 5 0`）。**教训：改之前先测一次语义，"文档里都这么写"不等于这台机的 procd 这么想。**

**角色的评估**：`main` 在 init 里发的是 `mesh.role=auto`，daemon 收到后写 `SetRoleEnable=1` + `Mode 0`，三秒后才由
`role_settle_at` 替身改成 `Mode 2`。沙箱里没有 cspd，这场"自适应选举"没有对手，替身走完只是白走；真正的风险是
**一台真的中兴子路由在那三秒里当选主控**，拓扑反过来。第三个名字还把两件不相干的事捆在一起：是不是主控、
要不要把配置写进本机无线。所以拆成两个开关：`mesh_role=master|slave` + `apply_local=0|1`，`main`/`auto` 作为
"master + apply_local=1" 的别名继续被读，线上从此只发 `master`/`slave`。C 侧的 `CONTROLLER_ROLE_AUTO` 分支与三秒
结算留着——升级前写好的 `/run/zte-mesh/config` 里可能还有 `auto`，而新配置永远走不到那条分支。

**顺带修的一处真 bug**：`restart.sig` 只记键名（`cut -d= -f1`），角色取值变化看不出差别，于是改角色不会重启服务，
procd 实例集合（`search`、`wlan-sync`）保持原样——正是"改了不生效，得手动重启"那一类。现在把两个决策的值也进签名。

**LuCI 侧**：`mesh_role` 只剩两个选项，多一个 `apply_local` 复选框（子路由不显示）。旧配置 `main`/`auto` 的显示与保存
都不会掉行为：复选框的 `default` 跟着别名走，存盘时写出 `master` + `apply_local=1`。rpcd `status` 现在返回两个轴
（`role` + `local`），页面标题由这两值决定。

**主机测试**：init 103 项（新增 `role-local-sig`、`role-slave-local-keeps-plan`、`role-main-local-off`、两个 legacy 别名、
respawn 预算与 attach 看门狗的判据）、rpcd 24 项（六个 role/apply 组合）、luci、i18n 全过。`test_wlan_sync.sh` 在本机
（Git Bash）跑不完，只在容器里算数。

**还缺的**：H-10（`ip link del zmesh0` 后自愈）、H-11（中兴原厂路由器在 `master` 下照样入网、且没有自当选）都要上机；
这两个是本轮唯一没被主机测试覆盖的部分。改动全在 shell / JS / po / 文档，没碰 C，所以不需要 CI 就能装机——但要装机
验证才谈得上"修好了"。

## 批 4：无线回程的另一半（B13a/B13b）——4 地址的开关是 `wds`，不是 `multi_ap`

**为什么先查这一步**：§11.6 写回程时只做了 AP 那部分，"仍缺"里挂着两条——"4addr 由 hostapd 依 `multi_ap` 去设，
真实路由器上要看"和"STA 那部分还没写"。这两条其实是一件事：如果不先在 netifd 侧搞清楚谁决定 4 地址，写出来的 STA 段
大概率是个连不上的配置。所以本轮第一件事不是写代码，是读装机的那份 ucode。

**实测（ax3600，ImmortalWrt 25.12，`/usr/share/ucode/wifi/`；VM 那台没有无线，`/lib/wifi` 都不存在）**：

- `supplicant.uc:83`——`case 'sta':` 里 `set_default(config, 'multi_ap_backhaul_sta', config.multi_ap)`。UCI 的
  `multi_ap` 在客户端被改名成 wpa_supplicant 的 `multi_ap_backhaul_sta`，它只决定**关联能不能被回程 BSS 接受**。
- `supplicant.uc:278-279`——接口挂着 bridge、`mode == 'sta'`、且 `wds` 和 `multi_ap` 都没有 → `BRIDGE_NOT_ALLOWED`，
  直接起不来。
- `supplicant.uc:305` / `:313-314`——**`'4addr': !!interface.config.wds`**，`config.bridge` 也只在 `wds` 时才写。
  4 地址和入桥都只认 `wds`，跟 `multi_ap` 一点关系没有。
- AP 侧不受这个影响：`ap.uc:58` 把 `multi_ap` 原样透传给 hostapd，回程 BSS 的 4 地址由 hostapd 自己在驱动里设。
  顺带 `ap.uc:224`：`multi_ap == 1` 会关掉 WPS——对我们没影响，但值得记着。

**所以回程 STA 一段要写两个选项**：`multi_ap 1`（让主控那个 `multi_ap=2` 的 BSS 接受它）+ `wds 1`（4 地址 + 入桥）。
这纠正了 §11.6 "4addr 跟 `multi_ap` 走"的推断——那条只在 AP 侧对。也意味着 H-01 的清单变短了：映射对不对主机测试就能
断言，真实路由器只剩端到端。**教训：推断来自哪一层要说清。** "hostapd 会依 multi_ap 设 4addr"是 hostapd 侧的事实，我把它
当成了整条链的事实，而 OpenWrt 这一侧真正动手的是 netifd。

**实现**：`wlan-sync` 加 `backhaul_side()`（读 `mesh_role`，`slave` → `sta`，其余 → `ap`）与 `apply_backhaul_sta()`
（段名 `zte_backhaul_sta_<band>`，`mode sta` + `multi_ap 1` + `wds 1`，名称/密钥/加密全取 plan 那行，**不写 `hidden`**
——隐藏是 AP 的概念，客户端没有广播）。同一条 `access&64` 的行现在按角色写成两端的某一段，`clear_backhaul` 因此加了
参数：换角色时把**对端**那段还回去（子节点上留一个回程 BSS、或主控上留一个回程客户端，都会在页面上显示成一条"链路正常"
的假象）。回程行"声称加密但 plan 里没有密钥"两端都拒绝应用——写下去就是一个永远连不上的 BSS/STA，不如不写。
`zte-mesh.init` 补了一条启动日志：`backhaul=multi_ap` 落在主控 + `apply_local=0` 上时这个开关无事可做，因为这台机根本不
本地落配置。`wpad-basic` 的告警扩到客户端（4 地址同样要完整 wpad）。

**踩的坑（记下来免得重犯）**：`set -u` 这一条本轮**撞了两次**，而且情况不同。

1. 把 `clear_backhaul` 改成带参数时写了 `local keep="$1"`，无参调用（回程关着的时候就是无参）当场炸
   `line 405: $1: unbound variable`，整段 apply 没跑——测试从 extra-slots 区块开始连片失败，**73 passed / 57 failed**。
2. `apply_backhaul_sta` 里 `local device iface main network enc`，而 `network` 只在"找得到主 BSS 且它有 network"那条
   分支里被赋值；找不到主 BSS 时读 `$network` 又是 `unbound variable`（`line 332`）。这一次更阴：脚本已经把
   `zte_backhaul_sta_2g` 的段建出来了才炸，所以配置写了一半、`commit` 与 `wifi reload` 根本没发生——真实路由器上表现成

## 批 4 收尾（B13d）：`backhaul` 这个开关原来只显示了一半

上一节登记的那条不一致，做法上只有两个选择：把字段限回子节点并解释清楚，或者让它跟角色真正对应。选了后者，理由和
`extra_slots`、`apply_local` 已经立过的规矩是同一个——**页面上只出现在"这个字段会动本机"的角色上**。回程是一条链路，
两端各由一个角色来建：

| 角色 | `backhaul=multi_ap` 在本机建什么 | 页面 |
|---|---|---|
| `slave` | `zte_backhaul_sta_<band>`：`mode sta` + `multi_ap 1` + `wds 1`，挂到该频段的桥 | 显示，标题"连回控制器" |
| `master` + `apply_local=1` | `zte_backhaul_<band>` 回程 BSS（`multi_ap 2`），主 SSID 标为前传 | 显示，标题"给子路由的回程网络" |
| `master` + `apply_local=0` | **什么都不建**（本机不动无线，也没有子节点来连它的本机广播接口） | 不显示 |

以前只有第一行有字段，第二行只能去 `zte-mesh.config` 手写 UCI；而 `apply_local=0` 的主控以前也看得到这个开关，设了
不会有动静（init 那条告警是这批加的）——所以这一改同时消掉两种误导。

**实现落点**（`luci-app-zte-mesh/htdocs/luci-static/resources/view/network/zte-mesh.js`，`backhaul` 那段）：条件从
`if (child)` 换成 `if (child || local)`，标题与描述都按角色给两份文案，描述里各自写清本端建的是客户端接口还是 BSS、
需要完整 wpad、以及对端没下发回程网络时不会创建东西。文案同步 `po/zh_Hans/zte-mesh.po`（旧的那条只讲"子路由如何回连"
却说建 BSS 的条目删掉，换成三条：新标题 + 两端各自描述）。`.lmo` 不入库，打包时生成。

**测试**：`tests/test_luci.js` 的角色分支要能同时看到 `mesh_role` 与 `apply_local` 两个轴，所以给 uci 桩加了 `uciLocal`，
断言三种组合——子节点（有 `backhaul`，无 `apply_local`）、旧名 `main`（现在**要求**有 `backhaul`，以前是禁止）、
`master` + `apply_local=0`（`backhaul` 与 `extra_slots` 都不出现，`apply_local` 自己在）。结果
`34 main / 10 slot / 4 ACL / 2 client / child 5`；`python tests/test_i18n.py` **12 项全过**（含每条新文案在 `.po` 里可查）。

**这一层的收获**：一个开关的可见性属于它的语义，不属于它的名字。`backhaul` 读起来像"子节点的事"，但它真正的条件是
"本机会不会因此动射频"——和 `extra_slots`（能应用配置的两端才给序号）、`apply_local`（只有主控才有意义）是同一条规则。
下次加字段先问这句，别按角色名硬套。

纯主控表单，而按新规矩纯主控就是少两个字段——那一遍改成渲染"会把配置写进本机的主控"，顺带把 `extra_slots` 也补进了
init 测试的"每个可选项都写一遍"用例。）

## 批 4 的最后一格（B13e/B13f）：`backhaul` 的取值，和"改了不生效"

接着上面那条线查下去，发现同一个选项还有两个更实在的问题，都在主机侧，都能测：

**一、取值没人管。** `wlan-sync` 的 `backhaul_mode()` 故意宽容——"认不出的就当 off"，这一条本身没错（应用侧不该因为
一个拼写就把整份配置停掉）。错在**没有任何地方告诉用户他写错了**：`multi-ap`（中兴自己文档里的写法，带连字符）、`on`
这种都会变成"页面开关是设过的、射频上什么都没有"。同类问题 `extra_slots` 早就在 `write_config` 里拒了，`backhaul` 漏了。
现在 `write_config` 只收 `off` / `multi_ap`，别的取值报 `backhaul must be off or multi_ap` 并不启动；空值按默认 `off` 收。

**二、改了不生效。** `reload_service` 只比 `restart.sig`，而签名以前只记 `role=` 与 `local=` 两个值 + 一批**键名**。
`backhaul` 既不加实例也不改 plan（回程那一行本来就在 plan 里，`MapAccessAttr&64`），它只改 `wlan-sync` 拿到**同一份
plan 时写什么**——而那个 watcher 只对 plan 的**内容摘要**起作用（`stamp()`，`md5sum`/`stat`/`ls -ln` 三选一）。于是
`off → multi_ap` 保存后什么都不发生，要等下一次别的原因引起的重启才生效。这正是用户报过的"改了没生效"那一类，
`mesh_role`/`apply_local` 上一批已经这么修过。

**做法**：签名按值带上 `backhaul=<取值>`，但**只带会跑 applier 的两个角色**——`slave`（客户端在这一端）与
`master + apply_local=1`（回程 BSS 在这一端）；`master + apply_local=0` 不带，因为在那个情况里这个值不起作用，
为一个不起作用的东西重启组网服务（子路由最长一分钟掉出拓扑）是白重启。这个判据在 procd 起 `wlan-sync` 实例的那一行的
条件里**本来就已经写过一遍**，现在抽成 `sync_runs ROLE APPLY_LOCAL`，两处共用——实例行在 `start_service()` 里，
这套主机测试跑不到它，所以加了三条对源码文本的断言，防止两处将来各写各的。

**再往下问一句"还有谁是这样的"**，就不止 `backhaul` 一项了。`wlan-sync` 直接从 UCI 读的一共四项：`backhaul`、
`extra_slots`、`mesh_role`（已经在签名里，作为 `role=`）、`wifi_2g` / `wifi_5g`。判据对四项一模一样——都不改 plan、
不改实例集合，只改 applier 拿同一份 plan 写出什么。其中**最容易被低估的是 `extra_slots`**：子节点的 plan 里序号行本来
就有（M2 下发的），这个开关只决定它们该不该广播出去；把它从 1 关到 0，`wlan-sync` 根本不会被叫醒，`prune_extras`
也就不会跑——**子路由会继续广播一个用户已经关掉的 guest 网络**，比"回程没生效"更难看出来。两个 radio pin 也一样：
一块板子有两个同频段射频时（ax3600：SoC 的 5G 旁边还有一块没用的 PCIe 5G），日志明确让用户去设 `zte_mesh.main.wifi_5g`，
可选了之后不重启就等于没选。所以签名带的是 `backhaul=… extra_slots=… pin2g=… pin5g=…` 一整组，同一个 `sync_runs` 判据。

**顺带**：`zte-mesh.config` 的注释补上"只收这两个值 / 保存会重启"和四项共用一条判据这段，页面上两端描述各加一句重启代价（这句是两端共用的
后果，`po/zh_Hans` 里只留一条 msgid，两端各保留自己那段说明——两条都写会变成四个要维护的长串）。

**测试**：`test_init.sh` **122 项全过**（106 → 122：坏取值两条 `multi-ap` / `on`、`sig-*` 十一条——主控两端、子节点两端、
显式默认与不设等价、纯主控四种写法签名相同且一个都不带、三条源码针）。`test_luci.js` `36 main / child 5`、
`test_i18n.py` 12 项、`sh -n` 都过。`test_wlan_sync.sh` 本轮没跑（`wlan-sync` 一个字没动）。

**踩到的一条**：给 init 测试的"每个可选项都写一遍"用例加 `option backhaul`，会让 `test_luci.js` 的完备性检查在**默认渲染
的表单**上要求这个字段——而默认渲染是纯主控，按上面的新规矩它恰恰不该有这个字段。这两条规则本身不冲突，冲突的是测试拿
"第一遍渲染"当"全部字段都在的那一遍"。改成渲染 `apply_local=1` 的主控即可，同时补 `extra_slots` 进那条用例（它以前只在
别的用例里出现，完备性检查从来没要求过它——**它漏检的正是这一类**：条件渲染的字段只要默认表单不显示，就永远查不出来）。

**这一节缺的**：`wifi_2g` / `wifi_5g` 两个 radio pin 只有注释掉的 UCI 一行，页面上没有字段（`wlan-sync` 却在日志里明确让用户去设它）——
登记成 PLAN 的 **B13g**，下面补掉了。回程本身的端到端还是 **H-01**（真实路由器）。

## 批 4 · B13g：日志让你去设的选项，页面上得有个地方设

`wlan-sync` 挑不出频段归属时会写这一行：`several 5g radios (…) and no way to tell which one carries the mesh; set
zte_mesh.main.wifi_5g to one of them`。也就是说**它把答案的一部分给了用户，却只给了一半**——它指定一个 UCI 选项，而页面上没有这个字段，
只能 SSH 进去手写。ax3600 恰好就是这台板子（SoC 的 5G 旁边还有一块没用的 PCIe 5G），所以这条日志不是假想。

**实现落点**（`zte-mesh.js`，紧跟 `extra_slots` 那块）：两个 `form.Value`（`wifi_2g` / `wifi_5g`），`child || local` 可见——和
`backhaul`、`extra_slots` 是同一批，判据仍然是"这个角色会不会动本机射频"。四条描述里两端共用一条重启代价（`Switching this restarts …`
那条 msgid 已经在 `po` 里，直接复用，不新开第二个长串）。校验用 `o.validate`（字母/数字/下划线），**没**去做"从 `wireless` 里列出真实段名"：

- 那要在视图里 `uci.load('wireless')`，再把 `radio_section_of()` 的频段判定（`band` 与 `hwmode` 两种写法）在 JS 里抄一遍——两处各写各的，
  正是这批一直在消的那类 bug；
- 而日志本来就把候选设备名列出来了（`(${candidates# })`），用户是看着那行来填的；
- `test_luci.js` 的 uci 桩对别的包只回 `null` / `[]`，加了这条路径等于给一个字段引入一整套依赖。

**测试**：`test_luci.js` **38 main / child 7**（原来 36 / 5）——三处可见性都带上两个 pin（子节点要**有**、纯主控要**没有**），另加一段情况断言
覆盖七个取值：空、`radio1`、`radio_hwmode11g` 收；`radio-1`、`radio 1`、`radio.1`、`"radio1"` 拒。`test_init.sh` 的"每个可选项都写一遍"
用例补 `option wifi_2g 'radio2'` / `wifi_5g 'radio1'`，`restart.sig` 的期望跟着变成 `… pin2g=radio2 pin5g=radio1`——**这一条同时证明
完备性检查真的会要求它们**（上一节那条教训的用法）。`test_i18n.py` 12 项过（四条新文案在 `po/zh_Hans` 可查，`.lmo` 重新编译）。

**顺手查的一条**：`test_rpcd.sh` 在这台 Windows 上是 17/24，7 条挂在设备动作（reboot / light）上——`python3` 是商店占位程序
（`python3 -c "print(1)"` 直接退出码 49、没有输出），桩 `jsonfilter` 不响应，`call` 全部拿到 `-2`。不是这批改出来的（这批没碰 rpcd），
PLAN §4 早已写明"Windows 上要先解决 `python3` 占位程序"，Linux/VM 上是 24 项。

**这一层的收获**：一条"让用户去设 X"的日志，就是一次对 X 的接口承诺——它必须能被兑现，否则等于把 UI 的活儿推给 SSH。
判断标准不是"这个选项重不重要"，而是**有没有任何一条运行时的话指向它**：有，就要有字段；字段做不到（比如要读别的包才能列出候选），
就至少在描述里抄一句日志的原话。

### `tools/lab/verify-install.sh`（busybox ash）+ `tests/test_verify_install.sh`（60 条主机断言）

**四条只在机器上才看得见的东西**：

1. **`apk add` 换的是文件，不是进程。** owrt 上替换完 `luci-app-zte-mesh` 之后，`ubus call luci.zte-mesh status`

   现在按 `uci` 的真实输出写（段类型不带引号、值带引号），并留一条不带引号的防止只认带引号那一种。

## 批 5 · A21 做完主机侧：`controller-peer.c` 拆出来，两个子节点第一次在同一条链上被验

入口就是那个缺失的接缝。把 `write_peer` / `note_peer` 从 `controller-trace.c` 原样搬到 `controller-peer.c`，
对外只留一个 `controller_peer_note(frame, bytes)`（返回写了几个文件），落盘目录听 `ZTE_MESH_PEERS_DIR`，默认仍是
`/run/zte-mesh/peers`。trace 那边少掉两个 include、`recvfrom` 里改成一行调用，preload 的钩子逻辑一个字没动。
新测试 `tests/controller-peer-codec.c` 在 `mkdtemp` 出来的临时目录上跑，**58 项**：

| 断言的 | 结论 |
|---|---|
| 两个 MAC 各写各的 `.metrics`，后者不覆盖前者 | ✅ 目录里两个文件、计数各自的 |
| 一帧同时带 `0x94` 与 `0x83` | 一个文件两行 `stations=` / `bss=`，正是 `read_peer()` 逐行走的形 |
| 一帧两个 `0x94` | 求和（原厂守护进程一 BSS 一 TLV），不是"取最后一个" |
| `stations=0` | 仍写进去——"没人连"和"没上报"必须在文件里分得开 |
| 灯（vendor `0x21`） | 跟着 sub-TLV 里的 AL MAC，**不跟以太网源**；且只在 `0x000e` 读，别的消息类型里同一个小类不算灯 |
| `0x8015` / `0x8017` 回执 | 记在**终端** MAC 下（`ok=1` / `ok=0`），发送它的 agent 名下没有文件 |
| 不落盘的帧 | 非末片、片号非 0、错 ethertype、长度不足 22、`0x0004` 碎帧（测试环境链路上每秒两帧） |
| 洪水预算 | 用满 32 个 MAC 即拒，被拒的那个 MAC 一个文件都没有；已 admitted 的照样能重写；`.t` 临时名零残留 |

三条"测试写下来才知道是原有行为"的事实，都按现状固化，不当 bug 改：

1. **中继转发的计数帧记在中继自己名下**（`hops=2`）：`0x94`/`0x83` 里没有 AL MAC 可跟，只能靠以太网源地址。
   灯是唯一自带节点身份的字段，所以只有它能改 `mac`。
2. 一帧只带灯（`0x000e` 无计数）时，除了 `.light` 还会写一个 `.metrics`，内容只有 `hops=`——把上一次的
   `stations=` 覆盖掉。读取端按"缺键 = 没数据"处理，加 30 秒新鲜度，所以页面表现为"稍后再说"，不是显示 0。
3. `0x0004` 若真带了 `0x94`，过滤器拦不住（它只拦"什么计数都没带"的帧），照样落盘。

**交付这一步差点漏掉**：源码改了不等于设备改了。ARM32 `libzte_controller_trace.so` 是随
`openwrt/zte-mesh/zte-mesh-runtime.tar.gz` 提交的。这台机器没有 mac 也没有原厂镜像，`make-runtime.py` 被
`prepare.verify_existing()` 按设计挡住（本机 `out/` 是合成清单，`rootfs_sha256` 为空），所以走 LAB.md 第 3.0 节的
**只换成员**路线：`repack-runtime.py --replace root/lib/libzte_controller_trace.so=...`。换之前先在测试环境里的 ImmortalWrt 虚拟机
把五个 shim 和 `db-engine-probe`/`zte-meshctl`/`ns-run` 全重编一遍做对照——**除 trace 外四个 shim 与两个 ARM32 工具
逐字节相同**（交叉工具链同为 Ubuntu GCC 11.4.0-1ubuntu1~22.04.3），`ns-run` 不同是因为虚拟机默认 `ROUTERCC=cc`
编出来是 x86 静态的，随包的 `ns-run` 是 aarch64，不动它。解包 diff 结果只有两个成员变了（该 `.so` 与 `SHA256SUMS`），
成员数 41 不变、41 条 sha256 全匹配、`tests/test_runtime.py` 九条守卫 0 失败。导出符号表逐条对齐（13 个 GLOBAL FUNC，
