## 装机反馈两条：有线口会掉，`search` 会死；角色从三个名字拆成两个开关

**报上来的现象**：master 端长时间运行后，页面上的「有线接口」变成未接入，重启主控就恢复。这是用户描述，不是结论——
中间隔了多久、期间发生了什么，都得自己查。

**线的死法**：沙箱的入口 `veth-lab` 与宿主的 `zmesh0` 是一对 veth，删掉任一端两个一起消失。沙箱里没有 `/proc`、
没有 `/sys`、没有 `ip`、也没有 `CAP_NET_ADMIN`，daemon 又在 `bind()` 时把 ifindex 钉死了——所以掉线之后**里面没有任何
办法重建这根线**，即使能建，已绑定的 socket 也还对着那个已经消失的 ifindex（`controller-route.c:49` 只在绑定时改写
br0→veth-lab）。用户"重启主控就好"不是巧合，那是唯一出路，只是以前得有人守着。

**修法（按用户定的口径：只改 host 侧 shell，不动 C）**：`attach` 本来就是唯一看着这根线的人，让它兼任看门狗——
`zmesh0` 与 `lab-peer` 连续 20 秒都不在，而沙箱进程还活着，就给它发 `SIGTERM`；ns-run 退出码 128+signo，procd 重新拉起，
新沙箱建出新线，同一个循环把它改名入桥。之后 60 秒冷却，不追着杀。选 shell 而不是 C 的实际收益：**不用重编 ARM32
二进制、不动 prebuilt 归档、不用跑 CI 就能装机验证**，代价是"发现问题的进程"和"重建线的进程"是两个。

**顺手挖出来的第二条**：核对 respawn 语义时发现 `search`（和 `wlan-sync`）写的是裸 `procd_set_param respawn`。
被中断那一轮的结论是"改成 `-1` 才是无限"，实测下来这条前提是错的：procd 把裸 `respawn` 填成 `3600 5 5`，
而 **retry=0 本身就是不限次**（ lab 上让一个进程 50 秒内退出 13 次，仍在拉起）。`search` 每 300 秒按设计退出一次，
5 次预算半小时烧完，日志 `crash loop 6 crashes, 300 seconds since last crash`，之后永久不再启动——晚开机的子路由
再也找不到主控。`zte-mesh status` 当时只剩 `running (2/3)`。所以真正要改的只有 `search` 和 `wlan-sync`
（`controller`/`attach` 早就写了 `3600 5 0`）。**教训：改之前先测一次语义，"文档里都这么写"不等于这台机的 procd 这么想。**

**角色的评估**：`main` 在 init 里发的是 `mesh.role=auto`，daemon 收到后写 `SetRoleEnable=1` + `Mode 0`，三秒后才由
`role_settle_at` 替身改成 `Mode 2`。沙箱里没有 cspd，这场"自适应选举"没有对手，替身走完只是白走；真正的风险是
**一台真的中兴子路由在那三秒里当选主控**，拓扑反过来。第三个名字还把两件不相干的事捆在一起：是不是主控、
要不要把档案落到本机无线。所以拆成两个开关：`mesh_role=master|slave` + `apply_local=0|1`，`main`/`auto` 作为
"master + apply_local=1" 的别名继续被读，线上从此只发 `master`/`slave`。C 侧的 `CONTROLLER_ROLE_AUTO` 分支与三秒
结算留着——升级前写好的 `/run/zte-mesh/config` 里可能还有 `auto`，而新配置永远走不到那条分支。

**顺带修的一处真 bug**：`restart.sig` 只记键名（`cut -d= -f1`），角色取值变化看不出差别，于是改角色不会重启服务，
procd 实例集合（`search`、`wlan-sync`）保持原样——正是"改了不生效，得手动重启"那一类。现在把两个决策的值也进签名。

**LuCI 侧**：`mesh_role` 只剩两个选项，多一个 `apply_local` 复选框（子路由不显示）。旧配置 `main`/`auto` 的显示与保存
都不会掉行为：复选框的 `default` 跟着别名走，存盘时写出 `master` + `apply_local=1`。rpcd `status` 现在返回两个轴
（`role` + `local`），页面标题由这两值决定。

**主机测试**：init 103 项（新增 `role-local-sig`、`role-slave-local-keeps-plan`、`role-main-local-off`、两个 legacy 别名、
respawn 预算与 attach 看门狗的判据）、rpcd 24 项（六个 role/apply 组合）、luci、i18n 全过。`test_wlan_sync.sh` 在本机
（Git Bash）跑不完，只在容器里算数。

**还欠的**：H-10（`ip link del zmesh0` 后自愈）、H-11（真中兴子路由在 `master` 下照样入网、且没有自当选）都要上机；
这两个是本轮唯一没被主机测试覆盖的部分。改动全在 shell / JS / po / 文档，没碰 C，所以不需要 CI 就能装机——但要装机
验证才谈得上"修好了"。

## 批 4：无线回程的另一半（B13a/B13b）——4 地址的开关是 `wds`，不是 `multi_ap`

**为什么先查这一步**：§11.6 写回程时只做了 AP 那一半，"仍缺"里挂着两条——"4addr 由 hostapd 依 `multi_ap` 去设，
真机上要看"和"STA 那一半还没写"。这两条其实是一件事：如果不先在 netifd 侧搞清楚谁决定 4 地址，写出来的 STA 段
大概率是个连不上的配置。所以本轮第一件事不是写代码，是读装机的那份 ucode。

**实测（ax3600，ImmortalWrt 25.12，`/usr/share/ucode/wifi/`；VM 那台没有无线，`/lib/wifi` 都不存在）**：

- `supplicant.uc:83`——`case 'sta':` 里 `set_default(config, 'multi_ap_backhaul_sta', config.multi_ap)`。UCI 的
  `multi_ap` 在客户端被改名成 wpa_supplicant 的 `multi_ap_backhaul_sta`，它只决定**关联能不能被回程 BSS 接受**。
- `supplicant.uc:278-279`——接口挂着 bridge、`mode == 'sta'`、且 `wds` 和 `multi_ap` 都没有 → `BRIDGE_NOT_ALLOWED`，
  直接起不来。
- `supplicant.uc:305` / `:313-314`——**`'4addr': !!interface.config.wds`**，`config.bridge` 也只在 `wds` 时才写。
  4 地址和入桥都只认 `wds`，跟 `multi_ap` 一点关系没有。
- AP 侧不受这个影响：`ap.uc:58` 把 `multi_ap` 原样透传给 hostapd，回程 BSS 的 4 地址由 hostapd 自己在驱动里设。
  顺带 `ap.uc:224`：`multi_ap == 1` 会关掉 WPS——对我们没影响，但值得记着。

**所以回程 STA 一段要写两个选项**：`multi_ap 1`（让主控那个 `multi_ap=2` 的 BSS 接受它）+ `wds 1`（4 地址 + 入桥）。
这纠正了 §11.6 "4addr 跟 `multi_ap` 走"的推断——那条只在 AP 侧对。也意味着 H-01 的清单变短了：映射对不对主机测试就能
断言，真机只剩端到端。**教训：推断来自哪一层要说清。** "hostapd 会依 multi_ap 设 4addr"是 hostapd 侧的事实，我把它
当成了整条链的事实，而 OpenWrt 这一侧真正动手的是 netifd。

**实现**：`wlan-sync` 加 `backhaul_side()`（读 `mesh_role`，`slave` → `sta`，其余 → `ap`）与 `apply_backhaul_sta()`
（段名 `zte_backhaul_sta_<band>`，`mode sta` + `multi_ap 1` + `wds 1`，名称/密钥/加密全取 plan 那行，**不写 `hidden`**
——隐藏是 AP 的概念，客户端没有广播）。同一条 `access&64` 的行现在按角色落成两端的某一段，`clear_backhaul` 因此加了
参数：换角色时把**对端**那段还回去（子节点上留一个回程 BSS、或主控上留一个回程客户端，都会在页面上显示成一条"链路正常"
的假象）。回程行"声称加密但 plan 里没有密钥"两端都拒绝应用——写下去就是一个永远连不上的 BSS/STA，不如不写。
`zte-mesh.init` 补了一条启动日志：`backhaul=multi_ap` 落在主控 + `apply_local=0` 上时这个开关无事可做，因为这台机根本不
本地落档案。`wpad-basic` 的告警扩到客户端（4 地址同样要完整 wpad）。

**踩的坑（记下来免得重犯）**：`set -u` 这一条本轮**撞了两次**，而且形状不同。

## 批 4 收尾（B13d）：`backhaul` 这个开关原来只显示了一半

上一节登记的那条不一致，做法上只有两个选择：把字段限回子节点并解释清楚，或者让它跟角色真正对应。选了后者，理由和
`extra_slots`、`apply_local` 已经立过的规矩是同一个——**页面上只出现在"这个字段会动本机"的角色上**。回程是一条链路，
两端各由一个角色来建：

| 角色 | `backhaul=multi_ap` 在本机建什么 | 页面 |
|---|---|---|
| `slave` | `zte_backhaul_sta_<band>`：`mode sta` + `multi_ap 1` + `wds 1`，挂到该频段的桥 | 显示，标题"连回控制器" |
| `master` + `apply_local=1` | `zte_backhaul_<band>` 回程 BSS（`multi_ap 2`），主 SSID 标为前传 | 显示，标题"给子路由的回程网络" |
| `master` + `apply_local=0` | **什么都不建**（本机不动无线，也没有子节点来连它的空中接口） | 不显示 |

以前只有第一行有字段，第二行只能去 `zte-mesh.config` 手写 UCI；而 `apply_local=0` 的主控以前也看得到这个开关，设了
不会有动静（init 那条告警是这批加的）——所以这一改同时消掉两种误导。

**实现落点**（`luci-app-zte-mesh/htdocs/luci-static/resources/view/network/zte-mesh.js`，`backhaul` 那段）：条件从
`if (child)` 换成 `if (child || local)`，标题与描述都按角色给两份文案，描述里各自写清本端建的是客户端接口还是 BSS、
需要完整 wpad、以及对端没下发回程网络时不会创建东西。文案同步 `po/zh_Hans/zte-mesh.po`（旧的那条只讲"子路由如何回连"
却说建 BSS 的条目删掉，换成三条：新标题 + 两端各自描述）。`.lmo` 不入库，打包时生成。

**测试**：`tests/test_luci.js` 的角色分支要能同时看到 `mesh_role` 与 `apply_local` 两个轴，所以给 uci 桩加了 `uciLocal`，
断言三种组合——子节点（有 `backhaul`，无 `apply_local`）、旧名 `main`（现在**要求**有 `backhaul`，以前是禁止）、
`master` + `apply_local=0`（`backhaul` 与 `extra_slots` 都不出现，`apply_local` 自己在）。结果
`34 main / 10 slot / 4 ACL / 2 client / child 5`；`python tests/test_i18n.py` **12 项全过**（含每条新文案在 `.po` 里可查）。
`test_wlan_sync.sh` 169、`test_init.sh` 106 不受影响（只动 LuCI 与文案）。

**这一层的收获**：一个开关的可见性属于它的语义，不属于它的名字。`backhaul` 读起来像"子节点的事"，但它真正的条件是
"本机会不会因此动射频"——和 `extra_slots`（能应用档案的两端才给槽位）、`apply_local`（只有主控才有意义）是同一条规则。
下次加字段先问这句，别按角色名硬套。

（那一句 `34 main` 在下一节之后变成 **36**：`test_luci.js` 里"init 读到的每个选项都要有表单项"这一遍原先渲染默认的
纯主控表单，而按新规矩纯主控就是少两个字段——那一遍改成渲染"会落地的主控"，顺带把 `extra_slots` 也补进了
init 测试的"每个可选项都写一遍"用例。）

## 批 4 的最后一格（B13e）：`backhaul` 的取值，和"改了不生效"

接着上面那条线查下去，发现同一个选项还有两个更实在的问题，都在主机侧，都能测：

**一、取值没人管。** `wlan-sync` 的 `backhaul_mode()` 故意宽容——"认不出的就当 off"，这一条本身没错（应用侧不该因为
一个拼写就把整份档案停掉）。错在**没有任何地方告诉用户他写错了**：`multi-ap`（中兴自己文档里的写法，带连字符）、`on`
这种都会变成"页面开关是设过的、射频上什么都没有"。同类问题 `extra_slots` 早就在 `write_config` 里拒了，`backhaul` 漏了。
现在 `write_config` 只收 `off` / `multi_ap`，别的取值报 `backhaul must be off or multi_ap` 并不启动；空值按默认 `off` 收。

**二、改了不生效。** `reload_service` 只比 `restart.sig`，而签名以前只记 `role=` 与 `local=` 两个值 + 一批**键名**。
`backhaul` 既不加实例也不改 plan（回程那一行本来就在 plan 里，`MapAccessAttr&64`），它只改 `wlan-sync` 拿到**同一份
plan 时写什么**——而那个 watcher 只对 plan 的**内容摘要**起作用（`stamp()`，`md5sum`/`stat`/`ls -ln` 三选一）。于是
`off → multi_ap` 保存后什么都不发生，要等下一次别的原因引起的重启才生效。这正是用户报过的"改了没生效"那一类，
`mesh_role`/`apply_local` 上一批已经这么修过。

**做法**：签名按值带上 `backhaul=<取值>`，但**只带会跑 applier 的两个角色**——`slave`（客户端在这一端）与
`master + apply_local=1`（回程 BSS 在这一端）；`master + apply_local=0` 不带，因为在那个形状里这个值不起作用，
为一个不起作用的东西重启组网服务（子路由最长一分钟掉出拓扑）是白重启。这个判据在 procd 起 `wlan-sync` 实例的那一行的
条件里**本来就已经写过一遍**，现在抽成 `sync_runs ROLE APPLY_LOCAL`，两处共用——实例行在 `start_service()` 里，
这套主机测试跑不到它，所以钉了三条源码针，防止两处将来各写各的。

**顺带**：`zte-mesh.config` 的注释补上"只收这两个值 / 保存会重启"，页面上两端描述各加一句重启代价（这句是两端共用的
后果，`po/zh_Hans` 里只留一条 msgid，两端各保留自己那段说明——两条都写会变成四个要维护的长串）。

**测试**：`test_init.sh` **118 项全过**（106 → 118：坏取值两条 `multi-ap` / `on`、`sig-*` 七条——主控两端、子节点两端、
显式 `backhaul=off` 与不设等价、纯主控两种写法签名相同且不带 `backhaul`、三条源码针）。`test_luci.js` `36 main / child 5`、
`test_i18n.py` 12 项、`sh -n` 都过。`test_wlan_sync.sh` 本轮没跑（`wlan-sync` 一个字没动）。

**踩到的一条**：给 init 测试的"每个可选项都写一遍"用例加 `option backhaul`，会让 `test_luci.js` 的完备性检查在**默认渲染
的表单**上要求这个字段——而默认渲染是纯主控，按上面的新规矩它恰恰不该有这个字段。这两条规则本身不冲突，冲突的是测试拿
"第一遍渲染"当"全部字段都在的那一遍"。改成渲染 `apply_local=1` 的主控即可，同时补 `extra_slots` 进那条用例（它以前只在
别的用例里出现，完备性检查从来没要求过它——**它漏检的正是这一类**：条件渲染的字段只要默认表单不显示，就永远查不出来）。
