## 子路由（Slave）角色：静态判定实验

背景：用户问能否让装插件的路由器既能当 master 又能当子路由。先给了可行性分析，随后要求做判定性实验。

本机没有 lab 环境（无 docker、WSL 被安全策略拦、out/ 与原厂 rootfs 不在），所以做了**静态那一半**：从
`openwrt/zte-mesh/zte-mesh-runtime.tar.gz` 里取出 `multiapd`（哈希 `a0ba6bee…`，与文档一致）和 `libcmapi.so`，
用新写的 `tools/probe/agent-surface.py` 解析 `.symtab` / PLT / 调用图。

结论（写进 `docs/research/AGENT_PROBE.md`）：
- `slave_init` 由运行时的数据字节把门（0x62824 前的 `ldrb r3,[r4,#0x1f]`），不是编译期开关。
- M2 不走 ASEND 到 `wlan_mgr`，走 `CmWLANSetAPConfig` / `CmWLANSetPsk`（经 `MeshWlanSetAPCfgByBandAndIfIndex`、`acdcWlanSetPWKey`）。
- `_CmWLANSetAPConfig` 顺序：`WlanCfgDbRead` → `WlanCfgDbWrite`(0x14d2c0) → `CmMultiAPWlanRenewNotify` → `cm_wlan_send_cmapi_set_msg`(0x14d8d8)。
  **先写库**，所以没有 cspd 时库照样被写。
- 但 setter 的返回值 = 通知结果（0x14d8dc `mov r5,r0` → 0x14d92c `mov r9,r5` → `mov r0,r9`），所以要替身 `CmSendMsg2MM`（已导出，0x33df8）返回 0。
- 失败分支（0x75e18）只记日志继续，不整体中止，但成功标记不置位。

对成本估计的修正：不是"重写 cspd + wlan_mgr 翻译层"，而是"同步器（WLANCfg/WLANPSK/WLANBase → hostapd）+ 一个返回值替身 + 无线电状态适配 + 选举触发（事件 0x909b）"。
剩余不确定性：`WlanCfgDbWrite` 在 db-engine-probe 库上是否成功、无线电状态查询、驱动 4 BSS/4-addr、主控路径 CurHop 回归。

## agent 模式 M1/M2 跑通（lab，2026-10-29 下午）

目标：让 daemon 以 `Mode=1 / SetRoleEnable=0 / EnMasterOnly=0`（子路由）启动，用合成主控陪它走完 M1/M2。
结果：走通，M2 被完整接受，SSID/PSK 配置**写进了 WLANCfg**。细节写进 `docs/research/AGENT_PROBE.md` §8。

关键结论（帧形状，全部由反汇编确认）：
- Supported Service(0x80) 的值是**角色**不是位数：0=Controller、1=Agent。原来的合成响应写 1 是错的。
- M2 必须带 **0x82 AP Radio Identifier**（不是 0x85），值取 M1 的 0x85 payload 前 6 字节；
  沙箱里这个值就是 `"MAP24G"`/`"MAP5GL"`（`.data 0xe207c` 的硬编码表，`get_wlan_radio_info` 按频段取）。
  `_acdcCheckAPRadioIdentifier` 拿它和自己库里的表比，不等就 `Check APRadioIdentifier failed`。
- M2 的 WSC 属性号：UUID-R 是 **0x1048**（0x1047 是 M1 的 UUID-E）；`eap_wps_process_message_M2`
  按固定顺序读 0x104a/0x1022/0x101a/0x1039/0x1048/0x1032/0x1004/0x1010/0x100d/0x1008/0x1021/0x1023/
  0x1024/0x1042/0x1054/0x1011/0x103c/0x1002/0x1009/0x1012/0x102d/0x1005/0x1018，缺哪个报哪个。
  设备类属性直接从 M1 回显最省事（`tag_list()` 打出的 m1_tags/m2_tags 对照）。
- 0x1018 明文**不要**套 0x100e Credential：`acdcParseM2Msg` 用 8 项表按属性号派发
  （0x1045/0x1003/0x100f/0x1028/0x1027/0x1020/0x101e/0x1049），套了就解出空 profile。
- 0x1018 = 随机 IV(16) + AES-128-CBC **PKCS#7**；填充 `16 - len%16`（对齐时补满一整块）。
  原来用零填充 + 零 IV，`EVP_EncryptFinal_ex` 那套坑也一并去掉了。

运行结果：
- `CmWLANSetAPConfig instid=DEV.WIFI.AP1 status=-3 errno=9`（无 cspd → `cm_wlan_send_cmapi_set_msg` 失败），

- 本机没有 `sudo -n`：VM 上统一 `echo 123 | sudo -S -p "" …`。

## agent 模式第二轮：PSK 与 repeater 同步也落库（2026-10-29 下午续）

上一轮的"PSK 没写"有两个原因，这一轮都解决了，M1/M2 现在**完整落地**。

### 1. cspd 替身只该覆盖两个 setter，不该替 CmSendMsg2MM

`CmSendMsg2MM` 有 324 个调用点，全局返回 0 会让读接口拿到未填充的缓冲区。真正需要的是把
`CmWLANSetAPConfig` / `CmWLANSetPsk` 的**返回值**改掉（写库在 notify 之前，已经发生），
即 `controller-trace.c` 里的 `setter-ok` flag 开关：厂商码记在 `status=`，交给调用方的是 `report=`。

`acdcConfigM2EncryptedSettings`（0x75b7c）的门槛：
- `75e18 cmn r0,#9` → -9 当"已配置"；`75e20 cmp r0,#0` → 0 才算成功；其它（-3）直接失败返回。
- `75e6c cmp sl,#0` → `sl` 是 M2 flag bit4，**置位时 PSK 按设计跳过**，与返回值无关。
- `75f08 MeshWlanMapSsidCfgSync2Repeater` 只在 `m2flag & 0x40` 且 `(r8 & 2)==0` 时执行。

### 2. `WLANPSK` 的读法是错的，所以上轮看到"空"

必须 `dbAPIGetView("WLANPSK", "DEV.WIFI.AP1.PSK1", buf)` 按实例 id 读，密钥在行内偏移 260；
`dbGetValComm("WLANPSK", row, "PreSharedKey", …)` 按行号读这张表永远读不到。
（`_CmWLANSetPsk` 里 `WlanPSKDbWrite` 在 0x147720，确实在 `CmMultiAPWlanRenewNotify` 之前。）

### 3. 结果（可复现两次）

```
before  PSK1 key_len=20 m2_match=0   |  WLANCfg row0 zte-controller-test
after   PSK1 key_len=18 m2_match=1   |  WLANCfg row0 zte-agent-m2
        PSK5 key_len=20 m2_match=0   |  WLANCfg row1 不变（M1 是 band 0）
success, mesh sync for M2: index[0], SSID[zte-agent-m2], Auth[0x20], EncryptionType[0x8]
acdcParseM2Msg cfgChg[0]=1
```
`m2_match` 是与 M2 密钥的逐字节比较（只输出布尔，不输出密钥）。

### 4. 工程改动
- `controller-trace.c`：`setter-ok` flag + `CmWLANMapSsidCfgSync2Repeater` interposer（后者命中不到：
  libcmapi 内部是直接调用不走 PLT，只能靠 `%s, mesh sync for M2` 那行日志判断成功与否）。
- `controller-run.c`：新增 `dump_psk_rows()`，按视图 API 读 WLANPSK 并给 `m2_match`。
- 新测试 `tests/controller-wsc-crypto-codec.c`（87 断言）：PKCS#7 边界 1/15/16/17/…/300、随机 IV、
  错误密钥、非法入参。VM 上没有 libcrypto 的 dev 符号链接，Makefile 里 `HOSTCRYPTO` 自动回退到
  `-l:libcrypto.so.3`。
- 文档：`AGENT_PROBE.md` §9（含 8.3 的更正）、`docs/LAB.md` §3.1（agent 模式与两个 flag 文件）。

## agent 模式第三轮：band 1 与重启（2026-10-29 傍晚）

上一轮留下的两个"还没测"都测完了，结论都进了 `docs/research/AGENT_PROBE.md` §10。

### 1. band 1 不会被拒：一个 radio 一份 M1、一份 M2

- daemon 每个 radio 各发一次 M1：`85:17`（前 6 字节 ASCII `MAP24G`）与 `85:47`（`MAP5GL`）。
  原来的循环 `&& !m1_seen` 只回答第一个，所以 band 1 一直停在 identity。
- 改成按 radio 标识去重、逐个回答（表长 4），并且每频段不同 profile：2.4G→`zte-agent-2g`、
  5G→`zte-agent-5g`。不同 profile 是必要的，否则"落到正确行"和"同一行写两次"在库里看不出区别。
- 结果：`row0=zte-agent-2g`、`row1=zte-agent-5g`，`AP1.PSK1`/`AP5.PSK1` 均 `m2_match=1`；
  双向对称 `CmWLANSetAPConfig DEV.WIFI.AP1/AP5`，无一次 `Check APRadioIdentifier failed`。
- 两个易错点：`The WSC-%d will cfg to %d %d` 的第一个数是**M2 内凭据序号**（每份 M2 只带一份，
  所以恒为 0），频段来自 0x82 TLV；acd 状态机**每频段一台**，`state[i]:0→1(event2)→2(event7)`。

### 2. 重启：库保留、磁盘不写、agent 每次都重新入网

- 方法：复用已有的 `controller_respawn_daemon()`（SIGKILL + fork/exec，库与订阅池留在探针进程）。
- **坑**：第一次得到 `reboot_m1=0`，差点读成"它记得已配置"。实际新 daemon 构建了 M1 报文却没发，
  因为 acd 不自己离开 state 0，需要先有一次拓扑交换。补上"重启后再通告"后两个 M1 都来了。
  重启后 M1 通常要两次 topology retry（约 19 s）才出现。
- 结论三行：库里行跨重启**在**（`m2_match=1`）；daemon **不写盘**（`find -newer` 0 个文件）；
  重启后 acd 从 `state[0]:0` 起、**重新发全部 M1**（未回答还会重试）。
- 对插件：子路由必须能接受**重复下发的 M2**；控制器在拓扑发现后无条件重发即可。
- 另外每份 M2 落库后稳定出现 `CmMultiAPWlanRenewNotify ASEND error !`（订阅者 cspd 不在），
  这条 notify 就是"库 → hostapd 同步器"要挂的钩子。

### 3. 回归
主控 `running=1 / mode=2 / set_role_enable=1 / en_master_only=1 / cur_hop=2 / startup_renew=0`；
主机测试 162+331+87 断言全过。flag 文件（trace-all / setter-ok）已清掉。
`--agent` 建议 `--seconds 120`（一次完整运行约 50 s，含重启阶段）。

## 第五轮（16:50）：回程 BSS 走 Multi-AP

### 先定结论
去查了 `Zlion-Y/e2631-openwrt`（同一套运行时在 E2631/ZX279128S 上的移植）：原厂无线是 `CSP_WLAN`
私有栈、`# CONFIG_CFG80211 is not set`，驱动 5.5MB `mt7916.ko` 用 dat 配置；dat 里的 `MeshId`/`MeshWPAKEY`
是空的、`MapMode=0`。**mt76 不消费那些参数，从原厂提取回程在这条路上没有落点。**
也否掉 802.11s：1905 CMDU 要 4 地址帧，802.11s 的数据帧带 mesh header，跑不上去。→ 用 hostapd `multi_ap`。

### 实现
- `wlan-sync` 新增 `zte_mesh.main.backhaul`（`off` 默认 / `multi_ap`）。
- `multi_ap`：主 BSS 写 `multi_ap=1`；plan 里 `MapAccessAttr & 64` 的行 → 独立段 `zte_backhaul_<band>`，`multi_ap=2`。
- 按 access 位判断而不是 slot 号（各型号槽位含义不同）；没有回程行就不造；`network` 从主 BSS 抄。
- `off` 复原：删 `zte_backhaul_*`，只清 `multi_ap=1`（2/3 是别人设的，不动）。
- `ap_iface_of()` 排除 `zte_backhaul_*` 与 `multi_ap=2`，否则第二次运行会把回程段当主 SSID。
- UCI/LuCI/po 暴露该选项；控制器侧本来就写 `MapAccessAttr = slot==3 ? 64 : 32`（`wlan-profiles.c:305`）。

### 测试
- `test_wlan_sync.sh` 21 → **53**（桩补了 section 建删与非 wireless 的 uci get）。
- init 66 / rpcd 15 不变。C codec 未改，未复跑。

### 坑
- **本机工作区是 CRLF**（`core.autocrlf=true`，仓库无 `.gitattributes`）。`test_init.sh` 的 UCI 解析桩
  不 strip 回车 → `cur` 带 `\r` → SSID 读成空 → 66 项里 65 挂。转 LF 副本跑即 66 全过。
  想在本机跑测试必须：`sed 's/\r$//'` 到临时目录，或改用 LF 工作区。
- 因此 `zte-mesh.config` 注释里**不要出现撇号**（`plan's`）——排查时误以为它是元凶，实际是 CRLF。

1. `zte-mesh.init`：`mesh_role` 提到档案校验之前；`slave` 且本地档案为空时 `borrow_profile()` 从
   `/etc/config/wireless` 借一套（这台机器正在广播的网络），借不到才拒绝，错误信息分角色。
   **没有走"允许无档案"**：`parse_config()` 要求 radio0 三件齐（`controller-service.c:516`），

   "子路由"清单区块对子路由隐藏；状态区加"角色"和"Wi-Fi 同步"行。

## 第七轮（21:40）：解包 ZXHN E2633 官方固件

用户给了 `F:/中兴E2633转正/6B5改_109适配/6B5改_109适配.bin`（26.87 MB，
MD5 `6f004d68c2bf0551a8ab383a658e38b2`）。**是 E2633 不是 E2631**（头部写
`ZXHN E2633 V1.0.0` / `V1.0.0.6B5.8000` / 构建 20240925150510）。

### 布局
`0x0` ZTE 头(564B) → `0x234` uImage(3.34MB, ARM, load 0x40008000, comp=0)
→ 65KB 零填充 → `0x340214` rootfs(23.46MB, **加密**) → 尾部 512B 16字节周期填充。

头部三个字段与实测吻合：`0x44`=0x019a0000（文件长-532）、`0x4c`=0x234（uImage 偏移）、
`0x54`=0x01660000（rootfs 长度）。

### 内核解开了（关键手法）
uImage 里是 zImage，再解一层：**gzip 流在 0x681c**，解出 6 627 680 字节 ARM Image。
Linux **4.1.25**，gcc 4.9.3，Buildroot 2015.08.1，SMP。
内核带 IKCONFIG（`IKCFG_ST` @0x42eae8），解出 **92 250 字节完整 .config**。
产物在 `out/analysis/e2633/`（`/out/` 已 gitignore）。

### 三条有价值的结论
1. `# CONFIG_CFG80211 is not set` / `# CONFIG_WLAN is not set` / `CONFIG_CSP_WLAN=y`
   —— 与 e2631-openwrt 的 v1.5 报告**逐字一致**，第二个机型独立确认「原厂无线不在标准栈」。
2. **`CONFIG_CSP_WLAN_EXTENDER_LINK_BY_DRIVER=y`** + `MTK_EXTENDER=y` +
   `# CONFIG_CSP_WLAN_ADAPTER_MULTI_AP is not set`，配合内核符号 `MULTIAP_SLAVE`/
   `wlan_multiap_mode` —— **回程是驱动建的**，原厂根本不经过 hostapd，
   §11.6 里「4addr 由 hostapd 依 multi_ap 设」的推断在原厂路径上不成立。
3. **`br_ieee1905_filter_init register nf hooks failed`** + `br_ieee1905_check_is1905_msg`
   + `CONFIG_CSPKERNEL_IEEE1905=y` + `CONFIG_BRIDGE_NETFILTER=y`
   —— 内核网桥对 1905 帧有**专门的 netfilter 钩子**。lab 里 1905 走 veth 是普通泛洪，
   真机有这个钩子参与，这是之前不知道的差异来源。

另外：`SUPPORT_80211KV=y`（无 r）、`DUAL_BAND_SETTING_SYNC=y`、`KEY_GLOBAL_SETTING=y`、
`VAP_CONFIG_INDEPENDENT=y`、`VLAN=y`、`ELINK=y` 都与既有结论对得上。

### rootfs 为什么解不开（四条判据）
熵 7.99 全程 / printable 35-37% / 四种 squashfs magic 全无 / 长度是 16 的倍数但起点 %16==4。
反向证据：内核 `CONFIG_CRYPTO_AES=y` 但 `# CONFIG_CRYPTO_CBC is not set`、
`# CONFIG_CRYPTO_XTS is not set` → 解密不在内核，在 bootloader（不在 bin 里）。

## 第八轮（22:30）：E2633 固件解密判定（结合 Zlion-Y 参考资料）

用户给了 Zlion-Y 的 5 篇博客/仓库，要求判定能否解密，不行就找第三方解包工具。

### 结论：算法确定（AES-128-ECB），密钥拿不到，解不开

1. **算法收敛**：`zte-e2631-openwrt/overlay/package/firmware/e2631-fwslot/src/e2631-fwslot.c`
   头部注释原话："only the stock rootfs is AES-128-ECB at rest, decryption lives in the
   vendor kernel's MTD read path"。与我实测的 ECB 指纹**双重吻合**：
   `9b58f878bbb341366b2b543daffb0185` 重复 5906 次 = JFFS2 的 0xFF 空闲块被 ECB 加密的结果
   （CBC/CTR 不会重复）。rootfs 是 **JFFS2** 不是 squashfs（上一版说错了，已改文档）。
2. **kernel 明文**：uImage @0x234 CRC `0x31f288df` 自洽（头里 dcrc 与实算一致）。
   fwslot.c 也说 E2631 包「kernel extent is a plaintext uImage; only stock rootfs is ECB」。
3. **密钥不可得**：由 `zte_token` 运行时推导，参考资料明说不公开，仓库/博客均无解密工具。
   内核 `.config`：`CONFIG_CRYPTO_AES=y` 但 `# CONFIG_CRYPTO_CBC is not set`、
   `# CONFIG_CRYPTO_XTS is not set` → AES 只给 MTD 透明解密用，密钥不落盘。

### 关键判断
**解密这个 bin 对「复现 mesh」边际价值≈0**：SR1010 已拿到同一套 multiapd/libcmapi，
解 E2633 rootfs 不会多出新代码。第三方解包工具本质都要先拿密钥，而密钥不在包内 →
「解包工具」这条路实际还是「从真机读」。

### 可复用的设备侧事实（已写进 E2633_FIRMWARE.md §7）
U-Boot：上电按 1，密码 `5cE080@fyBD`，串口 115200，earlycon=zteuart @0x94404000。
分区：bootloader/kernel(AES-ECB)/rootfs(JFFS2)/kmodule(JFFS2)/tag/wifi/config。
双槽 slot0@0x700000 slot1@0x2300000。telnet：Web 导出 config.bin 改后还原，账密 admin。
刷写：fw_flashing -f 只写备用槽；Web 上传被请求体限制（~330KB），大包走 TFTP。
