# 2026-10-30 工作日志

## GitHub CI 打包 apk：修复 kernel-headers 下载失败
- 报错：`make toolchain/install` → `toolchain/kernel-headers` 下载 `linux-6.18.38.tar.xz` 失败
  `Cannot find appropriate hash command`（hash="x"，URL=`@//kernel/linux/kernel/v6.x`）
- 根因：cnjn/immortalwrt `sr1010-zx279133` 分支的 ZTE target 用外部内核树
  （`KERNEL_PATCHVER=6.18`，`LINUX_VERSION-6.18=.38` → 6.18.38，`LINUX_KERNEL_HASH=x`）
  不设 `CONFIG_EXTERNAL_KERNEL_TREE` 时 kernel-headers 会去下载不存在的内核 tarball
- 修复：CI 新增 clone 外部内核树 `cnjn/linux-mainline-zte-zxslc-sr1010`（build 分支，--recurse-submodules），
  并在 .config 设 `CONFIG_EXTERNAL_KERNEL_TREE` 指向 `linux-6.18.38/`
- 关键证据链：target/linux/zte/Makefile 的 error 只在无 EXTERNAL_KERNEL_TREE 时触发；
  include/kernel.mk 设 EXTERNAL_KERNEL_TREE 后跳过无效 LINUX_SITE；generic/kernel-6.18 定义版本/hash

## 二次修复：CONFIG_EXTERNAL_KERNEL_TREE 无效，改走 dl/ 预置内核包
- 第一次修法（clone 外部树 + 写 CONFIG_EXTERNAL_KERNEL_TREE）经 CI 实测无效：
  该符号不在 Config-kernel.in / Config-build.in / target/Config.in，`make defconfig` 直接丢弃
- 决定性证据（include/download.mk）：
  - `$(DL_DIR)/$(FILE):` 规则无前置依赖 → 文件存在即跳过 recipe，完全不下载、不校验
  - `check_download_integrity` 在 hash 不匹配时会加 `FORCE` 强制重跑 → 必须写真实 SHA256
- 最终方案（走上游标准路径，不依赖外部树分支）：
  1. `git clone --depth 1 -b codex/sr1010-mainline cnjn/linux-mainline-zte-zxslc-sr1010 → linux-6.18.38`
     （父仓库 build 分支只是把同 URL 的该分支当 submodule 钉住，直接浅克隆分支更省）
  2. `tar --exclude=.git -cf - linux-6.18.38 | xz -T0 -3 > openwrt/dl/linux-6.18.38.tar.xz`
     （顶层目录名必须与 LINUX_VERSION 一致；TAR_OPTIONS 是 `-xf -`，无 strip-components）
  3. `sed -i` 把 target/linux/generic/kernel-6.18 里 `LINUX_KERNEL_HASH-6.18.38 = x` 换成真实 SHA256
  4. rm -rf 内核目录回收磁盘；timeout 90→180 分钟，-j1 改 -j$(nproc)

## 三次修复：kmod 依赖触发 target/linux/zte 的 $(error)
- 现象：kernel-headers 已过，libmnl 编译成功，随后顶层 `Error 2`，子 make 无 Error 行
- 真因链：
  - toplevel.mk 的 `%::` → package/Makefile 按 tmp/.packagedeps **连带构建依赖**
    → zte-mesh 的 +ip-full 拉出 libmnl/iproute2，+kmod-veth/+kmod-sched-core 拉出内核模块
  - 构建 kmod 会求值 target/linux/zte/Makefile，其中
    `ifeq ($(DUMP),) ifeq ($(strip $(CONFIG_EXTERNAL_KERNEL_TREE)),) $(error ...)`
  - 而 CONFIG_EXTERNAL_KERNEL_TREE 若在 `make defconfig` **之前**写入，会被 kconfig 重置为默认 ""
  - 空值时 include/kernel-defaults.mk 的 Kernel/Prepare 还会走 `ln -s ""` 的错误分支
- 关键源码事实：
  - host-build.mk：`$(if $(strip $(PKG_SOURCE_URL)),$(call Download,default))`
    → 设了 EXTERNAL_KERNEL_TREE 时 LINUX_SITE 为空 ⇒ 完全不调 Download ⇒ 不下载内核
  - config-6.18 里 `CONFIG_EXTRA_FIRMWARE_DIR="../../immortalwrt/target/linux/zte/zx279133/firmware"`
    ⇒ 布局必须是 <dir>/immortalwrt + <dir>/linux-mainline-zte-zxslc-sr1010/linux-6.18.38
- 最终 CI 布局：sr1010/immortalwrt + sr1010/linux-mainline-zte-zxslc-sr1010/linux-6.18.38
  - 内核树浅克隆 codex/sr1010-mainline 分支（父仓库 build 分支只是 submodule 钉同一 URL）
  - defconfig 之后 sed 删掉旧行再 printf 追加 CONFIG_EXTERNAL_KERNEL_TREE 绝对路径
  - 仍保留 dl/ tarball + 真实 SHA256 作兜底
  - 分三个目标构建（luci-base → zte-mesh → luci-app-zte-mesh），日志落 build.log，失败时打印摘要并上传 artifact

## 四次修复：feeds.conf 被覆盖导致 luci feed 缺失
- 报错：`No rule to make target 'package/feeds/luci/luci-base/compile'`
  （kmod/$(error) 已不再出现，说明 EXTERNAL_KERNEL_TREE 与外部内核树这条路已通）
- 真因：Install feeds 步骤用 `echo ... > feeds.conf` 覆盖写入
  → feeds.conf 里只剩 zte_mesh，packages/luci/routing/telephony 全丢
  → ./scripts/feeds update -a 只拉了我们自己的 feed，package/feeds/luci 不存在
  （libmnl 能编出来是因为它在主仓库 package/libs/，不属于任何 feed，掩盖了问题）
- fork 的 feeds.conf.default 自带 `src-git zte_mesh https://github.com/cnjn/zte-mesh.git`，同名会遮蔽我们的源码
- 修法：以 feeds.conf.default 为模板，grep -vE 剔除 zte_mesh 行，再 printf 追加
  `src-link zte_mesh <绝对路径>`；install -a 之后校验
  package/feeds/zte_mesh/zte-mesh/Makefile 与 package/feeds/luci/luci-base/Makefile 存在
- 另核实：Kernel/Prepare/Default 外部树分支只做 `ln -s $(CONFIG_EXTERNAL_KERNEL_TREE) $(LINUX_DIR)`
  （shell 会吃掉引号，路径无空格即可）；dts 兜底检查 arch/arm64/boot/dts/zte/zx279133-sr1010.dts 确实存在

## CI 加速：缓存交叉工具链
- 痛点：tools/install + toolchain/install（binutils→gcc/initial→musl→gcc/final）每次 30-45 分钟
- 方案：actions/cache 缓存 dl/feeds/staging_dir/build_dir
  - key = owrt-<immortalwrt commit>-<kernel commit>，只含上游版本
    → 改我们自己的包/文档/workflow 不击穿缓存（这是关键设计）
  - restore-keys 两级回退 owrt-<owrt>- / owrt- ，上游 bump 时可增量复用
  - 缓存需同时包含 staging_dir 的 install stamp 与 build_dir 的 .built stamp，
    只缓存 staging_dir 的话 make 仍会重建
  - build_dir 整体缓存（不列子目录），避免部分恢复；压缩后约 2GB，在 10GB 仓库额度内
- 内核 tarball 改为幂等：存在则复用，并从落盘字节重算 SHA256 再写回
  target/linux/generic/kernel-6.18 —— 否则缓存里的旧包和哈希对不上会触发 FORCE 下载
- 加 concurrency: cancel-in-progress，避免重复 push 时两次全量构建并行
- tools/toolchain 两步前加 time，日志里能看出缓存是否生效
- 预期：首次仍 40-50 分钟，之后 8-12 分钟
- 未采用的更大杠杆（备选）：预编译 SDK 作为 release 资产；self-hosted runner

## 五次修复：kmod 依赖拖入整个内核编译
- 报错：`Makefile:75: .../packages/.pkgdir/kernel.installed Error 1`
  → `ERROR: package/kernel/linux failed to build`（curl 403/404 只是镜像重试噪音）
- 真因：package/kernel/linux/Makefile 的 `Package/kernel/install` 要装
  `$(LINUX_DIR)/modules.builtin` 与 `modules.builtin.modinfo`，这两个只有真正
  编译过内核/模块才产生；zte-mesh 的 +kmod-veth +kmod-sched-core 把 package/kernel/linux
  拉进依赖图，于是隐式要求先编完整个厂商内核
- 关键事实（两次核对 config-6.18，342 行）：没有 CONFIG_VETH、
  CONFIG_NET_SCH_INGRESS、CONFIG_NET_CLS_ACT；只有 CONFIG_NET_SCHED=y 和 fq_codel
  ⇒ 两个 kmod 在本 target 上只能是空壳包
- 额外关键点：EXTERNAL_KERNEL_TREE 模式下 LINUX_DIR 是指向克隆树的符号链接，
  内核目标文件写进那棵树而不是 build_dir ⇒ 即使缓存也救不了，每次都要重编 20-30 分钟
- 修法：新增 "Drop kernel-module deps for this build" 步骤
  - `sed -i -E 's/[[:space:]]*\+kmod-veth[[:space:]]+\+kmod-sched-core[[:space:]]*$//'`
    作用在 $GITHUB_WORKSPACE/zte-mesh/openwrt/zte-mesh/Makefile（src-link 直接生效）
  - 必须排在 make defconfig **之前**，否则 CONFIG_PACKAGE_kmod-veth=m 会被固定进 .config
  - defconfig 之后再断言没有 CONFIG_PACKAGE_kmod-(veth|sched-core)!=，防止复活
  - 源码里的 DEPENDS 保持不变（DEPENDS:=@TARGET_zte +ip-full +kmod-veth +kmod-sched-core）
- 产物语义：zte-mesh.apk 依赖 @TARGET_zte +ip-full，正是目标固件已提供的
