## 06:35 子路由页面空白（`E([..null..])`）+ B 方案：plan 启用某 band 就打开关着的 radio

### LuCI 的 `charCodeAt` 报错不是玄学
`TypeError: Cannot read properties of null (reading 'charCodeAt')` 来自 `render()` 收尾的
`E([ statusBox, child ? null : nodesSection, formNode ])`。`dom.create()` 对数组是**逐个元素递归**调
`create()`，而 `create()` 第一件事是 `html.charCodeAt(0)`，所以 `create(null)` 直接抛；而
`E('div', attrs, [ok, null])` 不抛——那条路走 `append()`，它跳过 null。差别在「数组元素」与「子节点」。
修法：那一节不进列表（`sections.push`），不是往列表里塞 null。

教训：`tests/test_luci.js` 的 `E` 桩接受任何参数，连 null 都包成对象，所以这条路径只在浏览器里炸。桩现在按
`dom.create()` 语义实现（数组递归、首参 null 抛同一个 TypeError），改视图前能复现同一个异常，改后通过。

### B 方案：radios all disabled 的机器上「配置对了、空中没有」
`wlan-sync` 新增 `enable_radio()`：某 band 的主 BSS `enabled=1`（backhaul 行同样）时写
`wireless.<radio>.disabled=0`。只写 0，从不写 1（关设备会连带杀掉该 band 的 backhaul BSS，那是控制面通路）；
不是看门狗，只在 plan 变化时跑一次，用户之后手动关掉就一直关着。`radio_off()` 认 UCI 布尔的词形
（`true`/`on`/`yes`），`radio_section_of` 判断「哪个候选还活着」也改用它。

设备侧验证（192.168.1.1，`mesh_role=slave`）：

radio radio1 (5g) was switched off; switched on so the controller's network can go on the air

## 08:00 角色拆成三个：master 只控制 / main 主控+本机落地 / slave 只被控（ad598aa）

### 为什么
原厂"主路由"= 既当主控又自己发 Wi-Fi 的盒子；但刷 OpenWrt 的机器大多是有线网关（SR1010 零射频），
所以"控制"与"自己也发"必须能分开。用户要求：master 只控制、child 只被控、main = master + child。

### 关键设计
- 线上**一个字节没改**：`main` 发 `mesh.role=auto`（原厂"主路由/自适应"，Mode 0→2 的选举替身照旧）；
  旧值 `auto` 继续接受、等同 `main`。改的只有主机侧：`write_config` 里新增 `write_local_plan` 直接产出
  `/run/zte-mesh/wlan-plan`，格式与 `agent-sync.c` 逐字段相同（rows / radio / slot / ssid / key / enabled /
  hidden / access / beacon_type），`wlan-sync` 不看来源。
- **一个 plan 只能有一个生产者**：main → init 写；slave → 服务从 M2 的行写；master/空 → `rm -f` 且不起
  `wlan-sync` 实例。slave 分支**必须一个字节都不碰**：`write_config` 在 reload 时也跑，删掉等于把正在用的
  plan 抽走，而 `agent_sync_reset()` 只在启动时调，服务不会补发（`role-slave-keeps-plan` 钉这个）。
- 5G 派生（sync / suffix / 继承密钥）只在 `write_config` 算一次（`s1_air`/`k1_air`）；`emit_band_options` 顺手
  把 `hidden`/`beacon_type` 回传给调用方（`BAND_HIDDEN`/`BAND_BEACON`），避免第二套推导漂移。
- 没加 `apply_local_wifi` 开关：**角色本身就是开关**，多一个布尔值就多一种页面上没法解释的组合。

### 踩过的坑
- `luci.zte-mesh` 工作副本变 CRLF（Edit 工具写的），设备上 `sh -n` 报
  `line 41: syntax error: unexpected word (expecting "in")` —— CR 让 `case "$1" in` 的 `in` 变成 `in\r`。
  仓库里 `*.md`/`*.sh` 一律有 LF 检查，改完要归一。README.md 也是同样原因。
- `sh /tmp/probe.sh` 里 `set -u` + `. /lib/functions.sh` → `IPKG_INSTROOT: parameter not set`；先给它赋空值。
- 直接 `. /etc/init.d/zte-mesh` 不够，`config_load`/`config_get` 来自 `/lib/functions.sh`。
- 一次内联的临时命令里 `uci delete mesh_role` 把子路由的角色删掉了（它原本是 slave）：**临时改 UCI 一定先
  记下原值再恢复**，`/run/zte-mesh/config` 里的 `mesh.role=slave` 是旧快照，不能当依据。已恢复。

### 设备证据
VM（零 wifi-device）role=main：plan 316 B/0600 rows=2（ZTEMESHCTRL / Ztemesh2631! / hidden=0 /
beacon_type=12 / access=32）、wlan-sync 实例在、`no radio device for 2g|5g; left alone`、status ok、

## 08:1x 两条分支的来龙去脉：main 落后 47 个提交，apk CI 一直绿在旧代码上

### 结论
仓库有 `main` 与 `lab-tools` 两条分支，是刻意分工，不是误操作：

- `main`：源码主线，`build-apk.yml` / `build-firmware.yml` 只由 `push: branches: [main]` 触发
- `lab-tools`：托管 host 侧预编译件（ns-run-x86_64、libzte_mesh_shim.so、db-engine-probe、
  libzte_agent_mm.so）+ 完整开发历史。`build-lab-tools.yml` 带 `contents: write`，
  编完自己 `git add -f prebuilt/ && git commit && git push origin HEAD:$GITHUB_REF_NAME`，
  所以 log 里那十几条 `lab: ns-run rc=0/0 ...` 是机器人写的。
- 必须给产物留一条分支的原因：设备靠
  `raw.githubusercontent.com/<owner>/<repo>/lab-tools/prebuilt/<file>` 直接 wget；
  Actions artifact 要登录、会过期，raw 直链只能指到分支里的文件。

### 真问题
`main` 停在 1ede69e（10-31 01:43），落后 lab-tools 47 个提交。三角色、i18n、wlan-sync B 方案、
密码统一全在 lab-tools 上，而 apk/固件 CI 只认 main → **这些改动从没被真正的构建验证过**。
`git diff main lab-tools` 里 c9b888f/1ede69e 在 lab-tools 上有等价副本（50e96a5/5595c1c，05:16 重放），
所以两分支无内容回退，只是历史分叉。

```

git checkout main && git apply --binary /tmp/main-sync.patch
```
