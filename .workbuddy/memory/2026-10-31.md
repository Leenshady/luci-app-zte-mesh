## 06:35 子路由页面空白（`E([..null..])`）+ B 方案：plan 启用某 band 就打开关着的 radio

### LuCI 的 `charCodeAt` 报错不是玄学
`TypeError: Cannot read properties of null (reading 'charCodeAt')` 来自 `render()` 收尾的
`E([ statusBox, child ? null : nodesSection, formNode ])`。`dom.create()` 对数组是**逐个元素递归**调
`create()`，而 `create()` 第一件事是 `html.charCodeAt(0)`，所以 `create(null)` 直接抛；而
`E('div', attrs, [ok, null])` 不抛——那条路走 `append()`，它跳过 null。差别在「数组元素」与「子节点」。
修法：那一节不进列表（`sections.push`），不是往列表里塞 null。

教训：`tests/test_luci.js` 的 `E` 桩接受任何参数，连 null 都包成对象，所以这条路径只在浏览器里炸。桩现在按
`dom.create()` 语义实现（数组递归、首参 null 抛同一个 TypeError），改视图前能复现同一个异常，改后通过。

### B 方案：radios all disabled 的机器上「配置对了、空中没有」
`wlan-sync` 新增 `enable_radio()`：某 band 的主 BSS `enabled=1`（backhaul 行同样）时写
`wireless.<radio>.disabled=0`。只写 0，从不写 1（关设备会连带杀掉该 band 的 backhaul BSS，那是控制面通路）；
不是看门狗，只在 plan 变化时跑一次，用户之后手动关掉就一直关着。`radio_off()` 认 UCI 布尔的词形
（`true`/`on`/`yes`），`radio_section_of` 判断「哪个候选还活着」也改用它。

设备侧验证（192.168.1.1，`mesh_role=slave`）：
```
radio radio2 (2g) was switched off; switched on so the controller's network can go on the air
radio radio1 (5g) was switched off; switched on so the controller's network can go on the air
applied; wireless committed and reloaded
```
`iwinfo`：`phy1-ap0`（5 GHz ch36, HE80）与 `phy2-ap0`（2.4 GHz ch1, HE20）都是 `ZTEMESHCTRL`，空卡
`radio0` 仍 `disabled=1`。这是第一次真正「无线的端到端」：控制器的 SSID 在空中。

## 07:00 界面中文：三条断链（cca4627）

页面一直是英文，不是没写 `_()`，而是三处：

1. **po 与源码漂移**：`po/zh_Hans/zte-mesh.po` 少了 2 条（改过的 `mesh_role` 说明、默认密码
   `Ztemesh2631!`），14 条中文用半角逗号；文件头没有 `Plural-Forms`，po2lmo 因此不写哈希 0 那条
   （`load_catalog` 从这里拿 nplurals）。已对齐 180 条，标点统一全角（数字列表保持半角）。
2. **CI 没编翻译包**：`luci.mk` 把每个 `po/<lang>/` 编成**独立包** `luci-i18n-<app>-<lang>`，
   `build-apk.yml` 只 `build luci-app-zte-mesh/compile`，所以三个 apk 里从来没有中文目录。
   已补 `luci-i18n-zte-mesh-zh-cn/compile` 并把「三个 apk 都得在」加进断言。
3. **设备上没有 lmo**：实验室是拷文件不是装包。新增 `tools/lab/po2lmo.py`（照
   `po2lmo.c`/`lmo.c`：字符串块 + 16 字节索引 + 结尾块长度；键 = SuperFastHash，种子是长度
   **不是** 长度+init）。

**lmo 格式要点**（踩过的坑）：
- 头文件那条（msgid ""）靠 `msg->id == NULL` 区分——C 里空 msgid 不分配指针，所以走的是「只写
  `Plural-Forms:` 后面那一段」的分支。我的 parser 一开始按 `id == ''` 走普通分支，写出了一条
  `"00000000":"Content-Type: ...\nLanguage: ..."` 的垃圾条目（端点里能直接看到）。
- `sfh_hash(data, len, init)` 里 `hash = init`（luci 版本），经典 SuperFastHash 是 `len + initval`；
  写错就一条都查不到。
- 尾部 4 字节是字符串块长度，索引是 `(key, nplurals, offset, length)` 大端、按 key 排序。

**怎么验证到底有没有生效**：`/cgi-bin/luci/admin/translations/<lang>` **不需要鉴权**，直接
`wget -qO-` 就能看到 `window.TR={"<sfh_hash>":"<译文>"}`。例如 `"bf869601":"中兴组网"`
（`sfh_hash("ZTE Mesh")`）。这比看页面可靠——页面还有静态资源缓存（要 Ctrl+Shift+R）。
服务端则用 `ucode -e 'import {load_catalog,change_catalog,translate} from "luci.core"; ...'`。

菜单标题走同一条目录（`menu-bootstrap.js` 用 `_()` 包 title），所以 `ZTE Mesh` → 中兴组网。

测试：`tests/test_i18n.py` 12 项（覆盖率 / 无废条目 / `%s` 顺序 / `.description` 漏 `_()` /
编译后逐条查表 / 索引有序 / 未知串保持原文），已进 `make test-host`。luci-app release 5。
