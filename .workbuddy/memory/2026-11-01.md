## 00:40 中兴 E1630/E2631 编程器固件（132 MiB）静态解包

用户给的 `F://zte e1630 编程器固件\F35SQA001G(ECC_EN)@WSON8_20260322_223737.BIN`，产物放在同目录
`_analysis/`（REPORT.md、e1630.raw、kernel.uImage、vmlinux.bin、board.dtb、aesbrute.c）。

- **格式**：132 MiB = 65536 页 × (2048+64)，OOB **逐页全 0xFF** → 编程器关 ECC 裸读，剥掉得 128 MiB 逻辑镜像。
  （`4096+128` 也能整除 132 MiB，但 2112 分块的 OOB 位置 65536/65536 全 0xFF，排除了 4 KiB 页假设。）
- **设备**：ZTE **ZX279128S** 双核 A9 + 128 MB DDR + Denali NAND；Linux **4.1.25**、Buildroot 2015.08.1、
  gcc 4.9.3，2024-09-25 编；U-Boot 2013.04 + ZTE cspboot（双版本、签名校验、`zteflashinfo=`）。
- **型号对不上**：文件名 e1630，配置块自报 `ZXHN E2631`；`E1630` 只是 U-Boot 支持机型表里的一项。
- **布局**：0x0 引导签名头(`0001ZXIC/BOOTROM/RSA2048`) → 0xC0000 U-Boot env → 0x100000 出厂配置块 →
  0x2C0000/0x3C0000/0x5C0000 三个明文 JFFS2（caldata / `[global] SN=2419063068E5` / 串口日志）→
  0x700000 kernel uImage（hcrc+dcrc 双对，解压 6,627,680 B）→ 0xA40000 rootfs 密文 → 0x2300000 第二份拷贝
  （7.0–32.6 MiB 与 35.0–60.6 MiB 逐字节相同）→ 0x72C0000 `uu.conf`+`uu` 工具 → 其余 0xFF。
- **rootfs 打不开**：熵 8.00 / zlib 比 1.00；无任何 FS 魔数；尾部 1780 个连续相同 16 B 块 → **AES-ECB**；
  非固定 XOR（异或后熵仍 7.999）。写 `aesbrute.c`（FIPS-197 自检）把镜像每个 16 B 窗口
  （134,217,712 个）当密钥解那个重复块，要求全 0/全 FF → **0 命中**，密钥不在固件里（与 E2633 结论一致）。
- **mesh 线索**：配置块有 `ZMESH-7fTSDh`（mesh 专用 SSID 前缀）；vmlinux 符号表有 `ieee1905_msg`、
  `wlan_get_wlan_multiap_mode`、`wlan_cspkernel_ops`/`get_wlan_cspkernel_param`、`cspd.*` 调试模块名
  → 用户态 cspd 经 `cspkernel` 字符接口驱动无线驱动，1905 由驱动收发，Multi-AP 是开关位。
  印证 MESH_INTEROP 硬约束：mesh 能力必须走 CMDU/TLV。
- **坑**：JFFS2 节点在这份固件里是**小端**存的（`85 19 02 e0` 按 LE 解才对，BE 解 totlen 会变成 84 MB）；
  写 C 的时候手推 AES T-table 两次都错，最后退回教科书字节实现 + FIPS-197 自检才通过。

## 03:10 逆 E2631 内核读路径（无解密）+ 内核 1905 痕迹（`2e5e0be`）

对 `F://zte e1630 编程器固件\_analysis\vmlinux.bin`（6,627,680 B，dump 那版 2024-09 内核）做静态分析。

- **恢复方法**（镜像无 ELF 头、kallsyms token 表找不到）：
  - `__bug_table` = `{u32 bug_addr; u32 file; u16 line; u16 flags}` **绝对指针**（ARM 4.1 不是
    GENERIC_BUG_RELATIVE_POINTERS；曾按相对指针解，file_disp 得偏移 4 的假条目）。筛出 1908 条
    (addr, file, line)，375 个文件 → 函数级地图。
  - `__ksymtab` = `{u32 value; u32 name}`，各 6393 个导出符号。**必须过滤 value 处"像不像 ARM 指令"**，
    否则 name 指针会被当成 value（0xC05B0xxx / 0xC05A4xxx 全是 ksymtab_strings，不是函数）。
  - 基址 **0xC0008000**（`w - 文件偏移` 投票；注意别用 0xFFFFFFF 掩码，28 位会把结果切坏）。
  - 工具：`_analysis/kmap2.py`（KernelMap：bugs/ksymtab/file_at/text_range）、`_analysis/xref.py`
    （movw/movt 配对 + `ldr pc` 字面量，从字符串反查引用代码）。**脚本不入库**，同 elfsym.py 惯例。
- **① 结论：rootfs 解密不在内核**。`zx_denali_nand.c` 3 个 BUG 点 0xC023FE2C(L1261)/0xC0240080(L1454)/
  0xC0240B6C(L1370)，读页路径全是 Denali 寄存器序列（0x2200/0x2300/0x2400 命令码、`dsb st`、DMA），
  无 crypto 调用。旁证：内核只编 `crypto/{algapi,api,scatterwalk}.c`；无 `ecb(aes)`/`cbc(aes)` 串；
  AES 原语在（`crypto_aes_set_key`@0xC015A194、T 表@0xC045D690/0xC0464668）但它是 `cia_setkey` 回调、
  无直接调用者，`"aes"`（0xC052AF40/0xC063A278）零引用；`CBC decrypt OK!` 在 **0x619E**（Bootloader
  分区，与 HASH/RSA timeout 同段）。→ 密钥只剩 BOOTROM/cspboot、控制器硬件透明解密、eFuse/OTP 三处。
  **可证伪判据**：能 root 的同型号机器 `dd if=/dev/mtdblock8 bs=2048 count=1` 读到明文 ⇔ 硬件透明解密。
- **② 内核里的 1905 只有三件事**：
  - `br_ieee1905_check_is1905_msg`@0xC02AFB3C：比 `htons(0x893a)=0x3a89`，**并且认 802.1Q
    （比较值 0x81 = 0x8100 网络序），剥 VLAN 后取 head+offset174+16 再比** —— 新知识。
  - 桥接钩子@0xC02AFB84（ops 在 0xC0617954，`br_ieee1905_filter_init`@0xC05F723C 注册，失败打印
    "register nf hooks failed"@0xC0572614）：全局开关 0xC064EED8；目的 MAC 组播位 0 则放行；
    是 1905 则 **NF_DROP**。→ 这就是 lab 里 `0x893a` 被网桥泛洪回 zmesh0 而真机不会的原因
    （上一轮自检假阳性的根因）。
  - `wlan_get_wlan_multiap_mode`@0xC02AF210：`movw/movt 0xC066BFA8; ldr [r3,#0x94C]; bx lr`
    —— 三条指令，Multi-AP 在内核就是个 u32 位。没有 TLV/CMDU/拓扑解析。
  - 另：13 条 `cspd.*` 日志 view 名、22 条 `/zte/csp/opensource/cspkernel4.1/...` 源文件路径
    （无一是 mesh）、`[wlan_cspkernel] [%s(%d)] : %s(%s)!`@0xC0572198。8 处 `ieee1905_msg`
    碎片无引用，**标为未确证，不下结论**。
- **文档**：MESH_INTEROP 新增 §4.1（读路径无解密，含证伪判据）与 §5（1905 全景，原 5/6/7→6/7/8）；
  §1 加结论 6、§2 表加"ZTE 内核"行；FEATURE_STATUS B22；README 索引描述；
  WIRESHARK_1905 里"第 6 节"引用改"第 7 节"。
- **坑**：Windows 上 `Path.write_text()` 默认把 `\n` 翻成 `\r\n`——改完文档必须用

## 分析 `F:/中兴E2633转正/Telnet/`（市售 E2633「转正」工具链）

- **负结果**：拿配置密钥族去试 e1630 rootfs（0xA40000，84 组派生 × ECB/CBC × 128/192/256），
  熵仍 7.996、zlib 比 0.996 → **配置密钥与 rootfs 无关**，别再重复这条便宜的猜测。

  传输三条路（curl→wget→base64）按设备能力降级。
- **工具小坑**：Windows 上 python 打不开中文路径（文件系统编码），要把它当 `sys.argv` 传进去。

## 真机 telnet 能不能解 rootfs（MESH_INTEROP §4.2）

- **结论**：不用解。JFFS2 在 mtdblock8 挂得上 ⇒ 内核从 MTD 读到的就是明文节点，
  `dd if=/dev/mtdblock8` 与 `cat` 拿到同一份字节，中间没有要解的一层。17 MiB，tftp -p 传回即可。
- **纠正**：`VENDOR_MESH_STACK` §1 的"JFFS2 明文"是从 mount/df（jffs2、17MiB、100% 占满）推的，
  **没做过 hexdump**；§4.1 的判据一直没真跑。§4.2.2 补了只读 dd 与三种输出的分叉表。
- **密钥（解别人的编程器 dump）**：只有 RAM 一条路，期望值低。判据用 E2633 dump 里已知明文的
  `AES_ECB(FF×16)=9b58f878 bbb34136 6b2b543d affb0185`（重复 5906 次），对每个 4B 对齐候选 key
  一次块加密即判；范围 System RAM 256MiB，重点低 64–128MiB；`/kmodule/bin/devmem2` 可试 /dev/mem。
  **重要边界**：用 E2633 密文验 E2631 的 RAM 依赖"同密钥组"（只有 0238002E 五机型共用的旁证），
  所以"全空"不能单独证明 OTP，它同样兼容"每台设备一把 key"——要分开必须在同一台机器同时有 RAM 和它的 dump。
- **明确不做**：把密文写回 NAND 再读（只是解密服务，AES 下推不出 key，且是唯一可能变砖的操作）。
- **rootfs 真正的价值**：`/etc/init.d`（cspd/multiapd 启动参数与顺序）、`/etc/scripts`（区域/模式）、
  Web CGI（写 DB 的字段名 = D3–D6 的入口命名）、谁 dlopen `libzte_agent_mm.so`（D6 调用点）。
  二进制不用再取（multiapd 已有）。
- 已提交 0b01426（§4.2 + §7 两行 + §4.1 补注）。领先 origin 6 个提交。

## 真机取 rootfs 踩坑：tftp "can't open /tmp/rootfs.jffs2"

- **现象**：`dd if=/dev/mtdblock8 of=/tmp/rootfs.jffs2` 之后 `tftp -p -l ...` 报本地文件不存在。
- **四类成因**（写进 MESH_INTEROP §4.2.3 表）：/tmp 在 100% 占满的 rootfs 上（ENOSPC）／tmpfs 太小被
  OOM kill（rc=137）／没有 /tmp 要用 /var/tmp／busybox 没编 tftp put。
- **另两类"文件消失"**：整段粘贴时末尾的 `rm` 已执行；/tmp 是 tmpfs，重启即清。——先在对端 `ls -l` 分开。
- **定性最快一步**：`dd if=/dev/mtdblock8 bs=2048 count=1 2>&1 | hexdump -C | head -4`，不落盘，
  同时回答"读不读得出"和"是不是明文（85 19）"。
- **兜底两条**：分块 dd（2 MiB×9，实验机 cat 拼回并验 85 19）；或流式 `dd | curl -T -`。
  后者缺对端服务，已补 **`tools/lab/httpput.py`**（Content-Length + chunked、直写磁盘、.part 后 rename、
  basename 限根）。自测 3 000 001 B 随机数据两种传输逐字节一致、GET 回读一致、路径穿越受限。
- 已提交 c1b82c4。领先 origin 7 个提交。

## rootfs.jffs2 解开：三个坑 + mesh 配置库 schema（本轮最大产出）

- 输入 `F:/zte e1630 编程器固件/rootfs.jffs2`，17 825 792 B（=mtd8 尺寸），首 8 字节 `85 19 01 e0…`
  ⇒ **读路径返回明文**，MESH_INTEROP §4.1 判据正式结案（结论是当年列的第 2 条：不用解）。
- **坑 1（最重要）**：这份 JFFS2 是**变体** —— inode 头 **68 字节**（标准 64），
  `data_crc`@0x3C 后还多 4 字节未知字段(0x40) 才到 `data`@0x44；且 `ino`@0x0C / `version`@0x10
  与标准顺序**相反**。标准工具（jefferson / jffs2dump）会**静默解出垃圾**，不报错。
- **坑 2**：**JFFS2 的 CRC 不是 zlib 的** —— reflected poly `0xEDB88320`、`init=0`、**无收尾异或**。
  用 `zlib.crc32()` 会把全部节点判坏（bad hdr_crc 6412）。
- **坑 3**：`85 19` 是**小端** `0x1985`（ARM），`19 85` 才是大端。先写反导致 skipped 4.4 MB / inodes 0。
- 自写 `tools/lab/unpack_jffs2.py`（纯标准库、自动判字节序、data_crc 投票选 std64/zte68 布局）
  + `tools/lab/unpack_squashfs.py`（squashfs 4.0，gzip/lzma/xz/lz4/zstd，Cursor 跨块顺序读）。
  验证：bad hdr_crc 0 / bad data_crc 0 / inodes 518 dirents 518；squashfs inodes 1003、dir 57 / file 831 / symlink 115。
- **解包结果**：518 个 inode 里 **411 个是 /dev 空设备**，真实条目只 107 个；`/bin /lib /usr /home`
  → `./kmodule/*`，`/userconfig` → `/defcfg`。**没有 `/etc/init.d`、没有 `/www`**；启动链 `rc → init.norm → initwifi → pc&`。
- **mtd→挂载点权威表**（`/etc/init.norm`）：mtd3 /wlan、4 /usercfg、5 /defcfg、8 /、9 /UUPlugin、
  10 /owdptsplugin/bin、11 /status、12 /DPIPlugin、13 /UnifiedStorage、14 /owjdxbplugin/bin。
- **身份**：hostname `E2631`、账号 `Z500_w9bZ`、`/etc/hardcode` = `E2631_QD_MESH`、构建 2026-08-26、MT7916 11AX 11k/11v。
- **编译期证据**：`/etc/autokernelconf`（3498 行内核 .config）、`/etc/autouserconf`（612 个 `@define` = cspd 开关）。
  两条结论：`CONFIG_CRYPTO_AES=y` 但**没有 NAND crypto 消费者**；`CONFIG_CMDLINE_FROM_BOOTLOADER=y`
  解释 `mem=128M` 与 256M 的差异。**没有 11r**（只有 `CONFIG_CSP_WLAN_SUPPORT_80211KV`）。
- **§6 mesh 配置库 schema（核心产出）**：表 `P1905ComCfg` / `MultiAPMaster` / `MultiAPDomain`(MULTIAPDOMAIN%d) /
